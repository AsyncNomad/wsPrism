# 인증과 권한

모든 연결은 WebSocket 핸드셰이크에서 자격 증명을 내밉니다. 그것이 누구의 것이고 그 사용자가 무엇을 할 수 있는지는 테넌트의 **인증 사슬**이 판단합니다. 이 단계를 통과하기 전에는 어떤 서비스에도 메시지가 닿지 않습니다.

## 자격 증명을 보내는 곳

게이트웨이는 클라이언트가 내미는 것을 모두 *티켓*이라고 부릅니다. 1회용 티켓이든 JWT든 직접 만든 인증기가 알아보는 무언가든 마찬가지입니다. 테넌트는 클라이언트가 티켓을 어디에 실을 수 있는지 순서대로 나열합니다(`policy.ticket_sources`).

| 위치 | 클라이언트가 보내는 방법 | 어울리는 곳 |
|---|---|---|
| `header` | `Authorization: Bearer <ticket>` | 네이티브 앱, 게임 엔진, 서버 |
| `subprotocol` | `Sec-WebSocket-Protocol: wsprism.v2.json, wsprism.auth.<ticket>` | WebSocket에 헤더를 붙일 수 없는 브라우저 |
| `query` | `?ticket=<ticket>` | 레거시 클라이언트 전용 |

기본값은 `[header, subprotocol]`입니다. 쿼리스트링을 일부러 뺀 이유는 URL이 프록시와 액세스 로그에 그대로 남기 때문입니다. 로그에 남은 자격 증명은 이미 유출된 자격 증명입니다. 굳이 켜야 한다면 한 번 쓰면 쓸모없어지는 1회용 티켓하고만 쓰세요.

게이트웨이는 핸드셰이크 응답에 `wsprism.auth.*` 항목을 돌려보내지 않습니다.

## 인증 사슬

`tenants[].auth`는 인증기를 순서대로 늘어놓은 목록입니다. 각 인증기는 티켓을 보고 다음 넷 중 하나를 합니다.

- **받아들입니다.** 사용자 ID와, 있으면 권한과 만료 시각을 돌려줍니다.
- **거절합니다.** 클라이언트는 HTTP 401을 받습니다.
- **지금은 판단할 수 없다**고 알립니다. IdP에 닿지 않을 때가 그렇습니다. 클라이언트는 HTTP 503과 `Retry-After`를 받으므로, 자격 증명이 틀렸다고 오해하지 않고 다시 시도합니다.
- **자기가 다루는 티켓이 아니라고** 넘깁니다. 그러면 다음 인증기 차례입니다.

덕분에 한 테넌트가 브라우저에서는 1회용 티켓을, 서비스 간에는 JWT를 동시에 받을 수 있습니다.

```yaml
tenants:
  - id: acme
    auth:
      - kind: ticket
      - kind: jwt
        algorithm: RS256
        jwks_url: "https://idp.example.com/.well-known/jwks.json"
        issuer: "https://idp.example.com/"
```

어느 인증기든 돌려주는 사용자 ID는 `[A-Za-z0-9_-]` 1~64자여야 합니다. 사용자 ID가 내부 키의 일부가 되기 때문에, 그 밖의 값은 거절하고 로그에 남깁니다.

`auth`가 없는 테넌트는 개발용 인증기로 돌아가고 시작할 때 경고를 남깁니다. 내 노트북이 아닌 곳에서 이 경고가 보이면 오류로 여기세요.

## 1회용 티켓

사용자가 이미 백엔드에 로그인하고 있다면 가장 간단한 방법입니다.

1. 사용자는 평소대로 백엔드에 로그인합니다.
2. 백엔드가 게이트웨이 서버 API의 `POST /api/v1/tickets`를 사용자 ID와(필요하면) 룸 권한을 담아 호출합니다.
3. 받은 티켓(`wpt_…`)을 클라이언트에 돌려줍니다.
4. 클라이언트는 티켓 수명(기본 30초, 최대 300초) 안에 그 티켓으로 접속합니다.

```bash
curl -s -X POST http://127.0.0.1:8081/api/v1/tickets \
  -H "Authorization: Bearer $API_KEY" \
  -d '{"user":"alice","permissions":{"subscribe":["match:*"],"publish":["match:42"]}}'
# {"ticket":"wpt_...","expires_in_s":30}
```

티켓은 처음 제시되는 순간 소비됩니다. 다른 테넌트로 접속하는 식으로 그 시도가 실패해도 마찬가지입니다. 그래서 새어 나간 티켓으로 다시 시도할 수 없습니다. 클러스터에서는 티켓을 Redis에 저장하므로(티켓 자체가 아니라 SHA-256만 저장합니다) 한 노드가 발급한 티켓을 어느 노드에서든 한 번 쓸 수 있습니다. Redis가 내려가 있으면 티켓 로그인은 503으로 막힙니다.

테넌트의 `auth`에 `kind: ticket`이 없으면 발급 요청은 400을 받습니다.

## JWT

이미 JSON Web Token을 발급하고 있다면 게이트웨이가 누구에게도 묻지 않고 직접 검증합니다.

```yaml
      - kind: jwt
        algorithm: HS256
        secret_file: /run/secrets/jwt       # 또는 secret_env. 설정에 직접 쓰지 않습니다
        issuer: "https://auth.example.com"  # 선택. 지정하면 iss 필수
        audience: "wsprism"                 # 선택. 지정하면 aud 필수
        leeway_s: 30
```

- `sub`가 사용자 ID입니다. `exp`는 필수이고 `nbf`도 지킵니다.
- 알고리즘은 인증기마다 고정입니다. 헤더에 다른 알고리즘이 적힌 토큰은 다음 인증기로 넘기며, 절대 다른 알고리즘으로 검증하지 않습니다. 고전적인 알고리즘 혼동 공격을 막는 장치입니다.
- HMAC 비밀은 해시 길이(32, 48, 64바이트) 이상이어야 합니다.
- `kid`를 지정하면 그 키 ID를 단 토큰만 봅니다. `kid`가 다른 `jwt` 항목 두 개를 두면 정적 키를 중단 없이 교체할 수 있습니다.

wsPrism 전용 클레임은 `wsprism` 객체 하나 아래에 모아서, 발급자의 클레임과 부딪치지 않게 했습니다.

```json
{
  "sub": "alice",
  "exp": 1760000000,
  "wsprism": { "tenant": "acme", "subscribe": ["match:*"], "publish": ["match:42"] }
}
```

다른 테넌트를 가리키는 토큰은 언제나 거절합니다. `require_tenant: true`로 두면 이 클레임이 반드시 있어야 합니다.

### JWKS

Auth0, Cognito, Keycloak, Okta 같은 IdP를 쓴다면 키 파일 대신 IdP의 키 세트를 가리킵니다.

```yaml
      - kind: jwt
        algorithm: RS256
        jwks_url: "https://idp.example.com/.well-known/jwks.json"
        jwks_refresh_s: 300
        jwks_min_refetch_s: 30
        jwks_max_stale_s: 86400
```

키는 처음 쓸 때 가져오고 그 뒤로는 백그라운드에서 갱신합니다. 처음 보는 `kid`가 담긴 토큰이 오면(IdP가 방금 키를 바꿨다면) 즉시 한 번 다시 가져오되, 아무 `kid`나 만들어 IdP를 두들기지 못하도록 횟수를 제한합니다. 갱신이 계속 실패하면 마지막으로 받은 키를 최대 `jwks_max_stale_s` 동안만 쓰고, 그 뒤에는 IdP가 이미 폐기했을지 모를 키를 믿는 대신 503으로 답합니다. URL로 받은 대칭 키는 쓰지 않습니다.

## connect 프록시

접속 여부를 백엔드 고유의 로직으로 판단해야 한다면 게이트웨이가 백엔드에 묻게 합니다.

```yaml
      - kind: proxy
        url: "http://10.0.0.5:9000/wsprism/connect"
        timeout_ms: 2000
        max_in_flight: 256
        secret_env: BACKEND_SECRET
```

게이트웨이는 연결마다 다음 요청을 보냅니다.

```json
POST /wsprism/connect
{"tenant": "acme", "token": "<ticket>", "client_ip": "203.0.113.7"}
```

백엔드가 받아들이려면 이렇게 답하고,

```json
200 {"user": "alice", "permissions": {"subscribe": ["room:*"]}, "expires_at": 1760000000}
```

(`permissions`, `expires_at`은 선택) 거절하려면 401이나 403으로 답합니다. 그 밖의 상태 코드, 시간 초과, 백엔드에 닿지 않는 경우는 모두 503과 `Retry-After`로 바뀝니다. 백엔드 장애가 클라이언트에게 "자격 증명이 틀렸다"로 전달되는 일은 없습니다.

프록시는 어떤 토큰이든 받아들이므로 사슬의 **맨 끝**에 둡니다. 토큰이 백엔드까지 가니, 신뢰할 수 있는 네트워크 밖이라면 `https`를 쓰세요.

## 직접 만든 인증기

Rust에서 `Gateway::builder().auth_plugin(...)`으로 팩토리를 이름과 함께 등록하고, 설정에서 그 이름을 씁니다.

```yaml
    auth:
      - kind: plugin
        name: corp_sso
        options: { realm: "staff" }
```

팩토리는 게이트웨이를 빌드할 때 `options`를 받으므로, 설정 오류는 시작 시점과 `--check-config`에서 드러납니다. 인증기는 신원을 돌려주거나, 내장 인증기와 똑같은 세 가지 거절 가운데 하나를 돌려줍니다. [Rust API](../reference/rust-api.md)를 참고하세요.

## 권한

인증기는 세션에 목록 두 개를 붙일 수 있습니다.

- `subscribe`: 들어갈 수 있는 룸
- `publish`: 발행할 수 있는 룸

항목은 정확한 이름이나 `prefix*` 패턴입니다. 목록을 아예 빼면 제한이 없고, 빈 목록이면 아무것도 허락하지 않습니다. 권한 없이 들어온 사용자는 테넌트 정책의 제약만 받습니다.

룸에 들어가려면 `subscribe`가 필요합니다. 서비스가 사용자를 대신해 발행할 때도 `publish`가 필요합니다. `chat`, Hot 릴레이 같은 내장 서비스든 직접 만든 서비스든 마찬가지입니다. 이 검사는 서비스 컨텍스트 자체에 들어 있으므로, 커스텀 서비스가 깜빡하고 빠뜨릴 수 없습니다.

## 만료와 연결 중 갱신

자격 증명이 만료되면(JWT의 `exp`, connect 프록시가 준 `expires_at`) 게이트웨이는 세션을 닫습니다. 프로토콜 v2에서는 종료 코드 4001 `auth_expired`입니다. 만료는 단조 시계로 1초마다 확인합니다.

재접속하지 않으려면 열린 연결 위에서 자격 증명을 갱신하면 됩니다.

```json
{"v":1,"svc":"sys","type":"refresh","seq":7,"data":{"token":"<new token>"}}
{"v":1,"svc":"sys","type":"refreshed","reply_to":7,"data":{"expires_in_s":900}}
```

새 토큰은 새 연결과 똑같이 인증 사슬을 거치며, 같은 사용자의 것이어야 합니다. 새 토큰의 권한은 즉시 이전 권한을 대신합니다. 새 토큰이 더는 허락하지 않는 룸에서는 나가게 되고, 클라이언트는 룸마다 `sys.left`를 받습니다. 갱신에 실패하면 세션은 원래 만료 시각까지 이어지다가 닫힙니다. 갱신은 한 번에 하나, 1초에 한 번까지입니다.

JavaScript SDK는 이 과정을 알아서 처리합니다. 자격 증명 수명의 70~90% 사이 임의의 시점에 갱신하므로, 수많은 클라이언트가 한꺼번에 토큰 서비스를 두드리지 않습니다.

## 자격 증명보다 먼저: 입장 검사

인증기가 티켓을 보기 전에 여러 검사가 가벼운 순서대로 먼저 돕니다.

1. **핸드셰이크 속도 제한**: 전체 한도와 클라이언트 주소별 한도가 있습니다(IPv6는 기본적으로 /64 단위로 묶습니다). 넘으면 429와 `Retry-After`를 받습니다. 로드밸런서 뒤에 있다면 `gateway.trusted_proxies`에 로드밸런서를 적어 `X-Forwarded-For`에서 진짜 클라이언트 주소를 읽게 하세요. 오른쪽에서부터 처음 만나는 신뢰할 수 없는 주소만 쓰므로 클라이언트가 위조할 수 없습니다.
2. **`sid` 검사**(400)
3. **드레인 중인지**: 종료 중인 노드는 503으로 답해 다른 노드로 가게 합니다.
4. 클러스터라면 **과부하 보호**: Redis가 너무 느리면 새 연결을 503 `cluster_busy`로 거절합니다.
5. **테넌트 확인**(400)과 **프로토콜 협상**(게이트웨이가 아는 버전을 하나도 내밀지 않으면 400)
6. 브라우저의 **Origin 검사**: `policy.allowed_origins`와 대조합니다(403). `Origin` 헤더가 없는 요청은 브라우저가 아니므로 검사하지 않습니다.
7. **테넌트 수용량**(`max_sessions_total`): 503과 `Retry-After`

이 모두를 통과해야 비로소 티켓을 읽고 인증 사슬에 묻습니다. 인증을 맨 뒤에 둔 덕에, 다른 이유로 거절될 연결 때문에 JWT 서명을 검증하거나 백엔드를 호출하거나 1회용 티켓을 날리는 일이 없습니다.
