# 룸, 프레즌스, 이력

실시간 애플리케이션은 대부분의 시간을 룸에서 보냅니다. 경기 하나, 문서 하나, 채팅 채널 하나, 종목 하나가 각각 룸입니다. 이 장에서는 룸에 들어가고 나오는 법, 누가 함께 있는지 아는 법, 끊긴 사이의 메시지를 따라잡는 법을 다룹니다.

## 들어가기와 나오기

```json
{"v":1,"svc":"room","type":"join","room":"match:42","seq":1}
{"v":1,"svc":"sys","type":"joined","room":"match:42","chan":17,"member_id":4097,"reply_to":1}

{"v":1,"svc":"room","type":"leave","room":"match:42","seq":2}
{"v":1,"svc":"sys","type":"left","room":"match:42","reply_to":2}
```

다음 조건을 모두 만족해야 들어갈 수 있습니다.

- 테넌트가 `room:join`을 허용합니다.
- 사용자에게 `subscribe` 권한이 있다면 그 권한이 이 룸을 포함합니다.
- 테넌트 한도에 여유가 있습니다. 테넌트 전체의 `max_rooms_total`, 그 룸의 `max_users_per_room`, 그 사용자의 `max_rooms_per_user`(기본 64. 룸 하나에 들어갈 때마다 여러 색인에 메모리가 들기 때문입니다)입니다.

한도에 걸리면 `RESOURCE_EXHAUSTED`가 옵니다. 같은 룸에 두 번 들어가도 문제없고, 아무 알림도 나가지 않습니다.

`sys.joined` 응답에는 Hot 레인에서 중요한 식별자 두 개가 실립니다. `chan`은 이 연결에서 쓰는 룸의 숫자 ID이고, `member_id`는 이 멤버십이 Hot 프레임을 보낼 때의 송신자 ID입니다. 둘 다 불투명한 값으로 다루고, 재접속하면 바뀔 수 있다고 생각하세요.

세션이 어떤 이유로든 닫히면 들어가 있던 룸에서 모두 나갑니다.

## 발행

내장 `chat` 서비스는 보낸 사람이 들어가 있는 룸에 메시지를 뿌립니다.

```json
{"v":1,"svc":"chat","type":"send","room":"match:42","data":{"msg":"gg"}}
```

직접 만든 서비스는 컨텍스트를 통해, 백엔드는 서버 API(`POST /api/v1/publish`)로 발행합니다. 서버 API로 보낸 메시지는 멤버에게 `{"svc":"server","type":"publish","room":…,"data":…}` 형태로 도착합니다.

한 룸 안에서는 모든 멤버가 Ext 메시지를 같은 순서로 받습니다. 클러스터의 어느 노드에 있든 마찬가지입니다.

## 프레즌스

룸에 누가 있는지 아는 방법은 두 가지입니다.

- **백엔드에서:** `GET /api/v1/rooms/{room}/presence`가 룸에 있는 사용자 목록을 돌려줍니다. 사용자마다 한 번씩만 나오고, 클러스터라면 모든 노드를 합친 목록입니다.
- **클라이언트에서:** `policy.presence_events: true`이면 누가 들어오고 나갈 때 멤버들에게 알리고, 입장 응답에 이미 있던 사람들의 목록을 실어 줍니다.

```json
{"v":1,"svc":"sys","type":"member_joined","room":"lobby","data":{"user":"bob","member_id":7}}
{"v":1,"svc":"sys","type":"member_left","room":"lobby","data":{"user":"bob","member_id":7}}
```

룸을 떠나는 모든 경로에서 `member_left`가 나갑니다. 직접 나간 경우, 연결이 끊긴 경우, 다른 세션에 밀려난 경우, 서버 쪽에서 강제로 종료한 경우가 다 포함되고, 클러스터에서는 그 멤버가 있던 노드가 죽은 경우도 해당합니다(그 노드의 `slot_ttl_s`에 몇 초를 더한 시간 안에 정확히 한 번 나갑니다). `sys.joined`의 목록은 최대 1,000명까지 담고, 그보다 많으면 `members_truncated`를 표시합니다.

프레즌스 이벤트는 기본적으로 꺼져 있습니다. 들어오고 나갈 때마다 룸 전체에 알림이 가기 때문입니다. 1만 명이 있는 룸이라면 대부분 들여다보지도 않을 정보에 트래픽이 꽤 듭니다. 경기, 문서, 작은 채널처럼 누가 있는지가 중요한 룸에만 켜세요.

`member_id`는 그 멤버가 보내는 Hot 프레임의 `sender`와 같은 값입니다. 그래서 클라이언트는 따로 장부를 두지 않고도 나간 플레이어의 아바타를 지울 수 있습니다.

## 이력

룸이 최근 메시지를 남겨 두면, 끊겼다 다시 들어온 클라이언트가 놓친 메시지를 받을 수 있습니다. 이력은 테넌트마다 룸 이름에 대한 규칙으로 설정합니다. 처음 맞는 규칙이 적용되고, 어떤 규칙에도 맞지 않는 룸은 아무것도 남기지 않습니다.

```yaml
tenants:
  - id: acme
    history:
      - { rooms: "chat:*", size: 200, ttl_s: 600 }
      - { rooms: "orders", size: 1000, ttl_s: 3600, max_bytes: 4194304 }
```

| 항목 | 기본값 | 범위 | 의미 |
|---|---|---|---|
| `rooms` | | 이름 또는 `prefix*` | 규칙이 적용되는 룸 |
| `size` | 200 | 1~10,000 | 룸마다 남길 메시지 수 |
| `ttl_s` | 600 | 1~86,400 | 메시지를 남겨 두는 시간(초) |
| `max_bytes` | 1 MiB | 1 KiB~64 MiB | 룸마다 남길 바이트 수. 오래된 것부터 지웁니다 |

메모리는 `max_bytes`에 규칙에 맞을 수 있는 룸 수를 곱해서 잡으세요(룸 수는 `max_rooms_total`로 묶입니다). 노드가 하나면 이력은 게이트웨이 메모리에, 클러스터면 Redis에 둡니다.

### offset과 epoch

이력이 있는 룸의 메시지에는 모두 `offset`이 붙습니다. 1부터 시작해 남긴 메시지마다 하나씩 늘어납니다. offset은 **epoch** 안에서만 의미가 있습니다. epoch는 그 룸 이력의 한 생애를 가리키는 불투명한 ID입니다. `sys.joined`가 현재 위치를 알려 줍니다.

```json
{"svc":"sys","type":"joined","room":"chat:1","epoch":"9f2c…","offset":44}
```

프레즌스 이벤트, Hot 프레임, JSON이 아닌 메시지에는 offset이 없고 이력에도 남지 않습니다.

### 이어 받기

이어 받으려면 마지막으로 본 위치를 담아 들어갑니다.

```json
{"v":1,"svc":"room","type":"join","room":"chat:1","seq":3,"data":{"recover":{"epoch":"9f2c…","offset":41}}}
{"v":1,"svc":"sys","type":"joined","room":"chat:1","reply_to":3,"epoch":"9f2c…","offset":44,"recovered":true}
```

- `"recovered": true`: 응답 뒤로 42~44번 메시지가 순서대로, 새 메시지보다 먼저 옵니다.
- `"recovered": false`: 빈 구간을 채울 수 없습니다. epoch가 바뀌었거나(게이트웨이 재시작, Redis 데이터 유실, 룸이 `ttl_s`보다 오래 비어 있었음), 메시지가 이미 `size`·`max_bytes`·`ttl_s` 때문에 지워졌습니다. 백엔드에서 룸 상태를 다시 불러오세요.

`recover` 없이 들어가면 `recovered` 필드 자체가 없습니다. 클라이언트는 이미 본 offset의 메시지를 버려야 합니다. JavaScript SDK는 이렇게 처리하며, 재접속할 때마다 알아서 이어 받습니다.

느린 소비자로 끊긴 클라이언트도 같은 방법으로 회복합니다. `slow_consumer`로 닫힌 클라이언트는 재접속해서 마지막 offset부터 이어 받고, 이때 되돌려 받는 양은 넘쳤던 큐의 크기와 상관없습니다.

### 공백

`sys.gap`은 룸의 메시지 흐름에 구멍이 났다는 뜻입니다.

```json
{"v":1,"svc":"sys","type":"gap","room":"lobby"}
{"v":1,"svc":"sys","type":"gap","room":"chat:1","epoch":"a71e…"}
```

`epoch`가 없으면 그 룸의 메시지가 일부 빠졌을 수 있다는 뜻입니다. 클러스터에서 노드가 잠깐 Redis 구독을 놓친 경우입니다. 룸 상태를 다시 불러오세요. `epoch`가 있으면 룸의 이력 자체가 새로 시작됐다는 뜻입니다(Redis가 비어 있는 상태로, 또는 오래된 스냅숏으로 돌아왔습니다). offset이 새 epoch에서 다시 시작하므로 그 룸에서 마지막으로 본 offset은 잊어야 합니다. 그러지 않으면 새로 온 작은 offset이 이미 받은 메시지처럼 보입니다. SDK는 두 경우를 모두 처리하고 `gap` 이벤트를 냅니다.

## 이력이 아닌 것

이력은 재접속의 틈을 메우는 장치이지 저장소가 아닙니다. 채팅 기록, 주문, 문서처럼 중요한 데이터의 원본은 자체 데이터베이스에 두고, `recovered: false`와 `sys.gap`을 거기서 다시 불러오라는 신호로 쓰세요. 게이트웨이가 영속적인 전달까지 보장하려면 선행 기록 로그와 복제가 필요합니다. 그건 데이터베이스의 일이고, 그렇게 하면 wsPrism이 애써 없애려는 지연을 모든 메시지가 떠안게 됩니다.
