# 자주 묻는 질문과 문제 해결

## 접속

**브라우저가 핸드셰이크에서 403을 받습니다.**
페이지의 Origin이 테넌트의 `policy.allowed_origins`에 없습니다. 이 목록은 기본값이 비어 있어서 모든 브라우저를 거절합니다. 정확한 Origin(`https://app.example.com`, 개발 중이라면 `http://localhost:3000`)을 넣으세요. 하위 도메인은 `https://*.example.com`으로 한 번에 허용할 수 있습니다.

**핸드셰이크가 401로 실패합니다.**
테넌트가 티켓을 찾는 위치 어디에도 자격 증명이 없었거나, 인증 사슬이 거절한 경우입니다. 클라이언트가 테넌트가 보는 위치에 티켓을 싣는지 확인하고(`ticket_sources`. 쿼리스트링은 기본적으로 꺼져 있습니다), 사슬에 그 종류의 티켓을 다루는 인증기가 있는지 확인하세요. 1회용 티켓은 실패한 시도라도 처음 제시되는 순간 소비되고, 기본 30초면 만료된다는 점도 기억하세요.

**핸드셰이크가 400으로 실패합니다.**
없는 테넌트이거나, `sid`가 `[A-Za-z0-9_-]` 1~64자가 아니거나, 서브프로토콜을 보냈는데 게이트웨이가 아는 버전(`wsprism.v2.json`, `wsprism.v1`)이 없는 경우입니다.

**접속할 때 503을 받습니다.**
`Retry-After` 헤더와 `wsprism_handshake_rejections_total`을 보세요. 흔한 원인은 이렇습니다. 노드가 드레인 중이거나(다른 노드로 접속하세요), 테넌트가 `max_sessions_total`에 닿았거나, 인증 백엔드나 JWKS 엔드포인트에 닿지 않거나, 클러스터에서 Redis가 느려 노드가 새 연결을 덜어 내고 있는 경우(`cluster_busy`)입니다.

**wsPrism이 TLS를 종단하나요?**
네. `gateway.tls`에 인증서와 키를 지정하면 됩니다. SIGHUP을 보내면 재시작 없이 다시 읽습니다([설정](../reference/configuration.md#gatewaytls)). 서버에서 직접 `wss://`를 제공할 때 가장 싼 방법이기도 합니다. 같은 서버에 nginx 같은 TLS 프록시를 두면 전달당 CPU가 두 배가 됐습니다([TLS](../project/benchmarks.md#tls)). 별도의 로드밸런서에서 TLS를 끝내도 되며, 그때는 로드밸런서를 `gateway.trusted_proxies`에 적어 속도 제한이 진짜 클라이언트 주소를 보게 하세요.

## 메시지

**요청에 `NOT_ALLOWED`가 돌아옵니다.**
`svc:type`이 테넌트의 `ext_allowlist`에 없거나, 사용자 권한이 그 룸을 포함하지 않거나, 세션이 보내려는 룸에 들어가 있지 않은 경우입니다. 어느 쪽인지는 `msg` 필드에 나옵니다.

**룸 메시지는 오가는데 직접 만든 서비스에 요청이 닿지 않습니다.**
서비스는 등록돼 있어야 하고(내장, `Gateway::builder`, 또는 `rpc.allow` 라우트) 동시에 허용 목록에도 있어야 합니다. 존재하지 않는 서비스를 허용 목록에 적으면 시작 단계에서 실패하므로, 게이트웨이가 떴다면 허용 목록을 보세요.

**클라이언트가 `slow_consumer`(4101)로 닫힙니다.**
신뢰 메시지가 클라이언트의 송신 큐에 들어가지 못했습니다. 클라이언트가 너무 느리게 읽거나(백그라운드 탭, 성능 낮은 기기, 혼잡한 회선), 클라이언트가 소화할 수 있는 것보다 많은 신뢰 트래픽을 발행하는 룸이 있는 경우입니다. 클라이언트는 재접속해서 이력 룸을 마지막 offset부터 이어 받습니다. 자주 일어난다면 빠르게 바뀌는 데이터를 Hot 레인으로 옮기세요. 그러면 느린 클라이언트는 밀린 메시지 대신 최신 값을 받습니다. `session_queue_capacity`는 순간적인 몰림이 짧을 때만 키우세요.

**Hot 레인처럼 느린 클라이언트에게는 옛 메시지를 그냥 버리면 안 되나요?**
Ext 레인은 순서대로 전달하거나, 그러지 못했다고 분명히 알린다고 약속하기 때문입니다. 아무도 모르게 사라진 채팅 메시지는, 재접속해서 되찾는 것보다 훨씬 나쁩니다.

**메시지가 발행한 순서대로 도착하나요?**
한 룸 안에서는 모든 멤버가 같은 순서로 봅니다. 룸 사이에는, 그리고 백엔드가 서로 다른 노드로 발행할 때의 노드 사이에는 전역 순서가 없습니다. [전달 의미](cluster.md#전달-의미)를 참고하세요.

**전달이 보장되나요?**
연결 단위로는 최대 한 번 전달하고, 그 위에 복구 장치를 얹었습니다. 이력 룸에서는 재접속한 클라이언트가 놓친 것을 받아 가고, 그럴 수 없으면 게이트웨이가 분명히 알립니다(`recovered: false`, `sys.gap`). 절대 잃으면 안 되는 데이터라면 원본을 데이터베이스에 두고, 이 신호를 다시 불러오라는 신호로 쓰세요.

## 클러스터

**한 노드에서 발행한 메시지가 다른 노드의 클라이언트에게 가지 않습니다.**
모든 노드가 `kind: redis`에 같은 `prefix`, 같은 Redis를 쓰는지 확인하세요. `wsprism_broker_failed_total`은 Redis가 거부한 명령 수입니다. 0이 아니라면 대개 ACL 권한이 빠진 것입니다.

**모든 이력 룸이 새 epoch가 담긴 `sys.gap`을 보낸 이유가 뭔가요?**
Redis가 재시작했거나, 장애 조치가 일어났거나, 게이트웨이의 키를 내쫓았기 때문입니다. 그 데이터가 클라이언트가 본 것보다 오래됐을 수 있으므로, 게이트웨이는 offset을 재사용할 위험을 지는 대신 새 epoch를 시작합니다. 내쫓기는 `maxmemory-policy noeviction`으로 막을 수 있습니다.

**노드가 오류를 남기고 스스로 종료했습니다.**
`slot_ttl_s`보다 오래 Redis와 끊겨 있는 사이 다른 노드가 그 슬롯을 차지한 경우입니다. 계속 돌았다면 클러스터가 이미 죽었다고 판정한 노드의 이름으로 발행하게 되므로, 드레인하고 멈췄습니다. 오케스트레이터가 다시 띄우면 새 슬롯을 차지합니다.

**Redis Cluster나 Valkey, 관리형 Redis를 쓸 수 있나요?**
Redis Cluster는 아직 지원하지 않습니다. Redis 프로토콜을 쓰고, ACL 목록의 명령과 Lua 스크립트, pub/sub를 지원하는 6.2 이상의 서버라면 동작할 것입니다. 시험은 Redis 7로 합니다.

## 연동

**Rust를 꼭 써야 하나요?**
아닙니다. 인증(티켓, JWT, connect 프록시), 발행, 강제 종료, 요청 처리(RPC 프록시)가 모두 HTTP로 되므로 어떤 언어든 됩니다. Rust는 게이트웨이 안에서 도는 서비스를 만들 때만 필요합니다.

**Socket.IO나 Pusher 호환 계층이 있나요?**
없습니다. 클라이언트는 wsPrism 프로토콜을 씁니다. 브라우저와 Node는 JavaScript SDK가 맡고, 다른 플랫폼은 [와이어 프로토콜](../reference/protocol.md)에 명세가 다 있으니 아무 WebSocket 라이브러리로 구현할 수 있습니다.

**재시작 없이 설정을 바꿀 수 있나요?**
아직은 안 됩니다. 노드를 재시작하고, 노드가 여럿이면 하나씩 재시작하세요. 테넌트 정책을 실행 중에 다시 읽는 기능은 계획에 있습니다.

**운영 환경에 써도 되나요?**
단일 노드 게이트웨이는 기능이 갖춰졌고, 퍼징을 거쳤고, Rust 테스트 약 270개와 SDK·카오스 시험으로 덮여 있습니다. 클러스터는 실제 서비스에서 돌기 전까지 실험적 기능입니다. 외부 보안 감사는 아직 받지 않았습니다. [보안](../project/security.md)을 읽고 판단하세요.
