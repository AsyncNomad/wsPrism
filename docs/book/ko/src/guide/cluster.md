# 클러스터 운영

wsPrism 노드 하나로도 아주 많은 연결을 감당하지만, 노드가 하나뿐이면 장애 한 번이 곧 서비스 중단입니다. Redis 브로커를 쓰면 여러 노드가 룸, 세션, 프레즌스, 이력을 함께 쓰고, 클라이언트는 어느 노드에 붙어도 됩니다.

> **상태:** 클러스터는 기능을 모두 갖췄고 아래의 장애 시험도 통과하지만, 실제 서비스에서 검증되기 전까지는 **실험적** 기능입니다. 0.x 릴리스에서 설정이 바뀔 수 있습니다.

## 무엇을 배포하나

- **게이트웨이 노드**: 아무 로드밸런서 뒤에나 둡니다. 스티키 세션은 필요 없습니다. 로드밸런서 대신 클라이언트에 노드 목록을 줘도 됩니다(SDK의 `url: [...]`). 재접속할 때마다 다음 노드로 갑니다.
- **Redis 6.2 이상 하나**: 주소 하나로 쓰거나, Redis Sentinel이 관리하는 프라이머리로 씁니다. Redis Cluster는 아직 지원하지 않습니다. 키에 이미 해시 태그를 쓰고 있어서, 나중에 지원하더라도 키 이름은 바뀌지 않습니다.
- **상태 확인**: 생존 확인은 `/healthz`, 준비 확인은 `/readyz`입니다. 클러스터에서 자리를 잃은 노드는 준비되지 않은 상태가 되며, 재시작해야 합니다.

설정은 이렇습니다.

```yaml
gateway:
  broker:
    kind: redis
    url_env: WSPRISM_REDIS_URL     # 예: rediss://wsprism:secret@redis.internal:6380/0
    prefix: wsp
```

나머지 조정 항목은 적당한 기본값이 있으며 [설정](../reference/configuration.md#클러스터-브로커)에 모두 나와 있습니다. 저장소의 `deploy/compose/`는 Docker Compose로 노드 두 개와 Redis를 띄웁니다. 설정 파일은 하나이고, 노드 사이의 차이는 환경 변수로만 둡니다.

### Redis 준비

- `maxmemory-policy noeviction`(또는 `volatile-*` 정책)을 쓰세요. Redis가 게이트웨이의 키를 내쫓으면 이력 룸이 새 epoch로 다시 시작하고 클라이언트는 상태를 다시 맞춰야 합니다.
- 영속화는 선택입니다. 켜 두어도 Redis 재시작을 넘어 이력이 이어지지는 않습니다(아래 [Redis가 재시작되면](#redis가-재시작되면) 참고).
- 최소 권한 사용자를 만드세요. 테스트에서 검증한 명령 목록은 다음과 같습니다.

  ```
  ACL SETUSER wsprism on >PASSWORD ~wsp:* &wsp:* -@all +publish +subscribe +unsubscribe +set +get +getdel +del +pexpire +time +zadd +zcard +zrange +zrangebyscore +zremrangebyrank +zpopmin +hget +hmget +hgetall +hset +hincrby +hdel +hexists +sadd +srem +smembers +info +eval +evalsha +script|load +client|setinfo
  ```

  `wsp`는 실제 접두사로 바꾸세요. `client|setinfo`는 없어도 됩니다.

- 완전히 통제하지 못하는 네트워크라면 TLS(`rediss://`)를 쓰세요. 사설 CA와 클라이언트 인증서는 `gateway.broker.tls`에서 설정합니다.

### Sentinel

Sentinel이 프라이머리를 넘길 때 따라가려면 Sentinel 주소를 적습니다.

```yaml
gateway:
  broker:
    kind: redis
    url_env: REDIS_URL       # 자격 증명과 DB 번호만 씁니다. 호스트는 Sentinel이 알려 줍니다
    sentinel:
      addresses: ["redis://sentinel-1:26379", "redis://sentinel-2:26379", "redis://sentinel-3:26379"]
      master_name: mymaster
```

노드는 1초마다 Sentinel에 프라이머리를 묻고, 바뀌면 모든 연결을 새 프라이머리로 옮깁니다. 시험에서는 프라이머리를 멈추고 약 4.5초 뒤에 전달이 재개됐고, 모든 구간에 상호 TLS를 건 경우에는 2.3~3.2초 뒤였습니다. Sentinel 주소를 `rediss://`로 쓰면 Sentinel과도 TLS로 연결하고, `tls` 섹션은 Sentinel과 Redis 노드 양쪽에 똑같이 적용됩니다.

Sentinel을 쓰면 1회용 티켓을 소비할 때 적어도 레플리카 하나가 그 쓰기를 받을 때까지 기다립니다(`replica_ack`. Sentinel을 쓰면 기본으로 켜집니다). 장애 조치가 되돌릴 수 있는데 아무것도 그걸 복구하지 못하는 쓰기는 이것 하나뿐입니다. 소비 기록을 놓친 레플리카가 승격되면 같은 티켓을 한 번 더 받아 주게 됩니다. 제한 시간 안에 확인해 주는 레플리카가 없으면 그 로그인은 503으로 실패합니다. 장애 조치 중에도 티켓 로그인을 유지하려면 레플리카를 둘 두세요.

## 노드가 협력하는 방식

- **시작.** 노드는 누구를 받기 전에 Redis에서 1,024개 *노드 슬롯* 가운데 하나를 차지하고, 하트비트로 갱신합니다. 멤버 ID에 슬롯이 들어가므로 클러스터 전체에서 겹치지 않습니다. Redis에 닿지 못하는 노드는 시작하지 않으며, 오케스트레이터가 다시 띄웁니다.
- **룸 트래픽.** Ext 메시지는 Redis를 거치므로 모든 노드가 한 룸의 메시지를 같은 순서로 전달합니다. Hot 상태는 로컬 멤버에게 바로 전달하고 다른 노드에도 보냅니다.
- **세션**은 클러스터 전체에서 하나로 관리합니다. 같은 `sid`로 재접속하면 이전 연결이 어느 노드에 있든 대체하고, `max_sessions_per_user`도 노드 전체에서 정확히 지켜집니다. Redis 스크립트가 판정하므로 동시에 들어온 두 연결이 둘 다 이기는 일이 없습니다.
- **프레즌스**도 클러스터 전체 기준입니다. 프레즌스 조회와 `sys.joined`의 목록에 모든 노드의 멤버가 나옵니다.
- **이력**은 Redis에 있습니다. Lua 스크립트가 메시지를 저장하고 발행하는 그 자리에서 offset을 매기므로, 모든 노드가 같은 offset을 보고 클라이언트는 어느 노드에서든 이어 받을 수 있습니다.
- **자가 복구.** 노드마다 15초마다 자기 상태를 Redis와 대조해서, Redis가 잃어버린 세션과 멤버십을 다시 써 넣습니다.

## 이럴 때는 이렇게 됩니다

아래 표의 모든 행은 카오스 시험이나 무작위 soak 시험에서 실제로 일으켜 확인했습니다.

| 상황 | 클라이언트가 겪는 일 | 회복 |
|---|---|---|
| 노드가 강제 종료됨 | 그 노드의 클라이언트가 다른 노드로 재접속해 이력 룸을 마지막 offset부터 이어 받습니다. 잃는 것도, 두 번 받는 것도 없습니다 | `slot_ttl_s`에 약 5초를 더한 시간 안에 다른 노드들이 그 노드의 멤버를 지우고 `member_left`를 한 번 보냅니다 |
| 노드가 정상 종료됨(SIGTERM) | `/readyz`가 503이 되고, 세션은 4103 `draining`으로 닫혀 다른 노드에서 이어집니다. 잃거나 반복되는 것이 없습니다 | `drain_grace_ms` 안에 큐를 Redis에 넘기고 종료합니다 |
| Redis가 빈 상태로, 또는 오래된 스냅숏으로 재시작됨 | 이력 룸은 새 epoch로 시작하고(epoch가 담긴 `sys.gap`), 나머지 룸은 `sys.gap`을 받습니다. 연결이 끊기는 사람은 없습니다 | 노드들이 다시 연결하고, 다시 구독하고, 스크립트를 다시 올리고, 약 15초 안에 세션을 되살립니다 |
| Sentinel 장애 조치 | Redis 재시작과 같습니다 | 노드가 약 1초 안에 따라갑니다 |
| Redis가 느림 | 발행이 기다리다가 `outbox_max_wait_ms`(1초)를 넘으면 새 발행은 `UNAVAILABLE`을 받습니다. `admission.max_latency_ms`(500 ms)를 넘으면 새 연결은 503 `cluster_busy`와 1~5초의 `Retry-After`를 받고, 이미 붙은 세션은 그대로입니다 | Redis가 회복되면 250 ms 주기 점검 한 번 안에 저절로 풀립니다 |
| Redis가 내려감 | 새 연결은 4102 `unavailable`로 닫히고, 신뢰 발행은 `UNAVAILABLE`, 티켓 로그인은 503을 받습니다. 같은 노드의 멤버끼리는 Hot 상태가 계속 흐릅니다 | Redis가 돌아오면 저절로 풀립니다 |
| 노드가 `slot_ttl_s`보다 오래 Redis와 끊김 | 다른 노드에서는 한동안 그 노드의 룸이 빈 것처럼 보입니다 | 다시 연결되면 재등록하고 세션을 되살립니다. 그사이 다른 노드가 슬롯을 차지했다면 드레인 후 오류로 종료하고, 오케스트레이터가 다시 띄웁니다 |
| 노드 사이의 종료 명령이 유실됨 | 대체된 세션이 잠시 남아 있을 수 있습니다 | 자가 복구가 약 15초 안에 닫습니다 |

### Redis가 재시작되면

재시작한 Redis나 승격된 레플리카는 다른 프로세스이고, 그 데이터는 클라이언트가 이미 본 것보다 오래됐을 수 있습니다. 그대로 두면 같은 offset에 다른 내용이 실릴 수 있습니다. 게이트웨이는 Redis의 `run_id`로 이 변화를 알아채고, 모든 이력 룸을 새 epoch로 시작하면서 `sys.gap`으로 클라이언트에 알립니다. 클라이언트는 재사용된 offset을 모르고 받는 대신 상태를 다시 맞춥니다. 스냅숏은 정의상 마지막 쓰기보다 오래됐으므로 영속화를 켜도 달라지지 않습니다.

### 펜싱

다른 노드가 슬롯을 가져갈 만큼 오래 끊겼던 노드가 아무 일 없었다는 듯 계속 발행해서는 안 됩니다. 이건 Redis가 막아 줍니다. 룸 발행은 발행하는 스크립트 안에서 슬롯 소유를 함께 확인하므로, 슬롯이 없는 노드의 발행은 모두 거절됩니다. 그 노드는 처음 거절당한 쓰기나 다음 하트비트 가운데 먼저 오는 쪽에서 드레인하고 종료합니다. 세션과 멤버십 쓰기에는 펜싱이 걸리지 않으며, 그 노드가 사라진 뒤 다른 노드들이 정리합니다.

## 롤링 업데이트

노드를 하나씩 재시작합니다.

1. SIGTERM을 보냅니다. 쿠버네티스는 파드를 지울 때 보냅니다. 노드는 준비 상태를 내리고, 새 연결과 서버 API 발행을 503으로 거절하고, 세션을 4103으로 닫고, 큐를 Redis에 넘깁니다. 이 모두를 `drain_grace_ms`(기본 2초) 안에 합니다.
2. 새 버전을 띄우고 `/readyz`가 200을 줄 때까지 기다립니다.
3. 다음 노드로 넘어갑니다.

쿠버네티스라면 `terminationGracePeriodSeconds`를 `drain_grace_ms`보다 길게, 준비 프로브는 `/readyz`로, `maxUnavailable: 1`로 두세요. 카오스 시험이 정확히 이 순서를 밟으며 잃거나 반복되는 것이 없는지 확인합니다.

## 전달 의미

- **한 룸 안에서는 모두에게 같은 순서.** 모든 노드가 한 룸의 Ext 메시지를 같은 순서로 전달합니다.
- **룸 사이에는 전역 순서가 없습니다.** 서로 다른 룸으로 가는 메시지는 발행된 순서와 다르게 노드를 떠날 수 있습니다.
- **노드 사이에서는 Redis 도착 순서.** 백엔드가 메시지 A를 노드 1에, B를 노드 2에 보내면 멤버는 Redis가 받은 순서대로 받습니다. 한 룸의 메시지 순서가 중요하다면 한 노드를 통해 발행하세요.
- **서버 API의 200은 "그 노드의 큐에 들어갔다"는 뜻입니다.** 큐를 비우기 전에(보통 마이크로초 단위입니다) 강제 종료된 노드는 큐에 있던 것을 잃습니다. SIGTERM으로 멈춘 노드는 먼저 넘기고 끝냅니다.
- **게이트웨이 자신의 재시도로는 이력 메시지가 중복되지 않습니다.** 프레임마다 노드별 일련번호가 붙고 Redis 스크립트가 그것을 확인합니다. 이력이 없는 룸의 메시지는, Redis가 발행을 실행한 뒤 답하기 전에 연결이 끊긴 경우에만 중복될 수 있습니다.
- **백엔드의 재시도는 중복을 만들 수 있습니다.** 발행이 시간 초과돼 다른 노드로 다시 보냈는데, 첫 노드도 사실은 받아 둔 경우입니다. 중요하다면 메시지에 ID를 넣으세요.

## 용량

지금의 클러스터는 **고가용성에 제한적인 확장**을 줍니다. 노드를 늘리면 연결과 Hot 트래픽을 더 받지만, 룸 이력은 Redis 코어 하나가 천장입니다.

| 트래픽 | 확인한 한계 |
|---|---|
| Hot 상태 | 단일 노드와 같음(로컬에 먼저 전달) |
| 이력 없는 Ext | 노드당 초당 약 24만 발행을 모두 전달. Redis는 발행 하나에 약 2.5 µs를 써서 코어 하나로 클러스터 전체 초당 약 60만 |
| 이력 있는 Ext | 약 200바이트 메시지 기준 Redis 코어당 초당 약 15만 |
| 접속 폭주 | 노드당 초당 약 3만 세션. Redis 코어 하나는 최악의 경우(접속, 입장, 퇴장, 종료)를 초당 약 6만 처리 |

`gateway.session_queue_capacity`는 기본값(1024) 이상으로 두세요. Redis에서 오는 프레임이 묶음으로 들어오기 때문에, 큐가 작으면 멀쩡한 클라이언트까지 느린 소비자로 닫힙니다.

## 알려진 한계

- 테넌트 전체 한도(`max_sessions_total`과 룸 한도)는 노드마다 따로 셉니다.
- Redis 프라이머리는 하나입니다. 룸 트래픽을 여러 Redis에 나누는 설계는 마쳤지만 아직 구현하지 않았습니다.
- Redis가 빈 상태로 재시작된 뒤, 이전 노드가 세션을 되살리기 전(약 15초)에 같은 `sid`로 다른 노드에 재접속한 사용자는 잠깐 그 sid로 세션 두 개를 가질 수 있습니다.
