# 핵심 개념

이 문서 전체에서 쓰는 용어를 정리합니다. 하나하나는 짧지만, 모아 놓으면 게이트웨이가 하는 일 거의 전부를 설명합니다.

## 테넌트

테넌트는 게이트웨이를 쓰는 서로 격리된 고객입니다. 앱 하나, 게임 하나, 팀 하나일 수도 있고 내 SaaS 제품의 고객사 하나일 수도 있습니다. 배포 하나에 테넌트를 여럿 둘 수 있으며, 테넌트마다 다음을 따로 가집니다.

- **인증 사슬**: 누가 접속할 수 있는가
- **정책**: 허용하는 메시지, 속도 제한, 세션 규칙, 브라우저 Origin
- **한도**: 프레임 크기, 세션 수, 룸 수, 룸당 인원
- 서버 API용 **API 키**, 그리고 필요하면 백엔드로 가는 **RPC 라우트**와 **이력 규칙**

룸 이름, 사용자 ID, 세션 ID는 언제나 테넌트 안에서만 통합니다. 두 테넌트에 똑같이 `lobby` 룸과 `alice` 사용자가 있어도 서로 만날 일이 없습니다.

클라이언트는 접속 URL에서 테넌트를 고릅니다(`/v1/ws?tenant=acme`). 없는 테넌트면 WebSocket 업그레이드 전에 거절합니다.

## 세션

세션은 인증을 통과한 연결 하나입니다. 다음을 지닙니다.

- **사용자 ID**: 인증기가 정하며, `[A-Za-z0-9_-]` 1~64자입니다.
- **세션 ID**(`sid`): 클라이언트가 `?sid=`로 직접 정할 수 있습니다. 같은 `sid`로 다시 접속하면 두 번째 연결로 치지 않고 이전 연결을 대체합니다.
- 자격 증명에 딸려 온 **권한**: 들어갈 수 있는 룸과 발행할 수 있는 룸
- 크기가 정해진 **송신 큐**

한 사용자가 동시에 몇 개의 세션을 가질 수 있는지, 그 수를 넘는 새 세션이 오면 거절할지 가장 오래된 세션을 닫을지는 테넌트의 세션 정책이 정합니다. 클러스터에서는 이 규칙이 노드 전체에 걸쳐 지켜집니다.

## 룸

룸은 이름이 붙은 세션 묶음입니다. 룸에 들어가면 거기서 발행되는 모든 메시지를 받고, 나오면 더는 받지 않습니다. 룸은 멤버가 있는 동안 존재하며 미리 선언할 필요가 없습니다.

룸 이름은 제어 문자가 없는 UTF-8 1~128바이트입니다. 설정에서 쓰는 패턴(`chat:*`)은 접두사로 맞추므로, `match:42`나 `doc:7f3a` 같은 이름 규칙을 쓰면 편합니다.

룸은 최근 메시지를 **이력**으로 남길 수 있어서, 재접속한 클라이언트가 놓친 것을 받아 갈 수 있습니다. [룸, 프레즌스, 이력](rooms-and-history.md)에서 자세히 다룹니다.

## 두 레인

연결 하나에 두 종류의 트래픽이 오갑니다.

| | Ext 레인 | Hot 레인 |
|---|---|---|
| WebSocket 프레임 | 텍스트(JSON) | 바이너리 |
| 주소 | `svc`·`type` 이름 | 숫자 서비스 ID와 opcode |
| 전달 | 신뢰 전달, 룸 안에서 순서 보장 | 손실 허용: 밀린 수신자는 최신 값을 받음 |
| 주 용도 | 채팅, 명령, 룸 관리, RPC | 위치, 커서, 센서 값, 시세 |
| 이력 보관 | 룸에 이력 규칙이 있으면 보관 | 보관하지 않음 |

요청과 응답은 Ext 레인에서 오갑니다. 요청에 `seq`를 붙이면 그 요청에 대한 응답에는 모두 같은 번호가 `reply_to`로 붙어 돌아옵니다.

Hot 레인은 상태를 나릅니다. Hot 프레임에는 **키**를 붙일 수 있고, 게이트웨이는 수신자마다 송신자·키별로 가장 새 프레임만 남깁니다. 그래서 잠깐 멈췄던 클라이언트는 지난 위치를 하나하나 다시 받는 대신 곧바로 현재 상태를 따라잡습니다.

## 서비스

메시지는 서비스가 처리합니다. Ext 레인의 서비스는 이름(`room`, `chat`, 또는 직접 만든 것)으로, Hot 레인의 서비스는 숫자 ID(`1`은 내장 룸 릴레이)로 구분합니다.

룸과 채팅은 내장 서비스가 맡습니다. 내 서비스를 붙이는 방법은 손이 덜 가는 순서로 세 가지입니다.

1. `svc:type` 패턴을 HTTP로 백엔드에 넘깁니다(**RPC 프록시**). 언어는 상관없습니다.
2. Rust 서비스를 `Gateway::builder`로 등록합니다.
3. (계획) WebAssembly 플러그인

어느 방법이든 테넌트 허용 목록에 그 메시지가 있어야 합니다. 서비스를 등록하면 처리할 수 있게 되고, 허용 목록에 넣어야 실제로 허락됩니다.

## 서버 API

백엔드가 게이트웨이에 말을 거는 통로입니다. 티켓 발급, 룸 발행, 사용자 강제 종료, 룸 인원 조회를 합니다. 내부용 주소에서 따로 열리고, 테넌트별 API 키로 인증합니다. [서버 API](../reference/server-api.md)를 참고하세요.

## 브로커

브로커는 세션 사이의 룸 트래픽을 나릅니다. 노드가 하나면 프로세스 메모리 안에서 처리하고, 여럿이면 Redis를 씁니다. Redis를 쓰면 어느 노드에서 발행한 메시지든 모든 노드의 룸 멤버에게 가고, 세션과 프레즌스를 함께 쓰며, 이력은 Redis에 둡니다. 어느 쪽이든 클라이언트와 백엔드가 보는 프로토콜은 같습니다.

## 전달 등급

나가는 메시지는 내부적으로 모두 **Reliable** 아니면 **Lossy**입니다.

- Reliable 메시지가 수신자의 큐에 들어가지 못하면, 그 수신자를 *느린 소비자*로 보고 연결을 닫습니다(종료 코드 4101). 클라이언트는 재접속하고, 이력이 있는 룸이면 끊긴 지점부터 이어 받습니다. 조용히 버렸다면 Ext 메시지는 순서대로 도착한다는 약속이 깨졌을 것입니다.
- Lossy 메시지가 들어가지 못하면 그 수신자에게만 버리고 `wsprism_egress_drop_total`에 셉니다.

과부하에서 게이트웨이가 어떻게 움직일지 예측할 수 있는 건 이 규칙 덕분입니다. 느린 클라이언트 하나가 룸 전체를 늦추지 않고, 신뢰 데이터를 모르는 사이에 놓치지도 않습니다.
