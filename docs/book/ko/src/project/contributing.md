# 기여하기

버그 제보, 문서 수정, 시험, 코드 모두 환영합니다. 내 변경이 프로젝트에 자연스럽게 들어맞도록, 이 프로젝트가 일하는 방식을 소개합니다.

## 시작하기 전에

작은 수정이 아니라면 먼저 이슈를 열어 풀고 싶은 문제를 설명해 주세요. 설계 문제 가운데 상당수는 이미 [설계 결정](../architecture/decisions.md)에서 다뤘고, 짧게 이야기를 나누면 다시 짜는 수고를 덜 수 있습니다.

보안 문제는 이슈 트래커가 아니라 [보안](security.md)에 적힌 비공개 경로로 알려 주세요.

## 빌드와 시험

```bash
cargo build --workspace
cargo test --workspace --locked
```

통합 시험은 실제 게이트웨이를 띄웁니다. 클러스터 시험에는 로컬 Redis가 필요합니다.

```bash
docker run -d --name wsp-redis -p 6379:6379 redis:7.2 redis-server --save "" --appendonly no
```

SDK와 예제 앱에는 따로 종단 간 시험이 있습니다.

```bash
sdk/js/run-tests.sh
examples/chat-and-state/run-tests.sh
```

CI는 이 모두에 더해 포맷, 경고를 오류로 취급하는 Clippy, 최소 지원 Rust 버전으로의 빌드, 의존성 감사, 카오스 시험, 짧은 퍼징을 돌립니다. 풀 리퀘스트를 열기 전에 적어도 다음은 돌려 주세요.

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

## 변경을 만드는 방식

- **수정은 실패하는 시험부터.** 결함을 재현하는 시험을 쓰고, 실패하는지 확인한 뒤 고칩니다. 고친 부분을 한 번 빼 보고 시험이 결함을 잡는지도 확인합니다.
- **커밋 하나에 변경 하나.** 리팩터링과 동작 변경을 섞지 않습니다. 커밋 메시지에는 관례적 접두사(`feat:`, `fix:`, `docs:`, `perf:`, `test:`, `refactor:`)를 씁니다.
- **기능보다 경계가 먼저.** 새 기능은 트레이트, 레지스트리, 설정 섹션 뒤에 둡니다. 코어 경로에 특별 처리(`if svc == "x"`)를 넣으려면 아주 좋은 이유와, 나중에 어떻게 걷어 낼지에 대한 메모가 필요합니다.
- **성능 변경은 잽니다.** 빨라진다고 주장하는 변경에는 벤치마크 시나리오로 잰 전후 수치를 붙입니다. 값어치를 못 하는 변경은 되돌리되, 결과는 그래도 기록합니다.
- **결정은 글로 남깁니다.** 클라이언트에 보이는 변경은 프로토콜 문서에, 설계 결정과 버린 대안은 ADR에, 결함 수정은 견고화 기록에 남깁니다.
- **계약은 늘어나기만 합니다.** 와이어 프로토콜, 서버 API, 설정 형식의 변경은 덧붙이는 방식이어야 합니다. 새 설정 필드에는 언제나 기본값이 있어야 합니다.

## 가끔 실패하는 시험

가끔 실패하는 시험은 결함으로 봅니다. 시험의 결함일 수도, 제품의 결함일 수도 있습니다. 통합 시험은 여러 번 돌려 안정적인지 확인하고, 흔들리는 시험은 재시도로 덮지 않고 원인을 찾습니다.
