# 벤치마크

이 문서의 성능 이야기는 모두 저장소에 남긴 측정에서 나옵니다. 시나리오, 도구, 원자료(`bench/results/*.jsonl`), 그리고 측정마다의 해설이 [`docs/BENCHMARKS.md`](https://github.com/AsyncNomad/wsPrism/blob/main/docs/BENCHMARKS.md)에 있습니다. 이 장은 그 요약이며, 한계도 분명히 적습니다.

## 측정 방법

- **부하 생성기:** `wsprism-loadgen`이 실제 WebSocket 연결을 열고, 룸에 들어가고, 일부 연결이 보낸 시각을 찍은 탐침 메시지를 발행합니다. 받는 쪽은 지연을 HDR 히스토그램에 기록합니다. 보내는 쪽과 받는 쪽이 한 프로세스라 시계를 맞출 필요가 없습니다. 전달률(받은 탐침 ÷ 보낸 탐침 × 룸 인원)을 보면 유실이 드러납니다.
- **격리:** 게이트웨이는 코어 8개에, 부하 생성기는 다른 코어에 고정합니다. 네트워크 네임스페이스(`bench/netlab.sh`)로 지연과 손실을 넣을 수 있습니다.
- **비용:** 서버에서 잰 전달 하나당 CPU 시간과 연결 하나당 프로세스 메모리(RSS)입니다.
- **반복:** 설정마다 세 번 돌리고, 평균 내지 않고 각각 적어서 흔들림이 보이게 했습니다.
- **비교 대상:** Centrifugo 6.9.7과 Sockudo는 기본 설정에 시나리오에 꼭 필요한 것(익명 접속, 비교할 때의 이력)만 더했습니다. 설정 파일은 `bench/competitors/`에 있습니다.

**한계.** 모두 한 대의 장비(Intel i7-13700K, WSL2)에서 쟀고, 부하 생성기도 같은 장비를 썼습니다. 전용 서버에서의 절대값은 다를 것입니다. 비교 대상은 튜닝하지 않았습니다. 메모리는 프로세스 RSS이고 커널 소켓 버퍼는 빠져 있는데, 소켓 버퍼는 어느 서버든 비슷하게 듭니다. 배수는 경향으로 보시고 판정으로 받아들이지는 마세요.

## 단일 노드: 다른 게이트웨이와 비교

64바이트 메시지, 연결마다 다른 사용자, 서버 코어 8개입니다. "룸" 시나리오는 수십 명짜리 룸 여럿이고, "방송"은 큰 룸 몇 개입니다. 처리량은 다른 멤버에게 전달한 건수(초당)입니다.

| 시나리오 | 서버 | p50 / p99 (ms) | 전달당 CPU µs | 연결당 KB |
|---|---|---|---|---|
| 룸, 18만/s | wsPrism | 0.32 / 0.7 | 5.02 | 19.7 |
| | Centrifugo | 0.39 / 0.8~1.5 | 7.27 | 78.6 |
| | Sockudo | 0.41 / 0.8~0.9 | 8.64 | 255.8 |
| 룸, 108만/s | wsPrism | 0.87 / 2.0~3.3 | 4.30 | 21.8 |
| | Centrifugo | 1.31 / 7.6~9.7 | 5.68 | 83.7 |
| | Sockudo | 포화(전달률 0.87~1.0, p99 최대 7.4초) | 8.96 | 333.2 |
| 룸, 216만/s | wsPrism | 2.10 / 6.6~8.5 | 3.49 | 28.1 |
| | Centrifugo | 11.41 / 126~148 | 3.23 | 89.5 |
| 방송, 50만/s | wsPrism | 1.76 / 4.5~7.0 | 7.47 | 18.4 |
| | Centrifugo | 2.60 / 8.2~10.8 | 9.82 | 31.5 |
| | Sockudo | 2.76 / 8.3~9.4 | 9.46 | 198.0 |

읽는 법:

- **메모리** 차이가 가장 큽니다. 룸 부하에서 연결당 Centrifugo의 1/4~1/3, 방송에서 약 60%이고, Sockudo와 비교하면 1/10 이하입니다.
- **CPU:** 저·중부하에서 Centrifugo는 전달당 1.3~1.45배, Sockudo는 1.3~1.9배를 씁니다. 초당 216만 건에서는 Centrifugo가 CPU를 약 7% 덜 쓰지만, p99는 약 18배 높습니다. 꼬리 지연을 내주고 더 크게 묶어 보내는 것으로 보입니다.
- **꼬리 지연**은 시험한 가장 높은 부하까지 한 자릿수 밀리초에 머뭅니다.

### 모든 룸에 이력을 켰을 때

두 서버 모두 룸마다 메시지 200개를 10분간 보관합니다.

| 시나리오 | 서버 | 전달률 | p99 (ms) | CPU µs | 연결당 KB |
|---|---|---|---|---|---|
| 룸, 18만/s | wsPrism | 1.000 | 0.7~1.0 | 5.07~6.93 | 29.9 |
| | Centrifugo | 1.000 | 0.8~1.2 | 7.76~10.01 | 96.5 |
| 룸, 108만/s | wsPrism | 1.000 | 2.3~4.5 | 4.34~4.72 | 32.2 |
| | Centrifugo | 1.000 | 8.7~12.2 | 5.31~6.15 | 104.6 |
| 룸, 216만/s | wsPrism | 1.000 | 6.4~9.4 | 3.21~3.36 | 37.7 |
| | Centrifugo | 0.937~1.000 | 1,846~3,934 | 3.32~3.80 | 97.4 |

이 측정은 연결당 약 4 KB를 더 쓰던 회귀(지금은 수정됨)가 들어간 빌드로 했습니다. 그러니 이 표의 wsPrism 메모리 값은 그만큼 크게 나와 있습니다.

이력을 켜면 wsPrism의 CPU는 1~3%, 연결당 메모리는 4~10 KB 늘어납니다. 가장 높은 부하에서 이력을 켠 Centrifugo는 포화되지만(p50 최대 1초), wsPrism의 지연은 이력이 없을 때와 같습니다.

## 클러스터: Centrifugo Redis 엔진과 비교

두 제품 모두 코어 하나짜리 같은 Redis를 쓰고, 노드 하나 또는 같은 코어 8개를 나눈 노드 둘로 돌렸습니다.

**이력 켬**(Redis가 천장):

| 발행/s | 서버 | 전달률 | p50 | p99 |
|---|---|---|---|---|
| 12만 | wsPrism 노드 1 | 1.000 | 8.1~8.9 ms | 15~24 ms |
| | wsPrism 노드 2 | 1.000 | 13~17 ms | 25~64 ms |
| | Centrifugo 노드 1 | 0.79~0.83 | 2.7~3.0초 | 5.6~6.3초 |
| 24만 | wsPrism 노드 1 | 0.58~0.60 | 118~123 ms | 178~194 ms |
| | Centrifugo 노드 1 | 0.34~0.35 | 6.4~7.0초 | 14.7~14.9초 |

같은 Redis에서 wsPrism은 Centrifugo의 약 1.5~1.7배 이력 처리량을 냅니다(포화 시 초당 약 14만 대 8만 5천). 노드를 늘려도 두 제품 모두 이력 처리량은 늘지 않습니다. 둘 다 Redis 코어 하나에 묶여 있기 때문입니다. Centrifugo는 Redis Cluster와 샤딩을 지원해 이 천장을 넘을 수 있지만, wsPrism은 아직 그렇지 못합니다.

**이력 없음**, 용량 안에서는 둘 다 모두 전달합니다. wsPrism은 연결당 메모리가 3.5~4.5배 적고, 작은 룸과 방송 시나리오에서 CPU가 1.25~1.3배 적으며, 108만/s 시나리오에서는 비슷합니다. p99는 같거나 낮습니다.

노드 용량을 넘어서면 두 제품은 설계부터 다르게 움직입니다. Centrifugo는 쌓아 두었다가 늦게라도 보냅니다(94~97% 전달, p50 약 1초). wsPrism은 1초 넘게 기다린 발행을 거절하고(89~90% 전달, p50 12~80 ms) 발행자에게 알려 다시 시도하게 합니다. 어느 쪽이 나은지는 애플리케이션에 달렸습니다.

## 접속 폭주

작업자마다 접속, 인증, 룸 입장, 종료를 계속 반복하고, 세션마다 사용자가 다릅니다. 클러스터 노드 하나 기준입니다.

| 경우 | 초당 세션 | 입장 p50 / p99 |
|---|---|---|
| 새 룸, 세션당 입장 1번 | 28,600~33,900 | 1~5 ms / 3~10 ms |
| 새 룸, 세션당 입장 5번 | 11,700~12,300 | 1 ms / 2 ms |
| 이미 구독한 룸 | 37,500~37,900 | 2 ms / 7 ms |

구독을 묶어 보내도록 바꾼 뒤 첫 번째 경우가 초당 약 3,700에서 약 3만 세션으로 늘었습니다. 지금은 노드 CPU가 한계입니다. Redis 코어 하나는 이런 세션을 초당 약 6만 처리합니다. 실제 연결은 머물러 있으므로 이 값은 최악의 경우입니다.

## 테넌트 격리

한 테넌트가 초당 최대 180만 건을 몰아치는 동안 다른 테넌트는 가벼운 부하를 돌렸습니다.

- **굶주림은 없습니다.** 가벼운 테넌트는 모든 회차에서 메시지를 하나도 잃지 않았습니다.
- **완전한 격리도 없습니다.** 지연은 전체 부하를 따라갑니다. 단일 노드에서 p99가 0.5 ms에서 2.5~3.1 ms로 올랐습니다. 테넌트별 아웃박스(0.2) 덕에 Redis로 가는 길에서 한 테넌트의 묶음이 다른 테넌트 앞에 줄 서지는 않지만, CPU는 나눠 씁니다.

지금은 테넌트별 속도 제한으로 한 테넌트의 몫을 묶는 것이 방법입니다.

## datagram 위의 상태 동기화

단방향 지연 20 ms인 회선을 흉내 내고, 10명 룸에서 60 Hz 상태를 WebTransport datagram과 TLS 위 WebSocket으로 각각 보내 비교한 실험입니다.

| 손실 | 전송 | 초과 AoI p99 | 눈에 띄는 끊김 | WSS 대비 CPU / 메모리 |
|---|---|---|---|---|
| 균등 1% | WSS | 49.7 ms | 프레임의 2.3% | — |
| | WebTransport | 15.8 ms | 0.001% | 약 2배 / 약 2.3배 |
| 버스트 1% | WSS | 49.7 ms | 2.6% | — |
| | WebTransport | 15.8 ms | 0% | 약 2배 / 약 2.3배 |

datagram은 끊김을 거의 없애고 초과 AoI를 1/3~1/4로 줄이지만, 라이브러리 기본 설정으로는 연결당 CPU와 메모리가 약 두 배 듭니다. 그래서 결론은 혼합입니다. 작은 인터랙티브 룸에는 datagram을, 큰 방송형 룸에는 WebSocket을 쓰고 룸마다 고릅니다. 0.1.0에는 WebTransport가 들어가지 않습니다.

## 다시 재 보기

```bash
cargo bench -p wsprism-protocol --bench protocol      # 마이크로벤치마크
cargo bench -p wsprism-gateway --bench hotpath
bench/run-baseline.sh <label>                         # 표준 종단 간 시나리오
bench/run-compete.sh                                  # 다른 게이트웨이와 비교
bench/run-cluster.sh                                  # 클러스터
bench/run-churn.sh                                    # 접속 폭주
bench/run-fairness.sh                                 # 테넌트 격리
bench/run-v.sh v-judgment 3                           # datagram 대 WebSocket
```

스크립트는 비교 대상의 바이너리가 로컬에 있다고 가정하며, 모든 트래픽을 한 장비의 네트워크 네임스페이스 안에서만 돌립니다.
