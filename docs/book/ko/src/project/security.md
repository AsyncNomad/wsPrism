# 보안

wsPrism은 사용자를 맞이하는 자리에 있습니다. 연결을 인증하고, 테넌트마다 정책을 집행하고, 메시지를 나르니 결함은 곧잘 보안 결함이 됩니다. 이 장은 결함을 제보하는 방법, 지금 갖춘 장치, 아직 확인하지 못한 부분을 다룹니다.

## 범위

포함: 저장소의 크레이트, 게이트웨이 바이너리와 컨테이너 이미지, JavaScript SDK. 예를 들면 인증이나 테넌트 격리 우회, 다른 테넌트의 룸이나 데이터에 닿는 것, 클라이언트가 일으키는 크래시나 끝없는 자원 사용, 로그나 응답에 드러나는 비밀 값입니다.

제외: 벤치마크 도구와 스크립트, `spikes/` 아래의 버리는 실험, 문서가 하지 말라고 경고한 설정이 있어야 생기는 문제(운영에서 개발용 인증기를 쓰거나, 서버 API를 공개 인터페이스에 여는 경우).

## 갖춘 장치

**인증.** JWT 알고리즘은 인증기마다 고정이고, 설정한 발급자와 대상은 반드시 확인합니다. JWKS 재조회에는 횟수 제한이 있고, URL로 받은 대칭 키는 쓰지 않으며, 오래된 키는 더 믿지 않습니다. 1회용 티켓은 실패해도 한 번만 쓸 수 있고, 테넌트에 묶이고, 수명이 짧고, 개수에 상한이 있으며, Redis에는 해시로만 저장합니다. 연결 중 갱신으로 사용자를 바꿀 수 없고, 좁아진 권한은 즉시 적용합니다.

**권한.** 룸에 들어갈 때마다 구독 권한을, 서비스 컨텍스트를 거치는 발행마다 발행 권한을 확인합니다. Hot 프레임은 보낸 사람이 들어가 있는 룸에만 갑니다. 허용 목록은 기본이 거부입니다.

**입력.** 프레임 크기 제한은 WebSocket 코덱에서 테넌트별로 겁니다. 디코더에는 패닉 경로가 없고 퍼징을 거칩니다. 운영 코드에는 `unwrap`, `expect`, `panic!`이 없으며 린트가 막고, 패닉할 수 있는 슬라이스 인덱싱도 없습니다. 사용자·테넌트·세션 ID는 키의 일부가 되므로 안전한 문자만 허락하고, 룸 이름이 다른 키와 부딪칠 수 없게 했습니다.

**네트워크.** 브라우저 Origin을 확인합니다. 프록시 뒤의 클라이언트 주소는 `X-Forwarded-For`에서 오른쪽부터 처음 만나는 신뢰할 수 없는 주소를 씁니다. 핸드셰이크 속도 제한이 쓰는 메모리에는 상한이 있습니다. 백엔드 HTTP 클라이언트는 리다이렉트를 따라가지 않고, 환경의 프록시 설정을 무시하고, 응답 크기에 상한을 두고, 로그에서 자격 증명을 가립니다.

**시간.** 유휴 시간, 핑, 자격 증명 만료는 단조 시계로 잽니다. 그래서 일부 가상 머신에서 생기듯 벽시계가 뒤로 가도 세션이 더 살아남거나 일찍 닫히지 않습니다.

**공급망.** CI에서 `cargo deny`로 의존성을 감사합니다.

## 결함을 찾아낸 방법

고친 결함은 모두 어떻게 찾았는지, 어떤 시험으로 재현하는지와 함께 [`docs/HARDENING.md`](https://github.com/AsyncNomad/wsPrism/blob/main/docs/HARDENING.md)에 기록합니다. 지금까지의 출처는 이렇습니다.

- 단계마다 한 **검토**, 그리고 첫 릴리스 전의 전체 검토
- 신뢰할 수 없는 입력을 보는 모든 파서의 **퍼징**
- 노드를 죽이고, Redis를 재시작하고, 네트워크를 가르고, 롤링 업데이트를 하는 **카오스 시험**
- 메시지 하나하나를 추적하는 판정기가 붙은 **무작위 soak 시험.** 여러 결함을 찾았는데, 그 가운데에는 재시작 뒤 죽은 Redis 소켓에서 이력 읽기가 실패하던 문제와, 진짜 유실을 가렸을 시험 장치 쪽 결함도 있었습니다.
- **릴리스 전 결함 전수 탐색.** 위험이 큰 순서로 코드를 읽고, 의심 가는 곳은 고치기 전에 실패하는 시험으로 먼저 확인했습니다. 결함 다섯 개를 찾았습니다. 같은 세션 ID로 동시에 들어온 연결이 모두 살아남을 수 있었고(단일 노드와 클러스터 모두), 서버 API의 Hot 발행이 다른 노드의 멤버에게 가지 않았고, 아주 먼 만료 시각을 가진 토큰이 핸드셰이크를 패닉시킬 수 있었고, SDK가 재입장이 중간에 끊긴 룸을 영영 버릴 수 있었습니다.

## 아직 확인하지 못한 부분

- 외부 보안 감사를 받지 않았습니다.
- 펜싱은 룸 트래픽만 덮습니다. 펜싱된 노드의 세션·멤버십 쓰기는 거절되지 않고, 그 노드가 멈춘 뒤 정리됩니다.
- soak 시험은 노드와 Redis 사이에 네트워크 장애(지연, 블랙홀, 리셋)를 넣지만, 패킷 손실·재정렬·비대칭 분할은 넣지 않았고, 클라이언트와 노드 사이에는 장애를 넣지 않았습니다.
- Sentinel 장애 조치는 soak 안에 섞지 않고 따로 시험합니다.
- 극한 부하에서 테넌트가 완전히 격리되지는 않습니다. 굶는 테넌트는 없지만, 한 테넌트의 부하가 다른 테넌트의 지연을 올립니다. 테넌트별 속도 제한을 쓰세요.
