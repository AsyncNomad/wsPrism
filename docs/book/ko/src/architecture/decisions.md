# 설계 결정

wsPrism의 중요한 결정은 모두 아키텍처 결정 기록(ADR)으로 남깁니다. 무엇을 정했는지, 왜 그렇게 정했는지, 어떤 대안을 버렸는지, 그 결정이 무엇을 치르게 하는지를 적습니다. 원문은 저장소의 [`docs/adr/`](https://github.com/AsyncNomad/wsPrism/tree/main/docs/adr)에 있고, 이 장은 그 요약과 사용자에게 가장 중요한 이유를 정리합니다.

## 기록 목록

| ADR | 결정 | 상태 |
|---|---|---|

| 0002 | 전송과 무관한 송신 프레임. 한 번 인코딩해 모든 수신자가 함께 씀 | 채택 |
| 0003 | 자격 증명을 실을 위치를 설정으로, 프로토콜 버전은 서브프로토콜로 협상 | 채택 |
| 0004 | 제품 방향: 실시간 상태 동기화 | 측정 결과를 조건으로 채택 |

## 사용자가 알아 두면 좋은 결정

### 룸은 특별 취급이 아니라 서비스다 (0001)

예전에는 서비스가 세션 상태를 바꿀 방법이 없어서 `room.join`을 세션 루프 안에서 `if svc == "room"`으로 따로 처리했습니다. 세션마다 컨텍스트를 하나 두고 서비스에 가변 참조로 빌려주도록 바꾸자, 룸은 평범하게 등록되는 서비스가 됐습니다. 세션이 속한 곳을 바꿔야 하는 내 서비스도 마찬가지로 만들 수 있습니다. 세션 루프는 특정 서비스를 전혀 모릅니다.

### 자격 증명은 URL에 싣지 않는다 (0003)

브라우저는 WebSocket에 헤더를 붙일 수 없어서, 많은 시스템이 토큰을 쿼리스트링에 넣습니다. 그러면 프록시와 CDN 로그에 고스란히 남습니다. wsPrism은 쿠버네티스가 쓰는 것과 같은 우회로로, 토큰을 서브프로토콜 항목에 싣고 절대 되돌려 보내지 않습니다. 쿼리스트링은 레거시 클라이언트를 위해 남겨 두되 기본으로 꺼 두었습니다.

쿠키는 쓰지 않기로 했습니다. 브라우저가 아닌 클라이언트에 맞지 않고, 브라우저가 알아서 붙이기 때문에 교차 사이트 WebSocket 하이재킹을 더 쉽게 만듭니다.

### 프로토콜 v2는 SDK보다 먼저, 한 번에 (0006)

v1을 기존 게이트웨이들과 견주어 검토했더니 어긋나는 점이 여섯 가지 나왔습니다. 레인이 WebSocket 프레임 종류에 묶여 있었고, Hot 프레임에 명시적 대상이 없었고, 메시지마다 버전 바이트가 있었고, 모르는 필드를 무시하지 않고 거절했고, 어떤 끊김이든 종료 코드 하나로 처리했고, Hot 프레임이 송신자를 밝히지 않았습니다. 변경 비용이 가장 쌀 때, 즉 SDK가 생기기 전에 여섯 가지를 v2에서 한꺼번에 고쳤습니다. v1도 협상을 통해 계속 받습니다.

종료 코드 범위(4000번대: 재시도 금지, 4100번대: 기다렸다 재시도, 4200번대: 바로 재시도)는 클라이언트 개발자들이 Pusher에서 이미 익숙한 관례를 따랐습니다.

### 프레즌스 이벤트는 직접 켜야 하고, 신뢰 전달로 보낸다 (0010)

1만 명 룸에서는 한 명이 들어올 때마다 알림이 1만 건 나갑니다. 그래서 프레즌스 이벤트는 테넌트가 직접 켜야 합니다. 신뢰 전달로 보내는 이유는, `member_left`를 하나 잃으면 유령 멤버가 영영 남기 때문입니다. 재접속보다 나쁜 일입니다. 현재 멤버 목록은 따로 요청하지 않고 입장 응답에 실어 보내므로, 두 요청 사이에 이벤트가 끼어들 틈이 없습니다.

### Ext는 Redis를 거치고, Hot은 로컬에 먼저 준다 (0011)

클러스터에서 신뢰 메시지는 같은 노드에 있는 멤버에게 가는 것까지 Redis를 거칩니다. Redis 왕복 한 번이 들지만, 그 대신 모든 노드가 한 룸의 메시지를 정확히 같은 순서로 전달합니다. Hot 프레임은 로컬 멤버에게 바로 주고 다른 노드로도 넘깁니다. 상태를 Redis로 돌리면 낮은 지연이 존재 이유인 트래픽에 지연을 얹는 셈이고, 순서는 키별 일련번호로 이미 해결됩니다.

클러스터에서 버린 대안은 이렇습니다.

| 대안 | 버린 이유 |
|---|---|
| 스티키 세션으로 룸마다 노드 하나 | 한 룸의 멤버가 여러 노드에 흩어지는 순간 깨지고, 노드가 죽으면 룸도 함께 사라집니다 |
| 노드 사이 가십 메시 | 멤버 관리, 분할, 재연결을 모두 처음부터 만들고 검증해야 합니다 |
| Redis보다 NATS 먼저 | Redis 하나로 pub/sub, 이력, 카운터, 키-값, 프레즌스를 다 할 수 있고, 대부분의 팀이 이미 운영하고 있습니다. 브로커 트레이트가 나중의 NATS를 막지는 않습니다 |
| 이력을 기본으로 켜기 | 룸마다 메모리가 들고, 상태 룸에서는 의미가 없습니다 |
| 클라이언트 ACK로 복구 | 메시지마다 위로 가는 트래픽이 생깁니다. offset으로 다시 요청하는 편이 싸고 단순합니다 |

### 티켓만 레플리카를 기다린다 (0011)

장애 조치 뒤 노드들이 Redis에 쓴 것은 모두 저절로 복구됩니다. 이력은 새 epoch를 시작하고, 노드는 재등록하고 세션을 되살립니다. 예외는 1회용 티켓의 소비입니다. 기록을 놓친 레플리카가 승격되면 티켓을 다시 받아 줍니다. 그 쓰기 하나만 레플리카의 확인을 기다리고, 나머지는 모두 빠르게 둡니다.

### JWKS와 연결 중 갱신 (0012)

IdP는 키를 교체하고, 5~15분짜리 액세스 토큰을 발급합니다. JWKS가 없으면 키가 바뀔 때마다 설정을 고쳐야 했고, 연결 중 갱신이 없으면 모든 사용자가 몇 분마다 재접속했습니다. 둘이 함께 있어야 흔한 SSO 구성이 제대로 돌아가므로, 클러스터 작업보다 먼저 넣었습니다.

## 미뤄 둔 결정

### WebSocket 프레이밍 직접 구현 (0007)

프로파일을 떠 보니 WebSocket 프레이밍이 CPU의 약 14%였고, 유휴 연결마다 8 KB 읽기 버퍼가 붙어 있었습니다. 업그레이드된 소켓을 직접 맡는 시제품을 만들었지만 첫 단계에서 목표에 못 미쳤고, 기능을 먼저 갖추기로 하면서 미뤄 두었습니다. 전송 경계가 있으니 나중에 세션이나 서비스를 건드리지 않고 다시 시작할 수 있습니다.

### 룸 트래픽을 여러 Redis에 나누기 (0013)

이력 처리량은 Redis 코어 하나, 초당 약 14만~15만 메시지에서 막힙니다. 설계(논리 슬롯 16,384개를 샤드에 대응시키고, 샤드별 펜싱에 세대 번호를 쓰는 방식)는 채택했습니다. 구현은 수요가 생길 때 합니다. 노드 하나가 이미 초당 약 12만 건의 이력 발행을 감당하니, 지금 천장은 대략 노드 하나 분량의 이력 트래픽이 클러스터 전체의 한계라는 정도입니다. 이 복잡도는 브로커의 한가운데에 들어가게 되고, 접속 폭주의 천장은 그래도 제어용 Redis에 묶여 있습니다.

## 재 보고 되돌린 최적화

모든 아이디어가 측정을 통과하지는 못했습니다. 다음은 구현하고 재 본 뒤 되돌린 것들이며, 결과는 [벤치마크](../project/benchmarks.md)에 남겨 두었습니다.

- **전역 할당자 mimalloc:** CPU 이득이 없었고, 부하 중 연결당 메모리가 최대 두 배가 됐습니다.
- **노드의 룸 색인을 멤버마다가 아니라 룸마다 한 번:** Redis CPU가 2% 줄었지만, 맞춰 둬야 할 상태가 하나 더 느는 대가로는 작았습니다.
- **세션 등록을 파이프라인으로 묶기:** Redis CPU는 8~12% 줄었지만 노드 처리량이 3~6% 떨어지고 접속 지연이 늘었습니다. 먼저 닿는 천장은 Redis가 아니라 노드입니다.
- **Redis 명령을 Lua 스크립트 하나로 합치기:** 빈 스크립트 하나가 대신하려던 명령들보다 Redis에 더 비쌌습니다.
