# 设计理念

wsPrism 的设计始终围绕几条原则展开。先了解它们再读正文会轻松很多，因为后面描述的大多数行为都是由此而来。

## 把连接从应用里请出去

长连接是一份长期存在的状态：要定时发心跳，要计算超时，要限流，令牌过期后要重新认证，所属的任何一个房间有了新消息都得马上唤醒它。应用服务器擅长处理彼此独立的短请求，却很少擅长同时撑住几十万条这样的连接。

wsPrism 替应用接下了这份工作。它不是一个库，而是一个运行在后端旁边的独立进程，也就是常说的 sidecar。后端服务依旧是无状态的 HTTP 服务，可以按自己的节奏发布、扩容和重启。它们只通过三个很窄的接口与网关打交道：

- 决定谁可以连进来（一次性票据、JWT，或者由网关回调的连接代理）；
- 通过服务端 API 向房间发消息、踢下线用户；
- 响应经由 RPC 代理转发过来的请求。

这些事情都不需要会 Rust，也都不需要后端知道某个用户连在哪一个网关节点上。

## 数据分两类，所以通道也分两条

实时流量并不是同一种东西。一条聊天消息必须送达、只送一次、而且要按顺序；一个每秒移动六十次的玩家坐标，如果更新的值已经在路上，旧值送不送到都无所谓，硬要送达只会徒增延迟。

大多数系统只选其中一种模型，另一种就用得很别扭。wsPrism 让两者共用一条连接：

- **Ext 通道**传输 JSON 信封，是可靠投递：要么按顺序送达，要么明确告诉客户端送不到。
- **Hot 通道**传输按服务 ID 和操作码路由的小型二进制帧，生来就允许丢弃。接收方跟不上时，网关不会把中间值统统排队，而是每个键只保留最新的那一个。

选通道就是选投递语义，这个选择明明白白写在协议里，而不是藏在某个配置开关后面。

## 默认拒绝

网关直接面对公网上的用户，默认值理应是安全的那一边；要放宽，必须是一个在配置评审时一眼就能看到的明确决定。

所以，租户只接收白名单里的消息类型；浏览器的 Origin 不在列表里就拒绝；不从查询字符串里读取票据，因为代理会把 URL 记进日志；每一项限制（帧大小、每用户房间数、每用户会话数、请求速率）都有有限的默认值。配置解析器会拒绝不认识的字段，免得一个拼写错误就让某项保护悄无声息地失效。

## 失败要大声说出来

分布式系统一定会丢消息，关键在于有没有人知道丢了。

wsPrism 把"悄悄丢失"视为缺陷。集群节点短暂失去 Redis 订阅时，相关房间的成员会收到 `sys.gap`，知道该重新加载状态了；历史消息补不回来时，回复里会写明 `recovered: false`；Redis 太慢、接不住更多请求时，发布方会立刻收到 `UNAVAILABLE`，而不是先拿到一个"成功"、一分钟后才变成丢失；节点一旦发现自己的位置已被别的节点接管，就会停下来，而不是继续写入已经不属于它的状态。

[集群部署](guide/cluster.md)一章列出了我们测试过的每一种故障，以及客户端在每种情况下会看到什么。

## 先测量，再下结论

本文档里每一条关于性能的说法都有对应的测量，场景、硬件和原始数据都在代码仓库里。某项优化如果得不偿失，就撤回，但结果照样记录下来。和其他产品的对比如果在某些方面不公平（比如在同一台机器上测、对方用的是默认配置），基准测试的说明里也会写清楚。

正确性同样如此。故障下的行为，只有在混沌测试或长时间浸泡测试（soak test）实际验证过之后才会写进文档；尚未验证的盲区单独列在[安全](project/security.md)里，而不是略过不提。

## 先有边界，再有功能

新能力总是先放到一个边界后面：一个 trait、一个注册表条目、一段配置。认证是一条由认证器组成的链，内置认证器和你自己写的认证器用的是同一个接口。节点之间的房间流量走 broker trait，单节点和 Redis 只是它的两种实现。服务按名称注册，内置的 `room` 和 `chat` 服务在核心里也没有任何特殊通道。

这样一来，绝大多数定制都不需要 fork：加一个认证器、一个服务或一条后端路由即可，不用去改调度器。

## 契约只增不改

客户端更新得很慢，一个移动应用在最后一次发版后还可能被用上一年。所以线路协议、服务端 API 和配置格式只做加法：可以新增字段、错误码和接口，已有的名称和含义保持不变。实在无法这样做的改动，会像 v2 与 v1 并存那样，作为新的协议版本与旧版本一起协商。0.x 阶段 Rust API 可以变得快一些，哪些部分是稳定的，[Rust API](reference/rust-api.md) 里写得很清楚。
