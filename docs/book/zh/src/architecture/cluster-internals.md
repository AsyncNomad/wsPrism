# 集群内部机制

本章说明 Redis broker 如何让多个节点保持一致，以及每个机制为什么存在。从运维视角讲同一件事的是[集群部署](../guide/cluster.md)。

## 键与频道

所有键和频道都以配置的前缀开头（这里用 `wsp`）。属于某个房间或用户的键带有 Redis Cluster 哈希标签，将来支持 Redis Cluster 时无需改名。

| 键 | 内容 |
|---|---|
| `wsp:r:{tenant::room}` | 房间的 pub/sub 频道 |
| `wsp:r:{tenant::room}:st` | 历史状态：最后的 offset、epoch、字节数、按节点的去重标记、写入方 Redis 的 `run_id` |
| `wsp:r:{tenant::room}:log` | 历史消息：以 offset 为分值的有序集合 |
| `wsp:us:{tenant::user}` | 某个用户的会话表 |
| `wsp:pr:{tenant::room}` | 跨节点的房间成员关系 |
| `wsp:nr:<node id>` | 某节点上有成员的房间 |
| `wsp:nodes` | 存活的节点 |
| `wsp:ctl:<slot>` | 发往某节点的控制频道（关闭会话等） |

房间名可以包含任何可打印字符，但房间名从不出现在键模式中，而且每类键的后缀各不相同，所以无法靠构造房间名去撞上其他键。

## 节点槽位

节点在集群中的身份是 1,024 个槽位中的一个：启动时用 `SET NX PX` 占用，之后每隔 `slot_ttl_s` 的三分之一用心跳续约。成员 ID 中嵌入了槽位号，不需要中心计数器就能保证跨节点唯一。

心跳和延迟探测共用一条专用连接，二者都不会排在会话流量后面。探测连续失败四次，就重建这条连接。

## 发布

无论在哪个节点上发布，消息都先进入该节点的发件箱。发件箱容纳所有租户的帧，但每个租户各有一条 FIFO，轮流取出，因此一个租户的突发流量不会把其他租户的帧挤到单一队列的末尾。同一个房间内，帧与成员变更的先后顺序保持不变：订阅尚在确认中的房间，其帧会等待确认，其他房间照常前进。

离开发件箱的批次，按"每个房间每批一次"的粒度变成脚本调用：

- **不带历史的房间**使用 `PUBLISH_FENCED`：先确认本节点仍持有自己的槽位，再发布这一批。
- **带历史的房间**使用 `PUBLISH_KEPT`：为每条消息分配下一个 offset，追加到日志，按条数、时长和字节数修剪日志，发布，并记下本节点最后应用的帧序号。

有了这个序号，重试就是安全的。某一批的回复丢了（超时、连接断开）时，发件箱会重发，而脚本会跳过已经应用过的帧。网关自身的重试绝不会让一条历史消息被存两次或投两次。

Redis 变慢时，帧会排队等待。当发件箱或某个租户的份额已满，或者最早的帧已经等了 `outbox_max_wait_ms`，新的可靠发布会以 `UNAVAILABLE` 拒绝，可丢弃的发布则直接丢掉。发布方当场就知道结果，而不是先拿到一个"成功"、之后才变成丢失。

## 接收

节点只在某个房间有本地成员时才订阅它的频道。房间按哈希分布在 `pubsub_connections` 条连接上，同一个房间始终落在同一条连接上，从而保持顺序。同时发起的订阅会一起发出，并在每条连接上以流水线方式发送；改成这样之后，连接风暴中加入新房间的速度提高了八到十倍。

来自 Redis 的帧以每批最多 1,024 条交给各个房间，这也是会话队列应保持默认大小或更大的原因。

订阅连接断开时，节点会重连、重新订阅，并向该连接上所有房间的成员发送 `sys.gap`。它不知道自己漏了什么，所以就如实说明可能漏了。

## 加入带历史的房间

在单节点上，读取历史和登记新成员是原子完成的；在多节点上做不到：读取历史要去 Redis 走一个来回，而这期间消息还在不断到达。因此节点在读取期间先把该房间的新消息暂扣下来（最多 1,000 条），发完补发的消息后再放行暂扣的消息，并跳过补发中已经包含的部分。如果读取期间到达的消息超过 1,000 条，节点不做猜测，而是在补发之后发送 `sys.gap`。

## Epoch 与 Redis 重启

`:st` 哈希中记录了写入它的 Redis 进程的 `run_id`。重启后的 Redis 或被提升的副本 `run_id` 不同，其数据可能比客户端已经看到的更旧。节点一旦发现不一致，或发现状态丢失，该房间就开启新的 epoch。持有旧 epoch offset 的客户端会收到通知（带新 epoch 的 `sys.gap`）并重新同步，而不会从如今已指向别的消息的 offset 继续接收。

## 跨节点的会话

一个用户的所有会话存放在一个哈希中，只能由 Lua 脚本修改。`CLAIM` 原子地裁决一条新连接：顶替相同的 `sid`、执行 `max_sessions_per_user`、按配置挤掉最早的会话，并清理那些槽位键已不再指向自己的节点所留下的条目。失去会话的节点会通过控制频道收到通知。

有两种竞争需要专门处理，都有测试覆盖：

- 被驱逐的目标，可能是其所在节点已在 Redis 登记、但尚未在本地登记的会话。节点会把它标记为 *doomed*，等登记到达时予以拒绝。
- 节点之间的关闭命令可能丢失。每个节点每 15 秒把本地会话与会话表核对一次，关闭表中已不存在的会话。

## 在线状态与失效节点

成员关系存放在 `wsp:pr:{…}` 中，每个会话占一个字段。每个节点每隔几秒查找一次失效节点（槽位键中已不再是它的 ID）。对于每个失效节点，由一个节点抢到一把短期锁并移除它的成员。只有真正删除了成员的那次 `HDEL` 才会上报，所以无论由哪个节点清理，每条 `member_left` 都恰好发送一次。

## Fencing（隔离）

一个曾经卡住、或与 Redis 断开超过 `slot_ttl_s` 的节点，回来时可能发现槽位已归别人所有。若它继续发布，就会有两个节点以同一个身份发言。因此两个发布脚本都在 Redis 内部、在与发布相同的原子步骤中校验槽位归属。被隔离的节点会收到 `FENCED`，将自己标记为不健康（`/readyz` 变为 503），立即拒绝新的发布，排空后以错误退出，由编排系统重启。

Fencing 覆盖的是客户端看得到的房间流量。会话与成员关系的写入不受其约束，节点消失后由其他节点清理。

引入 fencing 后，每次不带历史的发布要多花约 1.2 µs 的 Redis CPU，也就是翻了一倍；但由于一批消息现在只返回一个回复，而不是每条一个，单个节点能推给 Redis 的量反而提高了。

## Sentinel 与主从切换

配置 Sentinel 后，节点每秒向 Sentinel 询问一次主节点。主节点一变，所有连接（发布、订阅、控制、心跳）都迁移到新主节点。带历史的房间开启新的 epoch，各节点在一个自我修复周期内重新注册，并恢复会话与成员关系。

有一种写入无法这样修复：一次性票据的消耗。没收到消耗记录的副本一旦被提升，就会把这张票据再接受一次。因此兑换票据时，会在专用连接上用 `WAIT` 等到 `replica_ack.replicas` 个副本收到记录；超时未确认就按失败处理。

## 过载保护

节点每 250 ms 通过专用连接 ping 一次 Redis。只要响应慢于 `admission.max_latency_ms`，或者等待中的会话登记超过 `max_pending_claims`，新连接就会在握手阶段以 503 `cluster_busy` 拒绝，`Retry-After` 在 1 到 5 秒之间随机分布。这一步在认证之前，被拒的客户端不会消耗票据。如果没有这道保护，故障后的重连风暴会把成千上万个会话登记堆在本已吃力的 Redis 前面，拖慢所有节点的心跳，最终连健康的节点也会被隔离。

## Redis 恢复之后

收到 `NOSCRIPT` 时重新加载脚本。心跳在 Redis 一响应就立即执行，因此刚启动的节点不会租用到某个仍然存活、但其槽位随旧数据一起消失的节点的槽位。可以安全重复的读取（历史、成员关系）在碰到随旧进程一起失效的连接时，会再重试一次。在加入这次重试之前，重启后的第一次补发总是失败，而下一次心跳又把这个问题掩盖了过去。

## 测试

集群行为由三层测试锁定：

- **集成测试**：针对 Docker 中真实的 Redis 运行，包括要求客户端证书的纯 TLS Redis，以及启用双向 TLS 的 Sentinel。
- **混沌测试**：杀节点、让 Redis 以空数据或快照重启、暂停 Redis、让节点断开超过 `slot_ttl_s`、执行滚动升级，然后检查没有消息丢失或重复投递。
- **随机浸泡测试**：持续运行十分钟以上，随机注入进程故障、链路故障（延迟、黑洞、重置）和 Redis 重启；判定器跟踪每一条发布的消息和每一次探测，报告任何无法用已通知的空缺来解释的丢失或重复。

浸泡测试在发布前发现了若干真实缺陷，见[安全](../project/security.md#缺陷是如何发现的)。
