# 设计决策

wsPrism 的每一项重要决策都以架构决策记录（ADR）的形式保存下来：决定了什么、为什么、否决了哪些方案、这个决定要付出什么代价。完整记录在仓库的 [`docs/adr/`](https://github.com/AsyncNomad/wsPrism/tree/main/docs/adr) 中（以韩文撰写）。本章做一个概要，并挑出对用户最重要的理由。

## 用户值得了解的决策

### 房间是服务，不是特例（0001）

过去，由于服务没有办法修改会话状态，`room.join` 是在会话循环里用 `if svc == "room"` 单独处理的。改为每个会话持有一个上下文、并以可变借用的方式交给服务之后，房间就成了一个普通的已注册服务；需要改变会话归属的自定义服务，也可以用同样的方式实现。会话循环对具体服务一无所知。

### 凭证不进 URL（0003）

浏览器不能给 WebSocket 设置请求头，于是很多系统把令牌放进查询字符串，结果被代理和 CDN 原封不动地记进日志。wsPrism 采用与 Kubernetes 相同的变通办法：把凭证放进一个子协议条目，并且从不回显。查询字符串仍为旧客户端保留，但默认关闭。

Cookie 方案被否决：它不适合非浏览器客户端，而且浏览器会自动附带 Cookie，跨站 WebSocket 劫持反而更容易。

### 协议 v2 在 SDK 之前一次性完成（0006）

把 v1 与成熟网关对照审查后，发现了六处不一致：通道与 WebSocket 帧类型绑定；Hot 帧没有显式目标；每条消息都带版本字节；未知字段被拒绝而不是被忽略；所有断线共用一个关闭码；Hot 帧不标明发送方。趁着改动成本最低、SDK 还不存在的时候，v2 一次性修正了这六点。v1 仍可通过协商继续使用。

关闭码区间（4000 段：不要重试；4100 段：退避后重试；4200 段：立即重试）沿用了客户端开发者在 Pusher 上早已熟悉的约定。

### 在线状态事件需显式开启，并可靠投递（0010）

一万人的房间里，一个人进来就要发出一万条通知，所以在线状态事件需要租户自行开启。它们以可靠方式投递，因为丢一条 `member_left` 就会留下一个永远不走的"幽灵成员"，这比重连更糟。当前成员快照随加入回复一起返回，而不是另发请求，两个请求之间就不存在事件插进来的空隙。

### Ext 经过 Redis，Hot 先本地投递（0011）

在集群中，可靠消息即使发给同一节点上的成员，也要经过 Redis。这多了一次 Redis 往返，换来的是所有节点投递同一房间消息的顺序完全一致。Hot 帧则先立即投递给本地成员，再转发给其他节点。让状态也绕道 Redis，就等于给一类以低延迟为存在意义的流量平添延迟；而顺序问题，按键递增的序号已经解决了。

集群方案中被否决的选项：

| 方案 | 否决原因 |
|---|---|
| 会话粘滞，每个房间固定在一个节点上 | 一旦房间成员分布在多个节点就会失效；节点宕机时房间也随之消失 |
| 节点之间组成 gossip 网状网络 | 成员管理、网络分区、重连都得从零开始实现并验证 |
| 先做 NATS 而不是 Redis | Redis 一个组件就能覆盖 pub/sub、历史、计数器、键值和在线状态，而且大多数团队已经在运维它。broker trait 并不妨碍日后加入 NATS |
| 默认开启历史消息 | 每个房间都要占内存，而对状态类房间毫无意义 |
| 用客户端确认（ACK）来做恢复 | 每条消息都会产生上行流量。按 offset 重新请求更省也更简单 |

### 只有票据需要等待副本（0011）

主从切换后，节点写入 Redis 的一切都会自动修复：历史开启新的 epoch，节点重新注册并恢复会话。唯一的例外是一次性票据的消耗：没收到这条记录的副本被提升后，会把票据再接受一次。只有这一种写入需要等待副本确认，其余写入都保持快速。

### JWKS 与连接内续期（0012）

身份提供方会轮换密钥，签发的访问令牌通常只有五到十五分钟有效期。没有 JWKS，每次轮换都要改配置；没有连接内续期，每个用户每隔几分钟就要重连一次。二者合在一起，决定了一套常见的 SSO 方案能否正常工作，所以排在集群之前完成。

## 暂缓的决策

### 自行实现 WebSocket 分帧（0007）

性能剖析显示，WebSocket 分帧约占 CPU 的 14%，每条空闲连接还挂着一个 8 KB 的读缓冲区。接管升级后套接字的原型在第一阶段没能达到目标，于是先把精力放在功能上。有了传输边界，日后重启这项工作时无需改动会话和服务。

### 把房间流量分散到多个 Redis（0013）

历史消息的吞吐量受限于单个 Redis 核心，大约每秒 14 万到 15 万条。设计方案（16,384 个逻辑槽位映射到各个分片，每个分片的 fencing 使用代数编号）已经采纳，实现则等到有实际需求时再做：单个节点已能承受每秒约 12 万次历史发布，所以眼下整个集群的上限大致相当于一个节点的历史流量。这份复杂度会落在 broker 的核心位置，而且连接风暴的上限依然受控于负责控制面的那台 Redis。

## 测过之后撤回的优化

并不是每个想法都经得起测量。下面这些都实现过、测过、又撤回了，结果保存在[基准测试](../project/benchmarks.md)中：

- **把全局分配器换成 mimalloc：** CPU 没有收益，负载下每条连接的内存最多翻倍。
- **节点的房间索引按房间而不是按成员只写一次：** Redis CPU 降了 2%，但为此要多维护一份与 Redis 保持一致的状态，得不偿失。
- **把会话登记合并成流水线批量发送：** Redis CPU 降了 8% 到 12%，但节点吞吐量下降 3% 到 6%，连接延迟也上升了。最先碰到的上限是节点，而不是 Redis。
- **把多条 Redis 命令合并进一个 Lua 脚本：** 一个空脚本对 Redis 的开销，就已经超过了它要替代的那些命令。
