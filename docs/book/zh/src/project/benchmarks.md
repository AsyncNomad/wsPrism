# 基准测试

本文档中的性能结论都来自保存在仓库里的测量：场景、工具、原始数据（`bench/results/*.jsonl`），以及每次测量的说明，见 [`docs/BENCHMARKS.md`](https://github.com/AsyncNomad/wsPrism/blob/main/docs/BENCHMARKS.md)。本章是这些测量的摘要，也会明确交代它们的局限。

## 测量方法

- **负载生成器：** `wsprism-loadgen` 建立真实的 WebSocket 连接并加入房间，其中一部分连接发布带有发送时间戳的探测消息。接收方把延迟记入 HDR 直方图。发送方和接收方在同一个进程里，不涉及时钟同步。投递率（收到的探测数 ÷ 发送的探测数 × 房间人数）能暴露任何丢失。
- **隔离：** 网关绑定在 8 个核心上，负载生成器使用其他核心。网络命名空间（`bench/netlab.sh`）可以注入延迟和丢包。
- **开销：** 在服务端测量每次投递的 CPU 时间和每条连接的进程内存（RSS）。
- **重复：** 每种配置跑三次，分别列出而不取平均，让波动一目了然。
- **对比对象：** Centrifugo 6.9.7 和 Sockudo 使用默认配置，只加上场景必需的内容（匿名访问，以及对比历史时开启历史）。配置文件在 `bench/competitors/` 中。

**局限。** 所有数据都在同一台机器上测得（Intel i7-13700K，WSL2），负载生成器也运行在这台机器上，换成专用服务器，绝对值会有所不同。对比对象没有调优。内存是进程 RSS，不含内核套接字缓冲区，后者对每种服务器来说开销差不多。请把倍数当作趋势参考，不要当成定论。

## 单节点：与其他网关对比

64 字节消息，每条连接使用不同的用户，服务端 8 个核心。"房间"场景是许多几十人的房间，"广播"场景是少数几个大房间。吞吐量指每秒投递给其他成员的次数。

| 场景 | 服务器 | p50 / p99（ms） | 每次投递 CPU µs | 每连接 KB |
|---|---|---|---|---|
| 房间，18 万/秒 | wsPrism | 0.32 / 0.7 | 5.02 | 19.7 |
| | Centrifugo | 0.39 / 0.8~1.5 | 7.27 | 78.6 |
| | Sockudo | 0.41 / 0.8~0.9 | 8.64 | 255.8 |
| 房间，108 万/秒 | wsPrism | 0.87 / 2.0~3.3 | 4.30 | 21.8 |
| | Centrifugo | 1.31 / 7.6~9.7 | 5.68 | 83.7 |
| | Sockudo | 饱和（投递率 0.87~1.0，p99 最高 7.4 秒） | 8.96 | 333.2 |
| 房间，216 万/秒 | wsPrism | 2.10 / 6.6~8.5 | 3.49 | 28.1 |
| | Centrifugo | 11.41 / 126~148 | 3.23 | 89.5 |
| 广播，50 万/秒 | wsPrism | 1.76 / 4.5~7.0 | 7.47 | 18.4 |
| | Centrifugo | 2.60 / 8.2~10.8 | 9.82 | 31.5 |
| | Sockudo | 2.76 / 8.3~9.4 | 9.46 | 198.0 |

从中可以看出：

- **内存**差距最大：房间类负载下，每条连接只有 Centrifugo 的四分之一到三分之一，广播场景约为 60%，与 Sockudo 相比则不到十分之一。
- **CPU：** 中低负载下，Centrifugo 每次投递的开销是 wsPrism 的 1.3 到 1.45 倍，Sockudo 是 1.3 到 1.9 倍。每秒 216 万次投递时，Centrifugo 的 CPU 少用约 7%，但 p99 高出约 18 倍，看起来它是以尾延迟为代价做了更激进的批处理。
- **尾延迟**直到测试的最高负载都保持在个位数毫秒。

### 所有房间都开启历史

两种服务器都为每个房间保留 200 条消息，保留 10 分钟：

| 场景 | 服务器 | 投递率 | p99（ms） | CPU µs | 每连接 KB |
|---|---|---|---|---|---|
| 房间，18 万/秒 | wsPrism | 1.000 | 0.7~1.0 | 5.07~6.93 | 29.9 |
| | Centrifugo | 1.000 | 0.8~1.2 | 7.76~10.01 | 96.5 |
| 房间，108 万/秒 | wsPrism | 1.000 | 2.3~4.5 | 4.34~4.72 | 32.2 |
| | Centrifugo | 1.000 | 8.7~12.2 | 5.31~6.15 | 104.6 |
| 房间，216 万/秒 | wsPrism | 1.000 | 6.4~9.4 | 3.21~3.36 | 37.7 |
| | Centrifugo | 0.937~1.000 | 1,846~3,934 | 3.32~3.80 | 97.4 |

开启历史让 wsPrism 的 CPU 增加 1% 到 3%，每条连接多占 4 到 10 KB。在最高负载下，开启历史的 Centrifugo 进入饱和（p50 最高达 1 秒），而 wsPrism 的延迟与不开历史时相同。

## 集群：与 Centrifugo 的 Redis 引擎对比

两款产品使用同一个单核 Redis，分别以一个节点、或在同样 8 个核心上拆成两个节点运行。

**开启历史**（Redis 是上限）：

| 发布/秒 | 服务器 | 投递率 | p50 | p99 |
|---|---|---|---|---|
| 12 万 | wsPrism，1 节点 | 1.000 | 8.1~8.9 ms | 15~24 ms |
| | wsPrism，2 节点 | 1.000 | 13~17 ms | 25~64 ms |
| | Centrifugo，1 节点 | 0.79~0.83 | 2.7~3.0 秒 | 5.6~6.3 秒 |
| 24 万 | wsPrism，1 节点 | 0.58~0.60 | 118~123 ms | 178~194 ms |
| | Centrifugo，1 节点 | 0.34~0.35 | 6.4~7.0 秒 | 14.7~14.9 秒 |

在同一个 Redis 上，wsPrism 的历史吞吐量约为 Centrifugo 的 1.5 到 1.7 倍（饱和时约每秒 14 万条对 8.5 万条）。增加节点对两款产品的历史吞吐量都没有帮助，二者都受限于单个 Redis 核心。Centrifugo 支持 Redis Cluster 和分片，可以突破这个上限，wsPrism 目前还做不到。

**不开历史**、负载在容量范围内时，两者都能全部送达。wsPrism 每条连接的内存少 3.5 到 4.5 倍；小房间和广播场景下 CPU 少 1.25 到 1.3 倍，108 万/秒的场景下大致持平；p99 相同或更低。

一旦超出节点容量，两款产品从设计上就走了不同的路。Centrifugo 先积压、晚一点也要送出去（投递 94%~97%，p50 约 1 秒）；wsPrism 则拒绝等待超过 1 秒的发布（投递 89%~90%，p50 为 12~80 ms），并通知发布方以便重试。哪种更合适，取决于具体应用。

## 连接风暴

每个工作者循环执行"连接、认证、加入房间、断开"，每个会话都是不同的用户。以下为集群中单个节点的数据：

| 情形 | 每秒会话数 | 加入 p50 / p99 |
|---|---|---|
| 新房间，每个会话加入 1 次 | 28,600~33,900 | 1~5 ms / 3~10 ms |
| 新房间，每个会话加入 5 次 | 11,700~12,300 | 1 ms / 2 ms |
| 已订阅的房间 | 37,500~37,900 | 2 ms / 7 ms |

改为批量订阅后，第一种情形从每秒约 3,700 个会话提升到约 3 万个，如今的上限是节点 CPU。单个 Redis 核心每秒约能处理 6 万个这样的会话；真实连接是会持续停留的，所以这已经是最坏情况。

## 租户隔离

一个租户以最高每秒 180 万次投递的强度猛灌，另一个租户运行轻量负载：

- **没有饥饿。** 轻量租户在每一轮测试中都收到了全部消息。
- **也没有完全隔离。** 它的延迟随总负载上升。单节点上，p99 从 0.5 ms 升到 2.5~3.1 ms。按租户划分的发件箱（0.2）保证在通往 Redis 的路上一个租户的批次不会排在另一个租户前面，但 CPU 仍是共享的。

目前限制单个租户占用份额的手段，是按租户设置限流。

## 基于数据报的状态同步

在单向延迟 20 ms 的模拟链路上，用 10 人房间、60 Hz 的状态更新，对比 WebTransport 数据报与基于 TLS 的 WebSocket：

| 丢包 | 传输 | 超额 AoI p99 | 可见卡顿 | 相对 WSS 的 CPU / 内存 |
|---|---|---|---|---|
| 均匀 1% | WSS | 49.7 ms | 2.3% 的帧 | — |
| | WebTransport | 15.8 ms | 0.001% | 约 2 倍 / 约 2.3 倍 |
| 突发 1% | WSS | 49.7 ms | 2.6% | — |
| | WebTransport | 15.8 ms | 0% | 约 2 倍 / 约 2.3 倍 |

数据报几乎消除了卡顿，并把超额 AoI 降到三分之一到四分之一；但在库的默认配置下，每条连接的 CPU 和内存大约翻倍。因此结论是混合使用：小型交互房间用数据报，大型广播房间用 WebSocket，按房间选择。0.1.0 不包含 WebTransport。

## 复现

```bash
cargo bench -p wsprism-protocol --bench protocol      # 微基准
cargo bench -p wsprism-gateway --bench hotpath
bench/run-baseline.sh <label>                         # 标准端到端场景
bench/run-compete.sh                                  # 与其他网关对比
bench/run-cluster.sh                                  # 集群
bench/run-churn.sh                                    # 连接风暴
bench/run-fairness.sh                                 # 租户隔离
bench/run-v.sh v-judgment 3                           # 数据报对比 WebSocket
```

这些脚本假定对比对象的二进制程序已在本地，所有流量都只在同一台机器的网络命名空间内运行。
