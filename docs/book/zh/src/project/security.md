# 安全

wsPrism 站在用户面前：它认证连接、执行每个租户的策略、传递消息，所以它的缺陷往往就是安全缺陷。本章说明如何报告问题、目前已有哪些防护，以及还有哪些地方尚未验证。

## 报告漏洞

请不要提交公开 issue，而是通过 GitHub 的私密安全公告表单报告：

<https://github.com/AsyncNomad/wsPrism/security/advisories/new>

请尽量提供：受影响的版本或提交、相关配置（去掉敏感信息）、攻击者能做什么以及需要什么条件（已认证用户、租户 API 密钥、网络位置等），以及复现步骤。

这是一个由小团队维护的年轻项目，下面这些是目标而非合同条款：7 天内确认收到；复现之后尽快给出评估和修复或缓解计划；发布修复版本并附上 GitHub 安全公告，除非你不希望署名，否则会致谢于你。请在公开披露之前给我们留出合理的修复时间。

1.0 之前，安全修复只进入最新的 0.x 版本。

## 范围

包括：仓库中的各个 crate、网关二进制程序和容器镜像、JavaScript SDK。例如：绕过认证或租户隔离、访问到其他租户的房间或数据、由客户端触发的崩溃或无限制的资源消耗、敏感信息出现在日志或响应中。

不包括：基准测试工具和脚本、`spikes/` 下的一次性实验，以及需要文档明确警告过的配置才能触发的问题（在生产环境使用开发用认证器、把服务端 API 暴露在公网接口上）。

## 已有的防护

**认证。** JWT 算法按认证器固定；配置了签发方和受众就必须校验；JWKS 重新拉取有频率限制，忽略通过 URL 获取的对称密钥，过期密钥不再信任。一次性票据只能使用一次（失败也算），绑定租户、有效期短、数量有上限，在 Redis 中只以哈希形式保存。连接内续期不能切换用户，收窄的权限立即生效。

**授权。** 每次加入房间都检查订阅权限，每次经由服务上下文的发布都检查发布权限，Hot 帧只会发往发送者已加入的房间。白名单默认拒绝。

**输入。** 帧大小上限在 WebSocket 编解码层按租户执行。解码器没有会 panic 的路径，并经过模糊测试。生产代码中没有 `unwrap`、`expect` 和 `panic!`（由 lint 保证），也没有可能 panic 的切片下标访问。用户、租户和会话 ID 会成为键名的一部分，因此只允许安全字符；房间名也无法与其他键冲突。

**网络。** 校验浏览器 Origin。代理之后的客户端地址取自 `X-Forwarded-For` 中从右往左第一个不可信的地址。握手限流占用的内存有上限。后端 HTTP 客户端不跟随重定向、忽略环境中的代理设置、限制响应大小，并在日志中遮盖凭证。

**时间。** 空闲、心跳和凭证过期都使用单调时钟计时。即使墙上时钟向回跳（某些虚拟机上确实会发生），会话也不会因此多活或提前关闭。

**供应链。** CI 中用 `cargo deny` 审计依赖。

## 缺陷是如何发现的

项目为每一个修复过的缺陷都留有记录，包括它是怎么发现的、由哪个测试复现：[`docs/HARDENING.md`](https://github.com/AsyncNomad/wsPrism/blob/main/docs/HARDENING.md)。迄今为止的来源有：

- 每个里程碑前的**评审**，以及首个版本发布前的全面评审。
- 对所有处理不可信输入的解析器进行**模糊测试**。
- 杀节点、重启 Redis、切断网络、执行滚动升级的**混沌测试**。
- 配有逐条核对消息的判定器的**随机浸泡测试**。它发现了不少问题，其中包括：Redis 重启后，历史读取在已失效的套接字上失败；以及测试框架自身的一些缺陷，它们原本会把真实的丢失掩盖掉。
- **发布前的全面缺陷排查**：按风险从高到低通读代码，每个疑点都先用一个失败的测试确认，再动手修复。共找到五个缺陷：使用同一会话 ID 的并发连接可能全部存活（单节点和集群都有）；服务端 API 发布的 Hot 帧到不了其他节点上的成员；过期时间极远的令牌可能让握手 panic；SDK 可能永久丢弃一个在重新加入途中被打断的房间。

## 已知盲区

- 尚未进行外部安全审计。
- Fencing 只覆盖房间流量。被隔离节点的会话与成员关系写入不会被拒绝，而是在它停止后被清理。
- 浸泡测试在节点与 Redis 之间注入网络故障（延迟、黑洞、重置），但没有注入丢包、乱序或非对称分区，也没有在客户端与节点之间注入故障。
- Sentinel 主从切换单独测试，没有混入浸泡测试。
- 在极端负载下租户之间并未完全隔离：不会有租户被饿死，但一个租户的负载会推高另一个租户的延迟。请使用按租户的限流。
