# 常见问题与排错

## 连接

**浏览器在握手时收到 403。**
页面的 Origin 不在租户的 `policy.allowed_origins` 中。这个列表默认为空，也就是拒绝所有浏览器。请加入确切的 Origin（`https://app.example.com`，开发时可以是 `http://localhost:3000`），子域名可以用 `https://*.example.com` 一并放行。

**握手失败，返回 401。**
租户查找票据的所有位置都没有凭证，或者认证链拒绝了它。请确认客户端把票据放在了租户会去找的位置（`ticket_sources`，查询字符串默认是关闭的），并且认证链里有能处理这类票据的认证器。还要记住，一次性票据在首次出示时就会被消耗（失败的尝试也算），默认 30 秒过期。

**握手失败，返回 400。**
租户不存在；`sid` 不是 1 到 64 个 `[A-Za-z0-9_-]` 字符；或者客户端提供了子协议，但其中没有网关支持的版本（`wsprism.v2.json` 或 `wsprism.v1`）。

**客户端连接时收到 503。**
看一下 `Retry-After` 头和 `wsprism_handshake_rejections_total`。常见原因有：节点正在排空（换一个节点连接）；租户达到了 `max_sessions_total`；认证后端或 JWKS 端点不可达；或者在集群中 Redis 太慢，节点正在拒绝新连接（`cluster_busy`）。

**wsPrism 会终止 TLS 吗？**
不会。请把它放在负责终止 TLS 的负载均衡器或反向代理后面，并把该代理写进 `gateway.trusted_proxies`，让限流看到真实的客户端地址。在独立的负载均衡器上终止 TLS，网关的开销就和测量结果一致；若在同一台主机上放置代理，代理本身比网关还贵：前置 nginx 的 wsPrism，CPU 开销是 Centrifugo 自带 TLS 的 1.6 到 1.9 倍（见 [TLS](../project/benchmarks.md#tls)）。

## 消息

**请求返回 `NOT_ALLOWED`。**
可能是 `svc:type` 不在租户的 `ext_allowlist` 中，可能是用户权限不覆盖该房间，也可能是会话没有加入它要发消息的房间。具体是哪一种，看 `msg` 字段。

**房间消息正常收发，但我自己的服务收不到请求。**
服务必须既已注册（内置、`Gateway::builder` 注册，或 `rpc.allow` 路由），又在白名单里。白名单里写了不存在的服务，启动时就会失败；所以如果网关已经正常启动，请检查白名单。

**客户端因 `slow_consumer`（4101）被断开。**
有一条可靠消息放不进该客户端的发送队列。要么客户端读得太慢（后台标签页、性能较弱的设备、拥塞的网络），要么某个房间发布的可靠流量超出了客户端的消化能力。客户端会重连，并从最后的 offset 续收带历史的房间。如果频繁发生，请把高频数据挪到 Hot 通道，这样慢客户端拿到的是最新值，而不是一堆积压。只有在突发很短的情况下，才考虑调大 `session_queue_capacity`。

**为什么不像 Hot 通道那样，直接给慢客户端丢掉旧消息？**
因为 Ext 通道承诺的是"按序送达，或者明确告知送不到"。一条谁也不知道已经丢掉的聊天消息，比一次能把它找回来的重连糟糕得多。

**消息会按我发布的顺序到达吗？**
同一个房间内，所有成员看到的顺序相同。不同房间之间，以及后端向不同节点发布时的跨节点场景，没有全局顺序。见[投递语义](cluster.md#投递语义)。

**投递有保证吗？**
单条连接上是"至多一次"，在此之上叠加了恢复机制。带历史的房间允许重连的客户端补收错过的消息；做不到时，网关会明确告知（`recovered: false`、`sys.gap`）。绝对不能丢的数据，请以数据库为准，并把这些信号当作重新加载的提示。

## 集群

**在一个节点上发布的消息，另一个节点上的客户端收不到。**
确认所有节点都使用 `kind: redis`、相同的 `prefix` 和同一个 Redis。`wsprism_broker_failed_total` 统计的是被 Redis 拒绝的命令；不为零时，通常是缺了某项 ACL 权限。

**为什么所有带历史的房间都收到了带新 epoch 的 `sys.gap`？**
Redis 重启了、发生了主从切换，或者驱逐了网关的键。它的数据可能比客户端已经看到的更旧，网关宁可开启新的 epoch，也不冒复用 offset 的风险。设置 `maxmemory-policy noeviction` 可以排除驱逐这种可能。

**某个节点自己报错退出了。**
它与 Redis 断开的时间超过了 `slot_ttl_s`，期间另一个节点占用了它的槽位。继续运行就意味着以一个集群已经判定死亡的身份发布消息，所以它排空后停了下来。编排系统重启它之后，它会占用一个新的槽位。

**可以用 Redis Cluster、Valkey 或托管 Redis 吗？**
暂不支持 Redis Cluster。任何兼容 Redis 协议、支持 ACL 列表中的命令以及 Lua 脚本和 pub/sub、版本不低于 6.2 的服务都应该可以使用。测试环境用的是 Redis 7。

## 集成

**必须会 Rust 吗？**
不必。认证（票据、JWT、连接代理）、发布、踢下线、请求处理（RPC 代理）都通过 HTTP 完成，任何语言都可以。只有在网关内部运行的服务才需要 Rust。

**有没有 Socket.IO 或 Pusher 的兼容层？**
没有。客户端使用 wsPrism 协议。浏览器和 Node 用 JavaScript SDK；其他平台可以用任意 WebSocket 库实现，协议在[线路协议](../reference/protocol.md)中有完整定义。

**能不重启就修改配置吗？**
暂时不能。请重启节点；多节点时逐个重启。租户策略的热加载已在计划中。

**可以用于生产环境吗？**
单节点网关功能完整，经过模糊测试，并有约 270 个 Rust 测试以及 SDK 测试和混沌测试覆盖。集群在经过生产检验之前标记为实验性。目前还没有做过外部安全审计。请阅读[安全](../project/security.md)后自行判断。
