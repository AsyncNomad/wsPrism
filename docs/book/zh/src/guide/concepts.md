# 核心概念

本章介绍后文反复用到的术语。每个概念都不复杂，合在一起，基本就涵盖了网关所做的全部事情。

## 租户

租户是网关上一个相互隔离的使用方：可以是一个应用、一款游戏、一个团队，也可以是你自己 SaaS 产品里的一个客户。一套部署可以承载多个租户，每个租户各自拥有：

- **认证链**：谁可以连进来；
- **策略**：允许哪些消息、限流、会话规则、浏览器 Origin；
- **限额**：帧大小、会话数、房间数、每个房间的人数；
- 用于服务端 API 的 **API 密钥**，以及可选的通往后端的 **RPC 路由**和**历史消息规则**。

房间名、用户 ID 和会话 ID 都只在租户内部有效。两个租户都可以有名为 `lobby` 的房间和名为 `alice` 的用户，彼此毫不相干。

客户端在连接 URL 中指定租户（`/v1/ws?tenant=acme`）。租户不存在的话，在 WebSocket 升级之前就会被拒绝。

## 会话

会话就是一条通过了认证的连接，它带有：

- **用户 ID**，由认证器给出，为 1 到 64 个 `[A-Za-z0-9_-]` 字符；
- **会话 ID**（`sid`），客户端可以通过 `?sid=` 自行指定，这样重连时会顶替之前的连接，而不是算作第二条；
- 随凭证一起下发的**权限**（可以加入哪些房间、可以向哪些房间发布）；
- 一个有容量上限的**发送队列**。

一个用户同时能有几个会话、超出时是拒绝新会话还是关闭最早的那个，由租户的会话策略决定。在集群中，这些规则跨节点生效。

## 房间

房间是一组具名的会话。加入房间就会收到其中发布的所有消息，离开则不再接收。房间在有成员时存在，无需事先声明。

房间名是不含控制字符的 UTF-8，长度 1 到 128 字节。配置中的模式（`chat:*`）按前缀匹配，因此 `match:42`、`doc:7f3a` 这样的命名方式会很方便。

房间可以保留最近的消息作为**历史**，让重连的客户端补收断线期间错过的内容，详见[房间、在线状态与历史消息](rooms-and-history.md)。

## 两条通道

每条连接上都有两类流量。

| | Ext 通道 | Hot 通道 |
|---|---|---|
| WebSocket 帧 | 文本（JSON） | 二进制 |
| 寻址方式 | `svc` 和 `type` 名称 | 数字服务 ID 和操作码 |
| 投递语义 | 可靠，同一房间内有序 | 可丢弃：跟不上的接收方只拿最新值 |
| 典型用途 | 聊天、指令、房间管理、RPC | 坐标、光标、传感器读数、行情 |
| 是否进入历史 | 房间配置了历史规则则保留 | 从不保留 |

请求和响应都在 Ext 通道上。请求带上 `seq`，针对它的每一条响应都会在 `reply_to` 中带回同一个编号。

Hot 通道承载的是状态。Hot 帧可以带一个**键**；对每个接收方，网关按发送方和键只保留最新的一帧。于是，卡顿了一下的客户端会直接追上当前状态，而不是把过去的坐标一个个重放一遍。

## 服务

消息由服务处理。Ext 通道上的服务有名字（`room`、`chat` 或你自己的），Hot 通道上的服务有数字 ID（`1` 是内置的房间转发服务）。

房间和聊天由内置服务负责。添加自己的服务有三种方式，按投入从小到大排列：

1. 把 `svc:type` 模式通过 HTTP 路由到你的后端（**RPC 代理**），用什么语言都行；
2. 用 `Gateway::builder` 注册一个 Rust 服务；
3. （计划中）WebAssembly 插件。

无论哪种方式，租户的白名单里都必须列出对应的消息。注册服务让它"能处理"，白名单让它"被允许"。

## 服务端 API

服务端 API 是后端与网关通信的渠道：签发票据、向房间发布消息、踢用户下线、查询房间里有谁。它在单独的内部地址上监听，用按租户划分的 API 密钥认证。见[服务端 API](../reference/server-api.md)。

## Broker

Broker 负责在会话之间传递房间流量。单节点时它就是进程内存；多节点时它是 Redis：任何一个节点上发布的消息都会送达所有节点上的房间成员，会话和在线状态全局共享，历史消息存放在 Redis 中。无论哪种情况，客户端和后端看到的协议都完全一样。

## 投递等级

在内部，每一条出站消息要么是 **Reliable**，要么是 **Lossy**。

- Reliable 消息放不进某个接收方的队列时，该接收方会被当作*慢消费者*断开（关闭码 4101）。客户端重连后，如果是带历史的房间，会从断开处接着收。悄悄丢掉它，就违背了"Ext 消息按序送达"的承诺。
- Lossy 消息放不进时，只对那个接收方丢弃，并计入 `wsprism_egress_drop_total`。

正是这条规则让网关在过载时的行为可以预期：一个慢客户端拖不慢整个房间，也不会在不知情的情况下漏掉可靠数据。
