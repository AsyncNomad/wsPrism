# ADR 0007: P2 전송 — axum 0.8을 건너뛰고 서버 측 WebSocket 프레이밍을 직접 구현

- 상태: **채택 → 단계 1 기준 미달 (2026-10-16)**. 단계 2 진행 여부는 사용자 결정 대기. 기본 전송은 tungstenite 유지, `gateway.transport: raw`는 실험 옵션
- 관련: [성능 아키텍처](../design/performance-architecture.md) §3.5·§4, [ADR 0005](0005-session-transport-seam.md)(전송 경계), [BENCHMARKS](../BENCHMARKS.md) 「P1-a」 프로파일

## 배경

P1-a 이후 프로파일(rooms:120)에서 우리 자료구조는 약 11%로 줄었고, 남은 비용은 커널 송신 46%(netlab에서는 상대 수신 포함), tokio 런타임 15%, **WebSocket 프레이밍(tungstenite) 14%**, UTF-8 재검증 2.4%, split 소켓 BiLock 1.2%다. 유휴 연결 메모리 16.2 KB 중 **8 KB가 tungstenite 읽기 버퍼**(4 KB `Vec` + 4 KB 청크, 연결 내내 유지)다.

로드맵의 P2 1단계는 axum 0.8(tungstenite 0.26, `Bytes` 기반 메시지)이었다. 검토 결과 이 단계는 효과에 비해 맞지 않는다.

## 검토: axum 0.8

| 항목 | 판단 |
|---|---|
| 얻는 것 | 수신자별 복사·UTF-8 재검증 제거 — 프로파일상 최대 약 2~4%. 종단 간 CPU에서는 잡음(±10%)에 묻힐 가능성이 높다 |
| **위험** | 최신 tungstenite는 `read_buffer_size` 기본값 **128 KiB를 연결마다 미리 할당**한다(공식 문서: 연결이 많으면 4 KiB 같은 작은 값 권장). 그대로 올리면 **연결당 메모리 약 8배 회귀**. 4 KiB로 줄여도 지금(8 KB)과 비슷하다 |
| 이전 비용 | `Message` 타입 변경, `Serve::tcp_nodelay` 제거(`ListenerExt`로 대체), S2 크기 초과 판별용 tungstenite 직접 의존 버전 동기화 |
| 다음 단계와의 관계 | 자체 프레이밍은 hyper의 업그레이드로 소켓을 직접 받으면 되므로 axum 0.8이 **필요 없다**. axum 0.8 작업은 자체 프레이밍으로 가면 대부분 버려진다 |

→ axum 0.8은 건너뛴다.

## 결정 (제안)

업그레이드 핸드셰이크와 admission은 지금처럼 axum/hyper에 두고, **업그레이드된 TCP 소켓을 자체 서버 측 WebSocket 코덱이 맡는다.** `SessionTx`/`SessionRx`(ADR 0005)의 새 구현(`RawWsTx`/`RawWsRx`)으로 들어가므로 세션·정책·서비스 코드는 바뀌지 않는다.

1. **업그레이드**: `hyper::upgrade::on(req)` + `Sec-WebSocket-Accept` 계산(SHA-1 + base64, RFC 6455 §4.2.2). 서브프로토콜·admission은 기존 그대로.
2. **수신 (§4.1)**: 소켓 readiness(`readable()`) → **워커 스레드 공용 버퍼**로 `try_read` → 완성된 프레임을 그 자리에서 마스크 해제·디코드. 완성되지 않은 꼬리만 연결별 작은 버퍼로 옮긴다(대부분의 연결은 대부분의 시간에 0 B). 텍스트 프레임은 RFC대로 UTF-8 검증(조각 경계 포함), 크기 한도는 헤더 단계에서(S2와 같은 의미).
3. **송신 (§3.5)**: 서버 프레임은 마스킹하지 않으므로 **완성된 와이어 프레임(헤더+페이로드)을 발행 시 한 번 만들어** `Bytes`로 공유한다. 수신자 task는 큐에서 꺼낸 프레임들을 `writev` 한 번으로 쓴다(연결별 쓰기 버퍼 없음, 부분 쓰기는 오프셋만 기억). BiLock도 사라진다(읽기·쓰기 절반이 소켓을 직접 나눠 가짐: `TcpStream::into_split`).
4. **제어 프레임**: Ping에 자동 Pong(지금 tungstenite 동작과 동일), Close 핸드셰이크(C3 `close_session` 순서 유지), 조각 메시지 재조립(한도 내), 제어 프레임 끼어들기 허용.
5. **지원하지 않는 것**: permessage-deflate(협상하지 않음 — 지금과 같다), 클라이언트 역할.

## 기대 효과 (검증 전 상한)

- CPU: 프레이밍 14% + BiLock 1.2% + UTF-8 2.4% + 복사·할당 일부 → **최대 약 18%**.
- 메모리: tungstenite 읽기 버퍼 8 KB 제거 → **유휴 16.2 KB → 8 KB 이하**(설계 목표).
- 큰 룸 방송: 수신자당 인코딩·복사가 0 → 1,000명 룸에서 효과가 가장 크다.

## 위험과 검증

| 위험 | 대응 |
|---|---|
| RFC 6455 적합성(조각, 제어 프레임, 종료, UTF-8 경계) | **Autobahn 테스트 스위트**(서버 모드)를 통과 기준으로. Docker 이미지 또는 파이썬 패키지를 받아야 함(네트워크 — 착수 시 확인), 실행은 netlab/`--internal` 네트워크 안에서만 |
| 신뢰할 수 없는 입력 파서 | 퍼징 대상 추가(프레임 디코더, 조각 재조립, UTF-8 경계) |
| 회귀 | 기존 통합 테스트 105개 + A/B·프로파일·메모리 측정. tungstenite 구현(`WsTx`/`WsRx`)은 설정으로 고를 수 있게 한동안 남겨 비교·롤백 경로로 쓴다 |
| 유지보수 비용 | 서버 측만, 확장 없음으로 범위를 좁힌다(대략 1,000줄 + 테스트). 그래도 tungstenite보다 우리가 책임질 코드가 늘어난다 — 측정 이득(위 상한)이 실제로 나오는지 1단계 프로토타입으로 먼저 확인한다 |

## 단계

1. **프로토타입**(버림 가능): 송신 경로만(사전 인코딩 + `writev`) — 수신은 tungstenite 유지. A/B·프로파일로 프레이밍 범주가 실제로 줄어드는지 확인. 기준: 프로파일 프레이밍 범주 절반 이하, 종단 간 CPU가 잡음 범위를 넘어 개선.
2. 통과하면 수신(공용 버퍼) + 제어 프레임 + Autobahn + 퍼징.
3. 기본 전송으로 전환, tungstenite 경로는 한 릴리스 동안 옵션으로 유지 후 제거.

## 기각한 대안

| 대안 | 이유 |
|---|---|
| axum 0.8 먼저 | 위 「검토」 |
| fastwebsockets 등 다른 크레이트 | 사전 인코딩 프레임 공유·공용 읽기 버퍼를 직접 제어할 수 없으면 같은 한계. 의존성을 바꿔도 목표(연결당 상주 버퍼 0, 수신자당 인코딩 0)에 닿지 않는다 |
| 현재 유지 | 남은 비용의 큰 몫(프레이밍 14%, 읽기 버퍼 8 KB)이 그대로 남는다 |

## 단계 1 결과 (2026-10-16)

[BENCHMARKS](../BENCHMARKS.md) 「ADR 0007 단계 1」. 종단 간 CPU는 3~14% **나빠졌다**(1,000명 방송 룸에서 가장 크게). 프로파일상 겨냥한 비용(송신 프레이밍·UTF-8 재검증·BiLock, 약 8%p)은 줄었지만, axum 서버의 hyper-util 자동 감지가 업그레이드된 IO를 비공개 타입으로 감싸 `TcpStream`을 꺼내지 못했고, 대체 경로(`tokio::io::split` + `TokioIo<Upgraded>`)의 런타임 비용(+12.5%p)이 이득을 넘었다.

**배운 것**

- 64 B 수준의 작은 메시지에서는 페이로드 복사 자체보다 **IO 경로의 계층 수**가 더 비싸다. "복사 제거"는 큰 메시지(예: 수 KB 상태 스냅샷)에서 의미가 커진다.
- 남은 프레이밍 비용(9.1%)은 tungstenite **읽기** 쪽이다.
- 공정한 재시험에는 업그레이드 후 맨 `TcpStream`이 필요하다 → axum 대신 **HTTP/1 전용 accept 루프를 직접**(hyper `http1` + upgrade) 두면 비공개 래퍼가 없다(WebSocket 게이트웨이는 HTTP/2가 필요 없다). 이 경우의 상한도 CPU 약 8~10%로 크지 않다.
- 메모리 목표(유휴 16.2 → 8 KB 이하)는 송신 쪽이 아니라 **읽기 버퍼**(tungstenite 8 KB)에 달려 있어 단계 2(자체 읽기)가 필요하다.

**선택지** (사용자 결정)

| 안 | 내용 | 기대 | 비용 |
|---|---|---|---|
| A. 여기서 멈춤 | `raw` 실험 코드 제거, 결과만 기록 | — | 없음 |
| B. 공정 재시험 | HTTP/1 accept 루프로 맨 `TcpStream` 확보 후 단계 1 재측정 | CPU 최대 약 8~10% | 중간 (서버 루프·드레인·ConnectInfo 재구현) |
| C. 단계 2 직행 | 자체 읽기(공용 버퍼) + 제어 프레임 + Autobahn + 퍼징 | 유휴 메모리 약 절반, CPU 일부 | 큼 |
