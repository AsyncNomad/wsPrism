# ADR 0012: JWKS와 대역 내 토큰 갱신

- 상태: **채택 (2026-10-19)** — §1 JWKS 구현 ✅ — 외부 피드백(배포 전 검토) 반영, 사용자 승인("진행"). M3/M4(ADR 0011) 앞에 둔다
- 관련: [ADR 0008](0008-m2-lite-integration.md) §5(JWT), [ADR 0006](0006-protocol-v2.md)(종료 코드), [ADR 0011](0011-broker-history-and-cluster.md)(복구)

## 배경

- **JWKS 없음:** JWT 링크는 정적 키(PEM 파일, HMAC 비밀)만 받는다. Auth0·Cognito·Keycloak·Okta 같은 IdP는 키를 JWKS URL로 공개하고 주기적으로 교체하므로, 정적 키로는 사실상 연동할 수 없다(교체 때마다 설정 변경과 재기동이 필요).
- **토큰이 만료되면 세션이 닫힌다(4001).** IdP 액세스 토큰 수명은 보통 5~15분이라, 모든 사용자가 그 주기로 재접속한다. 재접속하면 연결·인증·룸 재입장 비용이 들고, 복구(ADR 0011 R2)가 생기기 전까지는 그 사이 메시지를 잃는다.
- jsonwebtoken 9.3에 JWK 지원(`jwk::JwkSet`, `DecodingKey::from_jwk`)이 있고, 백엔드 HTTP 클라이언트(`reqwest`)도 이미 있다 → **새 의존성 없음.**

## 결정

### 1. JWKS (`kind: jwt` + `jwks_url`)

```yaml
auth:
  - kind: jwt
    algorithm: RS256
    jwks_url: "https://idp.example.com/.well-known/jwks.json"
    jwks_refresh_s: 300        # 주기 갱신 (기본 300, 60-86400)
    issuer: "https://idp.example.com/"
    audience: "wsprism"
```

- 키 출처는 셋 중 정확히 하나다: `secret_file`/`secret_env`(HS*), `public_key_file`, `jwks_url`(HS*에는 쓸 수 없다 — 비대칭 키 전용).
- **키 선택은 토큰 헤더의 `kid`로 한다.** JWKS에서 `kid`가 일치하고, `alg`가 링크에 고정된 알고리즘과 같으며(JWK에 `alg`가 있으면 그것도 일치해야 함), `use`가 `sig`이거나 비어 있는 키만 쓴다. alg 혼동 방지 원칙(ADR 0008 §5)은 그대로다.
- **모르는 `kid`:** IdP가 키를 막 교체했을 수 있으므로 **즉시 한 번 다시 받는다.** 다만 다시 받기는 최소 간격(30초)으로 제한한다. 공격자가 아무 `kid`나 보내 IdP를 두드리게 만들 수 없게 하기 위해서다. 다시 받은 뒤에도 없으면 `NotMine`으로 넘긴다(다른 발급자 링크가 체인에 있을 수 있다).
- **주기 갱신은 백그라운드 task가 한다.** 실패하면 **마지막으로 성공한 키 집합을 계속 쓴다**(경고 로그). IdP가 잠깐 장애여도 인증이 멈추지 않는다.
- **기동:** 키는 **첫 사용 때** 받는다(구현 중 조정: `build()`는 동기 함수라 런타임 밖에서도 불리므로 거기서 네트워크를 쓰지 않는다). 키를 한 번도 못 받은 동안 그 링크는 `Unavailable`(503 + `Retry-After`)을 낸다. 기동이 IdP에 묶이지 않는다. `--check-config`는 URL 형식만 검사한다(네트워크 안 씀).
- **즉시 재조회 간격은 설정할 수 있다** `jwks_min_refetch_s`(기본 30, 1-3600). 구현 중 추가 — IdP마다 허용하는 조회 빈도가 다르고, 키 교체 직후 동작을 테스트하려면 짧게 둘 수 있어야 한다.
- **전송 보안:** `https`만 허용한다. 예외는 루프백(`127.0.0.1`·`localhost`·`::1`)으로, 테스트용이다. 리다이렉트를 따르지 않는 기존 HTTP 클라이언트를 재사용한다. 응답 크기 상한도 같다(1 MiB).

### 2. 대역 내 토큰 갱신 (`sys.refresh`)

- **클라이언트 → 게이트웨이:** `{"svc":"sys","type":"refresh","seq":n,"data":{"token":"<새 토큰>"}}`
- **게이트웨이 → 클라이언트:**
  - 성공: `{"svc":"sys","type":"refreshed","reply_to":n,"data":{"expires_in_s":900}}`
  - 실패: `sys.error AUTH_FAILED`(또는 인증 백엔드 장애 시 `UNAVAILABLE`). **세션은 그대로 두고**, 기존 만료 시각이 지나면 지금처럼 4001로 닫힌다.
- **검증:** 테넌트 인증 체인을 그대로 탄다(JWT·프록시·플러그인 모두). 처음 접속할 때와 같은 규칙이다.
  - **새 신원의 user id는 기존과 같아야 한다**(다르면 거절). 대역 안에서 다른 사람이 될 수는 없다.
  - **권한은 새 토큰의 것으로 바꾼다.** 줄어든 권한이 즉시 적용되어야 하기 때문이다. 이미 입장한 룸 중 새 구독 권한 밖인 룸에서는 내보내고 `sys.left`를 보낸다.
  - 만료 시각을 새 토큰의 것으로 갱신한다(스위퍼가 보는 `SessionSignals`의 원자 변수).
- **세션 루프를 막지 않는다:** 인증(특히 connect 프록시의 HTTP 호출)은 별도 task에서 하고, 결과는 세션 루프의 select 분기로 받는다. 세션당 진행 중인 갱신은 하나만 허용한다(두 번째는 `RATE_LIMITED`).
- **1회용 티켓은 갱신 대상이 아니다.** 티켓 신원에는 만료가 없다(`expires_at` 없음). 티켓으로 갱신을 요청해도 체인 규칙대로 처리되지만, 티켓 신원의 만료는 "없음"이 된다.
- **허용 목록과의 관계:** `sys.refresh`는 게이트웨이 자신의 제어 메시지라 테넌트 `ext_allowlist`를 거치지 않는다. 대신 연결별 rate limit은 똑같이 적용된다.
- **만료 시각 알림:** `sys.authed`와 `sys.refreshed`에 `expires_in_s`를 싣는다(만료가 있는 신원만). 클라이언트는 토큰을 해석하지 않고도 언제 갱신할지 안다. 1회용 티켓·불투명 토큰도 그대로 동작한다.

### 3. SDK

- `refresh` 옵션(기본 켜짐): `expires_in_s`의 80% 시점에 `getTicket()`으로 새 토큰을 받아 `sys.refresh`를 보낸다.
  - 실패하면 백오프로 다시 시도한다(만료 전까지).
  - 결국 만료되면 지금처럼 4001 → 새 자격 증명으로 재접속한다(안전망).
- 이벤트: `refreshed`, 실패는 `error`(`REFRESH_FAILED`).

## 기각한 대안

| 대안 | 이유 |
|---|---|
| 만료 직전 서버가 `sys.expiring`을 따로 푸시 | `expires_in_s`를 처음부터 알려 주면 클라이언트가 스스로 예약할 수 있다. 메시지가 하나 줄고 시계 오차에도 강하다 |
| 갱신 때 user 변경 허용(재로그인) | 세션 상태(룸·presence·member id)가 이전 사용자에 묶여 있다. 사용자 변경은 재접속으로 한다 |
| 갱신 실패 시 즉시 끊기 | 기존 토큰이 아직 유효하다. 일시적인 IdP·백엔드 장애로 연결을 끊을 이유가 없다 |
| JWKS 키를 매 검증마다 받기 | IdP 부하와 지연. 캐시 + 주기 갱신 + 모르는 `kid`일 때만(간격 제한) 즉시 갱신이 표준이다 |
| 기동 시 JWKS 실패하면 기동 중단 | 게이트웨이와 IdP가 같이 재시작될 때 서로 묶인다. 대신 그 링크만 503을 낸다 |
| HS*에 JWKS(`oct` 키) 허용 | 공유 비밀을 URL로 받는 것은 비밀의 의미와 맞지 않는다. HS*는 파일·환경 변수만 |

## 테스트 계획

- **JWKS:** 테스트용 로컬 HTTP 서버가 JWKS를 제공한다(RS256·EdDSA 키를 테스트 안에서 생성).
  - `kid`로 키 선택, 모르는 `kid` → 즉시 갱신 후 성공(키 교체 시나리오), 갱신 간격 제한(한 번만 다시 받음).
  - 주기 갱신에서 키 제거, 갱신 실패 시 마지막 키 유지.
  - 처음부터 못 받으면 503, `alg`가 다른 JWK 무시, `http` 비루프백 URL은 설정 오류.
- **갱신:** 만료가 가까운 JWT로 접속 → `sys.refresh` → 만료가 연장되어 4001 없이 유지.
  - user가 다른 토큰은 거절되고 세션은 유지.
  - 권한이 줄면 그 룸에서 내보내고 `sys.left`.
  - 동시 갱신 두 번째는 `RATE_LIMITED`.
  - 프록시 인증기가 느려도 세션의 다른 메시지는 계속 처리.
- **SDK:** 자동 갱신으로 수명 2초 토큰이 4001 없이 유지되는지, 갱신이 실패하면 재접속 안전망이 동작하는지.
