## 배경

목표(사용자 정의): **웹·게임 영역에서 기존 게이트웨이보다 훨씬 좋은 성능, 쉬운 커스텀, 대기업 수준의 안정성.** 특정 산업 특화는 목표가 아니다.

경쟁 지형 (구성 요소별):

| 구성 요소 | 이미 가진 곳 | 비고 |
|---|---|---|
| 브라우저 datagram 전송 | **Centrifugo**: WebTransport는 공식 문서상 *EXPERIMENTAL, not recommended for production*, **양방향 스트림 하나**로 프로토콜을 나른다(datagram 아님)([문서](https://centrifugal.dev/docs/transports/webtransport)). **Colyseus**: 실험 단계 H3 전송(datagram 여부 미확인). **lightyear·aeronet**: WebTransport datagram 지원, 단 **Bevy 엔진에 묶인 Rust 라이브러리** | 독립 게이트웨이 중에서는 비어 있음 |
| 키별 최신값(conflation) | **Sockudo**: "conflation key"는 문서상 델타 압축용 엔티티 묶음(오래된 값을 버리는 의미인지 미확인). **Ably**: 채널 단위 시간 창 conflation(SaaS) | 키별 "오래된 값 버리기" + datagram 결합은 찾지 못함. Ably의 상품화는 **수요 근거** |
| 틱 단위 송신 조절 | Colyseus(patchRate), lightyear(대역폭 상한·우선순위) | 게임 프레임워크엔 흔하고 독립 게이트웨이엔 드묾 |
| 멀티테넌트 정책 | **Sockudo**: 앱 단위 Origin·연결 한도·이벤트 한도(Origin 미설정 시 모두 허용) | wsPrism은 기본 거부 + 세션 정책까지 더 엄격 |
| WebTransport pub/sub 릴레이 | **MoQ**: IETF 표준화 중. moq-rs(Cloudflare 유지보수) 저장소는 `moq-relay-ietf`를 *"A production-ready relay server"* 로 소개한다([repo](https://github.com/cloudflare/moq-rs)). 한 업계 블로그는 파일럿 수준으로 평가한다. Cloudflare가 릴레이 생성 API를 제공([문서](https://4da580d2.previews.developers.cloudflare.com/moq/index.md)) | "WebTransport로 pub/sub"은 그 자체로 차별점이 아니다 |
| 게임 릴레이 | **Nakama relayed**: op code + 바이트 중계 | 현재 Hot Lane과 구조가 같다 |

그 밖의 사실:
- ROADMAP의 따라잡기 기능(프록시, 발행 API, 이력·복구, 멀티 노드)은 Centrifugo와 Sockudo가 이미 갖고 있다.
- 현재 Hot Lane은 **서버 큐에서만 손실 허용**이다. 전송이 TCP라 네트워크 손실 시 뒤의 프레임이 재전송을 기다린다.
- WebTransport는 Safari 26.4(2026-03)로 주요 브라우저 지원(2차 자료, 엔진별 인증서 처리 차이 지적 있음).
- Rust 서버 라이브러리: `wtransport` 0.7, `web-transport-quinn` 0.13 — 1.0 이전.

**결론**: 위 어느 제품도 "언어 무관 독립 게이트웨이 + 브라우저 datagram + 키별 최신값 + 멀티테넌트 정책" 조합을 갖고 있지 않다. 개별 요소는 모두 어딘가에 있으므로, **조합 + 언어 무관 + 측정된 수치**로만 주장할 수 있다.

## 결정

1. **간판은 "실시간 상태 동기화 의미론"이다.** 키별 최신값 유지(conflation), 틱 단위 송신 조절과 묶음 전송, 관심 영역 필터링(이후), 테넌트 정책, 백엔드 연동을 **가장 좋은 비신뢰 전송 위에서** 제공한다.
   - 전송: WebTransport datagram(직접 구현 **또는 MoQ 위/호환** — V에서 결정), 안 되면 WebSocket 폴백. 전송은 수단이며 같은 의미론이 WebSocket 위에서도 동작한다.
2. **포지션: "어느 언어로 짠 게임·실시간 서버든, 그 앞에서 브라우저 연결·정책·팬아웃·datagram을 떠맡는 사이드카."**
   - 클라이언트끼리 릴레이하는 모델(Nakama relayed)만으로는 치트를 막을 수 없어 상용 멀티플레이 쓰임새가 좁다. 그래서 **서버 피어 경로**를 둔다: 권위 게임 서버가 신뢰된 장기 연결로 붙어 룸의 Hot 프레임을 받고 룸에 발행한다(설계 §4.6). 엔진에 묶인 lightyear·aeronet과의 차별점이 여기서 선명해진다.
   - 권위 시뮬레이션 자체는 만들지 않는다(사용자의 게임 서버가 한다).
3. **대표 시나리오(검증과 첫 사용자)**: 모바일·Wi-Fi 환경의 **20~60 Hz 웹 멀티플레이 상태 동기화**.
4. **멀티테넌트 정책 엔진은 기반**이다(대기업급 안정성·운영의 핵심).
5. **따라잡기 기능은 "갈아탈 때 막히지 않을 만큼"만**.
6. **경계를 먼저 연다(T0).** 전송 능력, 세션당 두 채널, 전달 등급, Hot 슬롯을 M2 공개 트레이트 전에 WebSocket만으로 구현한다. 이 경계는 서버 피어 경로도 막지 않아야 한다(설계 §4.6).
7. 확정 전에 **검증 단계 V**를 둔다.

### 관문

**판정 칸(고정)**: 단방향 지연 20 ms(RTT 40 ms), 60 Hz 송신·60 Hz 렌더 표본, 대표 시나리오(10명 룸, 전원 발행). 손실은 **균등 1%와 링크 단절 둘 다** 통과해야 한다. 지연 0 ms는 참고값(대표 환경이 아니고 정지 시간이 짧아 노이즈에 좌우됨).

**측정 조건 (개정 3)**:
- **위상 무작위**: 클라이언트마다 송신·렌더 시작 위상을 한 주기 안에서 무작위로 둔다(시드 고정). 실제 클라이언트는 서로 위상이 맞지 않는다. 위상을 고정하면 AoI가 계단값이 되어 판정이 계단 위치에 좌우된다.
- **링크 단절**: 개정 2의 "버스트(Gilbert-Elliott, 평균 길이 4패킷)"는 veth 하나를 모든 연결이 공유해 연결마다 흩어졌고, 균등 손실과 결과가 같았다. 그래서 **양방향을 동시에 일정 시간 끊는** Wi-Fi형 단절로 바꾼다. 짧은 단절(평균 1초마다 50 ms)과 긴 단절(평균 5초마다 250 ms) 두 가지다.
- **끊김 기준 민감도**: 끊김 비율은 100 ms 기준으로 판정한다. 기준이 결과를 좌우하지 않는지 보려고 50~300 ms 비율도 함께 공개한다.
- **비용**: 오프로드를 끈 조건(손실 주입에 필요)과 켠 조건(실서버에 가까움) 둘 다 재고, G5는 **켠 조건**으로 판정한다.

**초과 AoI**: AoI에는 줄일 수 없는 바닥값(2구간 지연 + 송신 주기 톱니)이 있어 전체 AoI의 배수는 개선을 과소평가한다. 판정은 **같은 지연·같은 설정의 손실 0% AoI p99를 뺀 증가분**으로 한다. (스모크 측정, n=10 클라이언트·4초: 1%·20 ms에서 AoI p99는 WS 100 ms / WT 67 ms로 1.5배였지만, 0% 바닥값 약 57 ms를 빼면 43 ms / 10 ms로 4배 이상 — 판정 근거는 아니고 지표 정의를 바꾼 근거.)

| 관문 | 기준 |
|---|---|
| **G1 체감 성능** | 판정 칸에서 비신뢰 전송의 **초과 AoI p99가 WSS 대비 1/3 이하**이고 **끊김 비율(AoI > 100 ms인 틱의 비율)도 WSS의 1/3 이하**. 손실 0% 대조군에서 **WSS보다 나쁘지 않다**(AoI p50·p99 10% 이내). 메시지당 지연은 보조(생존 편향) |
| **G2 호환성** | Chrome, Firefox, Safari에서 연결·datagram 송수신 성공 |
| **G3 안정성** | 1,000 세션 1시간 부하에서 패닉 0, 워밍업 후 RSS 증가 < 10% |
| **G4 폴백** | UDP 차단 시 클라이언트가 2초 안에 WebSocket으로 전환 |
| **G5 비용** | 같은 팬아웃에서 **메시지당 CPU와 연결당 메모리가 WSS(게이트웨이 TLS) 대비 2배 이내**. LB TLS 종단 WS와의 차이도 공개 |

**G1과 G5는 같은 설정에서 판정한다.** 틱 묶음 전송은 패킷 수를 줄여 비용을 낮추지만 최대 한 틱의 지연을 더한다. 그래서 틱 주기 {즉시, 60 Hz, 30 Hz}마다 (초과 AoI p99, 끊김 비율, CPU/메시지, 메모리/연결)을 같은 실행에서 측정하고, **G1과 G5를 동시에 만족하는 틱 설정이 하나라도 있으면** 통과다. 각 전송은 자기에게 가장 좋은 틱으로 비교한다(WSS도 묶음 이득을 받는다).

### G1 단절 기준 (개정 4, 확인 측정 전 사전 등록)

**배경**: 개정 3의 G1 기준("초과 AoI p99가 WSS의 1/3 이하")을 단절 칸에 적용하면 시드 1~3 측정(`v2-judgment.jsonl`)에서 실패했다. 그런데 이 기준은 **단절 칸이 생기기 전(개정 2)에 정한 것**이고, 길이 L인 단절에서는 링크가 끊긴 동안 아무것도 도착하지 않으므로 L이 어떤 전송도 넘을 수 없는 초과 AoI의 바닥이 된다. 그래서 WSS의 초과분이 3L 이상이 아니면 **어떤 전송도 만족할 수 없다.** 결과를 본 뒤 정의한 "단절 후 추가 지연"은 이를 보정하지만 사후 지표라 그대로 쓸 수 없다. 그래서 지표를 지금 고정하고, 탐색에 쓰지 않은 시드로 다시 잰다.

**기준** (단절 칸마다, 같은 틱의 WT 대 WSS, 3회 중앙값):

| 항목 | 정의 / 통과 조건 |
|---|---|
| 복구 지연 | `max(0, 초과 AoI p99 − L)` — 링크가 돌아온 뒤 전송이 더하는 지연. **WT ≤ WSS의 1/3** 이고 **WSS − WT ≥ 16.7 ms**(60 Hz 한 프레임, 체감 가능한 최소 크기) |
| 끊김 비율 | **L < 100 ms인 칸에서만** WT ≤ WSS의 1/3. L ≥ 100 ms면 단절 동안 AoI가 100 ms를 넘는 것이 물리적으로 불가피하므로 공개만 한다 |
| 0% 대조군 | 같은 시드의 손실 없음 실행에서 WT AoI p50·p99가 WSS의 10% 이내 |

- **칸**: 단절 {평균 1초마다 50 ms, 평균 5초마다 250 ms} × 틱 {즉시, 60 Hz} × {WSS, WT} + 같은 시드의 손실 없음 기준. 단방향 20 ms, 60 Hz, 10×10, 측정 20초.
- **시드**: 4, 5, 6(`FIRST_RUN=4`). 시드 1~3은 탐색 데이터라 판정에 쓰지 않는다.
- **균등 1% 칸**은 개정 2 기준을 그대로 쓰고 기존 측정(`v2-judgment.jsonl`, 즉시·60 Hz 모두 통과)을 쓴다.
- **G1 통과**: 틱 {즉시, 60 Hz} 중 하나에서 균등 칸과 두 단절 칸이 모두 통과.
- **명령**(고정): `FIRST_RUN=4 bench/run-v.sh v2-confirm 3 "none:20 outage:1000:50:20 outage:5000:250:20" "0 60" "wss wt" "--rooms 10 --room-size 10 --rate 60 --sample-hz 60 --warmup 3 --duration 20"` → `python3 bench/analyze-g1-confirm.py bench/results/v2-confirm.jsonl`
- **사전에 밝혀 둘 것**: 탐색 데이터(시드 1~3)에 이 기준을 적용하면 통과한다(분석 코드 검증용으로 확인함). 여유가 가장 작은 곳은 **60 Hz 틱·50 ms 단절의 끊김 비율**(WT 4.96% vs 기준 5.43%)이라 확인 측정에서 실패할 수 있다.
- **이 기준은 확인 결과를 본 뒤 고치지 않는다.** 실패하면 G1 실패로 기록하고 결정 분기를 따른다. 기준을 바꾸려면 새 개정과 새 시드의 측정이 필요하다.

**확인 측정 결과 (2026-10-16, `v2-confirm.jsonl`, 36회)**: **G1 통과** — 즉시·60 Hz 두 틱 모두 모든 칸 통과. 링크 복구 후 추가 지연 WSS 107~156 ms / WT 0~19 ms, 50 ms 단절 끊김 13.5~16.0% / 3.0~4.7%(60 Hz 기준 5.34% 안). 개정 3 기준으로는 단절 칸 실패(1.6~2.5×)이며 함께 공개한다 ([BENCHMARKS](../BENCHMARKS.md) 「G1 확인 측정」).

## 기각·보류한 대안

| 대안 | 판단 |
|---|---|
| 정책 중심 멀티테넌트 엣지를 간판으로 | 기각 — Sockudo가 같은 자리. **G1 실패 시** 재검토 |
| Centrifugo 기능 폭 전체 따라잡기 | 기각 — 동등해질 뿐, 같은 언어 사이에서 "훨씬 빠름"의 구조적 근거가 없다 |
| 게임 백엔드(Nakama·Colyseus 계열) | 기각 — 범위가 크고 성숙한 제품이 있다. 대신 **서버 피어 경로**로 권위 서버의 앞단이 된다 |
| 엔진 통합 라이브러리(lightyear·aeronet 계열) | 기각 — 특정 엔진·언어에 묶인다. 언어 무관 사이드카가 차별점 |
| gRPC 양방향 ↔ 브라우저 브리지 | 기각 — 기존 자산과 연결이 약하고 시장 공백 미검증 |
| WebRTC DataChannel로 브라우저 UDP | 기각 — 운영 복잡도. geckos.io는 비교 대상으로만 |
| **MoQ 위에 구축** | **기각 (V6 실측).** `moq-relay-ietf` 0.7.29: 이득은 직접 구현 WT와 같고(같은 datagram 물리), 비용은 같은 세션 WSS 대비 CPU 2.7~3.3×, 한계 메모리 약 16×. 발행자가 비정상 종료(모바일 망 전환)하면 죽은 세션이 유휴 타임아웃까지 네임스페이스를 쥐어 재발행이 거절되고 **10초 넘게 정지**. 크레이트 분기·개명으로 생태계가 아직 움직인다 ([BENCHMARKS](../BENCHMARKS.md) 「V6」) |
| **MoQ 릴레이와 정면 경쟁** | **기각.** 전송 이득이 같은 물리에서 오므로 차별점이 아니다. 차별점은 상태 동기화 의미론·서버 피어·정책·운영에서 만든다 |
| **MoQ 호환(와이어 수준)** | **보류 — T 이후 재검토.** 초안 안정화를 기다린다. `SessionIo` 경계가 이를 막지 않게 한다 |
| "브라우저 UDP"를 간판으로 (초안) | 개정 1에서 철회 |

## 결과

- ROADMAP: **V → T0(경계, WebSocket만) → M2-lite → T(비신뢰 전송 + 서버 피어) → M3/M4(동등 수준)**.
- **하이브리드 분기의 구체화 (개정 4 결과)**: 전송 선택은 **룸 정책**이다(`policy.hot_transport: auto | websocket`, 이름은 T에서 확정). 근거: WT의 이득은 손실 환경의 소규모 인터랙티브 룸에서 크고, 비용은 연결당 메모리(약 2.8×)와 수신자별 패킷 비용이라 대규모 방송 룸에서 가장 크다. T0의 `SessionIo`·전달 등급 경계는 한 룸 안에 WT와 WS 세션이 섞여도 같은 서비스 코드가 동작해야 한다는 요건을 그대로 유지한다.
- **경쟁 비교에서 나온 사실 (2026-10-16)**: WebSocket 경로에서 wsPrism은 연결당 메모리가 가장 적지만(Centrifugo 대비 1.4~3.6×, Sockudo 대비 9~14× 적음), 전달당 CPU 우위는 1.07~1.25×로 작고, **8코어 포화점은 Centrifugo가 더 높다**(216만 전달/s에서 wsPrism 전달률 0.65~0.86, Centrifugo 1.0). wsPrism의 전달당 CPU는 부하와 무관하게 일정해 쓰기 묶음이 없는 것으로 추정된다 → T0의 틱 묶음·쓰기 합치기 후 같은 시나리오로 재측정한다.
- **V에 추가 (개정 3)**: 경쟁 게이트웨이(Centrifugo, Sockudo)와 **WebSocket 경로 직접 비교**. 목표("기존 게이트웨이보다 훨씬 좋은 성능")를 직접 재는 실험인데 그동안 없었다. netlab 안에서만 한다.
- **서버 피어 멤버 지정 송신 (개정 3)**: 서버 피어가 룸 전체가 아니라 **특정 멤버(들)에게** 보낼 수 있어야 한다. 그래야 권위 서버가 관심 영역 필터링(벽 너머 정보 숨기기)을 할 수 있고, 서버 피어를 둔 이유(치트 방지)가 성립한다. Hot 슬롯은 이미 수신 세션마다 있어 수신자별 값과 맞는다. 필요한 것은 대상 타입이고, 코어 전달 API를 `Audience`(룸·멤버 지정·세션·사용자) 하나로 모으는 것을 **T0 완료 조건**에 넣었다(설계 §4.6).
- 비교 대상: Sockudo, Centrifugo, MoQ(moq-rs / Cloudflare), Nakama relayed, Colyseus, lightyear·aeronet, geckos.io. Ably는 수요 근거.
- **프로토콜 변경 예고**: 비신뢰 전송의 Hot 프레임 크기 상한(기본 1,100 B). WebSocket에도 같은 상한. T에서 PROTOCOL.md에 명시.
- WebTransport는 브라우저가 헤더를 붙일 수 없어 **1회용 단기 티켓**(URL) → M2-lite에 티켓 발급 API.
- 현재 Hot Lane의 한계를 PROTOCOL.md에 명시했다.
