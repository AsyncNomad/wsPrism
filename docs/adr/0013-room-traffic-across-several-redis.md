# ADR 0013: 룸 트래픽을 여러 Redis에 나누기 (이력 처리량 확장)

- 상태: **제안 (2026-10-22)** — 사용자 승인 전. 구현하지 않았다.
- 관련: [ADR 0011](0011-broker-history-and-cluster.md) (Broker·이력·클러스터), BENCHMARKS 「M5」「0.1.x: 클러스터 대 Centrifugo Redis 엔진」「0.2: Redis 펜싱 비용」

## 문제

지금의 클러스터는 고가용성과 제한적 확장이다. 노드는 늘릴 수 있지만 모든 룸의 트래픽이 Redis 하나를 지난다.

- **이력 룸:** Redis 한 코어가 천장이다. 약 14~15만 메시지/s(200 B)이고, 그 위에서는 전달률이 떨어진다(rooms:240 이력: 0.58~0.60). 노드를 늘려도 그대로다(2노드 측정).
- **이력 없는 룸:** 펜싱 이후 Redis가 발행 1건에 약 2.5 µs를 쓴다. 클러스터 전체로 약 60만 발행/s이고, 구독 노드가 많을수록 더 적다.
- 비교: Centrifugo도 같은 Redis 하나에서는 비슷하게 묶인다(이력 처리량은 wsPrism이 1.5~1.7배). 다만 Centrifugo는 Redis Cluster·샤딩을 지원해 그 이상으로 갈 수 있다.

## 결정 (제안)

**룸 단위 트래픽(룸 pub/sub, 룸 이력)을 Redis "샤드" N개에 나눈다. 나머지(세션 표, presence, 노드 등록·슬롯, 1회용 티켓)는 "제어" Redis 하나에 그대로 둔다.**

### 무엇이 어디로

| 데이터 | 위치 | 이유 |
|---|---|---|
| 룸 채널 `<p>:r:{room}`, 이력 `<p>:h:{room}:st/log` | 룸 키의 샤드 | 처리량의 대부분. 룸끼리 독립 |
| 세션 표 `us:{user}`, presence `pr:{room}`·`nr:<node>`, `nodes`·`noderid`, 노드 슬롯 `slot:<n>`, 티켓 `kv:*` | 제어 Redis | 스크립트들(`CLAIM`·`OF_USER`·`MEMBERS`)이 노드 슬롯 키를 함께 읽는다. 쓰기량이 룸 트래픽보다 훨씬 적다 |
| 펜싱용 슬롯 사본 `slot:<n>` | 각 샤드에도 | 샤드의 스크립트는 다른 Redis의 키를 읽을 수 없다. 노드가 슬롯을 얻을 때와 heartbeat 때 모든 샤드에 같은 값·TTL로 쓴다. 판단의 기준은 제어 Redis다 |

### 룸 → 샤드

- 샤드는 이름이 있는 목록으로 설정한다: `gateway.broker.shards: [{ name, url / url_env / sentinel, tls }]`. 샤드마다 Sentinel·TLS를 따로 둘 수 있다(지금의 `link.rs` 경계를 샤드마다 하나씩).
- 룸 키에서 샤드를 고르는 방법은 이름 기준 rendezvous(HRW) 해시다. 목록 순서를 바꿔도 결과가 같고, 샤드를 하나 더하면 약 1/N의 룸만 옮겨진다.
- **모든 노드가 같은 샤드 목록을 써야 한다.** 다르면 한 룸이 두 Redis로 갈라진다. 그래서 노드는 시작할 때 이름 목록의 지문을 제어 Redis에 `SET NX`로 남기고, 다르면 시작을 거부한다.
- 샤드를 바꾸려면(추가·제거) 모든 노드를 같은 설정으로 다시 띄운다. 옮겨진 룸은 새 샤드에서 새 epoch로 시작한다(클라이언트는 알림을 받고 다시 동기화한다. 지금의 "Redis 재시작"과 같은 의미다). 온라인 이전은 하지 않는다.

### 노드 안에서 바뀌는 것

- **송신:** 송신 큐의 묶음을 샤드별로 나눠 샤드마다 파이프라인 하나씩 **동시에** 보낸다. 지금도 한 번에 한 묶음씩 처리하므로, 샤드 수만큼 송신 처리량이 는다.
- **구독:** 샤드마다 구독 연결 묶음(`pubsub_connections`)을 둔다. 수신 분배(코어별 작업 task)는 그대로다.
- **이력 읽기·갭 메우기:** 룸의 샤드로 보낸다.
- **`run_id` 검사:** 이력 상태가 샤드마다 있으니 샤드별로 그대로 동작한다. 제어 Redis의 `run_id`는 등록에만 쓴다.
- **단일 Redis 설정은 그대로 동작한다**(샤드 1개 = 제어 Redis와 같은 곳). 설정과 코드는 "샤드 목록이 비어 있으면 제어 Redis를 유일한 샤드로 쓴다"로 통일한다.

### 기대 효과와 측정 계획

- 이력 처리량은 샤드 수에 거의 비례할 것으로 본다(룸이 고르게 퍼질 때).
- 측정: `run-cluster.sh`에 샤드 2개(코어 22, 23)를 둔다.
  - rooms:240 이력: 지금 0.58~0.60 → 1.0에 가까워지는지 본다.
  - rooms:120 이력: p50이 내려가는지 본다.
  - 샤드 1개와 같은 세션 A/B로 잰다.
- 정확성: 카오스·soak에 "샤드 하나만 재시작·정지" 장애를 더한다. 그 샤드의 룸만 새 epoch·gap이 나고, 다른 샤드의 룸은 영향이 없어야 한다.

## 기각한 대안

1. **Redis Cluster를 그대로 지원.** 키는 이미 룸별 해시 태그라 룸 데이터는 맞는다. 하지만 막히는 곳이 있다.
   - `CLAIM`·`OF_USER`·`MEMBERS`가 인자로 받은 접두사로 다른 슬롯의 노드 슬롯 키를 읽는다. Redis Cluster는 스크립트의 교차 슬롯 접근을 막는다.
   - 펜싱도 이력 스크립트가 룸 키와 노드 슬롯 키를 함께 쓴다.
   - pub/sub는 샤드 pub/sub(`SPUBLISH`, Redis 7)로 바꿔야 한다.
   - 클러스터용 클라이언트와 슬롯 재배치 처리도 들어간다.
   - 결론: 스크립트 설계부터 바꿔야 해서 이번 범위를 넘는다. 이 ADR의 "제어 + 룸 샤드" 분리는 나중에 Redis Cluster로 갈 때도 룸 쪽을 그대로 옮길 수 있게 한다.
2. **테넌트별 Redis.** 간단하지만, 가장 큰 테넌트 하나가 여전히 한 코어에 묶인다.
3. **이력 저장 구조 변경(Streams 등, M5 시제품).** 코어당 약 1.3배라 배수 확장이 아니다. 샤딩 뒤에도 코어당 효율이 필요해지면 다시 본다.
4. **샤드 목록 온라인 변경(룸 이전).** 이전 중의 순서·중복 처리가 복잡하다. 재시작 + 새 epoch로 충분히 안전하고, 운영자는 미리 알 수 있다.

## 위험과 미해결

- 샤드 하나가 내려가면 그 샤드의 룸만 멈춘다(지금은 전부가 멈춘다). 그 대신 장애 지점이 늘어난다.
- 제어 Redis는 여전히 하나다. 세션·presence 쓰기량이 한계에 가까워지면 이것도 나눠야 한다(사용자 키 기준). 아직 측정상 문제는 없다.
- 노드마다 샤드 수 × 연결이 늘어난다(샤드당 명령·발행·구독 4개 등).
- 이 기계에서는 Redis 두 개 + 노드 + 부하 생성기를 모두 같은 장치에 둬야 해서, 측정이 코어 수에 묶인다(샤드 2개가 한계).

## 검토 요청

1. "제어 Redis + 룸 샤드" 분리로 갈지, Redis Cluster 지원을 먼저 할지.
2. 샤드 변경 = 전체 재시작 + 옮겨진 룸의 새 epoch 정책이 운영상 받아들여지는지.
3. 측정을 같은 장치의 샤드 2개로 할지(이 기계의 한계), 아니면 클라우드 VM 측정을 함께 할지(로컬 원칙과 부딪힘).
