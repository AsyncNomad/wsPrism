# ADR 0013: 룸 트래픽을 여러 Redis에 나누기 (이력 처리량 확장)

- 상태: **제안, 개정 1 (2026-10-22)** — 사용자 승인 전. 구현하지 않았다.
- 개정 1: 외부 검토 #2를 반영했다. 샤드 고르기를 이름 기준 HRW에서 "논리 슬롯 16384개 + 슬롯 범위 표"로 바꿨다. 펜싱 사본을 세대 번호로 단조 증가하게 했다. 제어 Redis의 한계·presence 용량 측정·재시작 절차·Sentinel+TLS 필요·측정으로 주장할 수 있는 범위를 더했다. 바꾸기 전의 설계와 기각 이유는 「기각한 대안」 5·6에 남겼다.
- 관련: [ADR 0011](0011-broker-history-and-cluster.md) (Broker·이력·클러스터), BENCHMARKS 「M5」「0.1.x: 클러스터 대 Centrifugo Redis 엔진」「0.2: Redis 펜싱 비용」

## 문제

지금의 클러스터는 고가용성과 제한적 확장이다. 노드는 늘릴 수 있지만 모든 룸의 트래픽이 Redis 하나를 지난다.

- **이력 룸:** Redis 한 코어가 천장이다. 약 14~15만 메시지/s(200 B)이고, 그 위에서는 전달률이 떨어진다(rooms:240 이력: 0.58~0.60). 노드를 늘려도 그대로다(2노드 측정).
- **이력 없는 룸:** 펜싱 이후 Redis가 발행 1건에 약 2.5 µs를 쓴다. 클러스터 전체로 약 60만 발행/s이고, 구독 노드가 많을수록 더 적다.
- 비교: Centrifugo도 같은 Redis 하나에서는 비슷하게 묶인다(이력 처리량은 wsPrism이 1.5~1.7배). 다만 Centrifugo는 Redis Cluster·샤딩을 지원해 그 이상으로 갈 수 있다.

## 결정 (제안)

**룸 단위 트래픽(룸 pub/sub, 룸 이력)을 Redis "샤드" N개에 나눈다. 나머지(세션 표, presence, 노드 등록·슬롯, 1회용 티켓)는 "제어" Redis 하나에 그대로 둔다.**

### 무엇이 어디로

| 데이터 | 위치 | 이유 |
|---|---|---|
| 룸 채널 `<p>:r:{room}`, 이력 `<p>:h:{room}:st/log` | 룸 키의 샤드 | 처리량의 대부분. 룸끼리 독립 |
| 세션 표 `us:{user}`, presence `pr:{room}`·`nr:<node>`, `nodes`·`noderid`, 노드 슬롯 `slot:<n>`, 티켓 `kv:*` | 제어 Redis | 스크립트들(`CLAIM`·`OF_USER`·`MEMBERS`)이 노드 슬롯 키를 함께 읽는다. 쓰기량이 룸 트래픽보다 훨씬 적다 |
| 펜싱용 슬롯 사본 `slot:<n>` | 각 샤드에도 | 샤드의 스크립트는 다른 Redis의 키를 읽을 수 없다. 노드가 슬롯을 얻을 때와 heartbeat 때 모든 샤드에 같은 값·TTL로 쓴다. 판단의 기준은 제어 Redis다 |

### 룸 → 샤드

- 샤드는 이름이 있는 목록으로 설정한다: `gateway.broker.shards: [{ name, url / url_env / sentinel, tls }]`. 샤드마다 Sentinel·TLS를 따로 둘 수 있다(지금의 `link.rs` 경계를 샤드마다 하나씩).
- **룸 → 논리 슬롯:** `CRC16(해시 태그) mod 16384`. 해시 태그는 지금 키에 이미 있는 `{tenant::room}`이다. Redis Cluster와 같은 함수·같은 슬롯 수라서, 나중에 Redis Cluster로 옮기거나 슬롯 단위로 옮길 때 룸이 어느 슬롯인지 바뀌지 않는다.
- **논리 슬롯 → 샤드:** 슬롯 범위 표(`0-8191 → a`, `8192-16383 → b`). 설정에 범위를 쓰지 않으면 샤드 수로 고르게 나눈다.
- **표는 제어 Redis에 세대 번호와 함께 둔다**(`<p>:shardmap` = `{gen, ranges}`). 노드는 시작할 때 설정에서 만든 표를 비교한다.
  - 같으면 그대로 쓴다.
  - 표가 없으면 gen 1로 쓴다(`SET NX`).
  - 다르면 시작을 거부한다(오류에 두 표의 차이를 적는다). 한 룸이 두 Redis로 갈라지는 것을 막는다.
- 표를 바꾸려면(샤드 추가·제거·범위 이동) 아래 「재시작 절차」를 따른다. 옮겨진 슬롯의 룸은 새 샤드에서 새 epoch로 시작한다(클라이언트는 알림을 받고 다시 동기화한다. 지금의 "Redis 재시작"과 같은 의미다). 온라인 이전은 하지 않는다. 다만 슬롯 범위 표라서 나중에 슬롯 하나씩 옮기는 온라인 이전을 더할 여지가 있다.

### 펜싱 사본은 세대 번호로

- 샤드의 스크립트는 제어 Redis의 노드 슬롯 키를 읽을 수 없다. 그래서 노드는 슬롯을 얻을 때와 heartbeat 때마다 모든 샤드에 사본을 쓴다.
- 사본 값은 `node id`에 **슬롯 세대 번호**를 더한 것이다. 세대 번호는 제어 Redis에서 그 슬롯을 새로 얻을 때마다 `INCR`로 받는다.
- 샤드에 쓰는 스크립트는 저장된 세대보다 작은 세대의 쓰기를 거부한다(단조 증가). 그래서 늦게 도착한 옛 소유자의 heartbeat가 새 소유자의 사본을 덮지 못한다. 단순히 값을 복사하면 이 순서 역전을 막을 수 없다.
- 판단의 기준은 제어 Redis다. 샤드 사본은 발행을 막는 데만 쓴다. 한 샤드에 사본 쓰기가 실패한 노드는 그 샤드에 발행하지 않는다(그 샤드의 룸만 `UNAVAILABLE`).

### 재시작 절차와 운영 제약

- 표를 바꾸는 절차:
  1. 모든 노드를 drain해서 멈춘다.
  2. 운영 도구(`wsprism-gateway shardmap set`, 구현 예정)로 제어 Redis의 표를 새 gen으로 바꾼다.
  3. 새 설정으로 노드를 띄운다.
- 이 동안 서비스가 멈춘다. 이것은 **정비 시간이 필요한 작업**이고, 문서에 그렇게 적는다.
- 순서대로 하나씩 재시작하는 무중단 변경은 하지 않는다. 옛 표와 새 표의 노드가 섞이면 한 룸이 갈라진다. 위의 표 비교 검사가 이 경우 새 노드의 시작을 거부한다.
- 샤드 하나만 재시작하는 것은 표 변경이 아니다. 노드를 멈출 필요가 없고, 그 샤드의 룸만 새 epoch가 된다.

### 노드 안에서 바뀌는 것

- **송신:** 송신 큐의 묶음을 샤드별로 나눠 샤드마다 파이프라인 하나씩 **동시에** 보낸다. 지금도 한 번에 한 묶음씩 처리하므로, 샤드 수만큼 송신 처리량이 는다.
- **구독:** 샤드마다 구독 연결 묶음(`pubsub_connections`)을 둔다. 수신 분배(코어별 작업 task)는 그대로다.
- **이력 읽기·갭 메우기:** 룸의 샤드로 보낸다.
- **`run_id` 검사:** 이력 상태가 샤드마다 있으니 샤드별로 그대로 동작한다. 제어 Redis의 `run_id`는 등록에만 쓴다.
- **단일 Redis 설정은 그대로 동작한다**(샤드 1개 = 제어 Redis와 같은 곳). 설정과 코드는 "샤드 목록이 비어 있으면 제어 Redis를 유일한 샤드로 쓴다"로 통일한다.

### 기대 효과와 측정 계획

- 이력 처리량은 샤드 수에 거의 비례할 것으로 **기대한다**(룸이 고르게 퍼질 때). 이것은 가설이다.
- 측정: `run-cluster.sh`에 샤드 2개(코어 22, 23)를 둔다.
  - rooms:240 이력: 지금 0.58~0.60 → 1.0에 가까워지는지 본다.
  - rooms:120 이력: p50이 내려가는지 본다.
  - 샤드 1개와 같은 세션 A/B로 잰다.
- 정확성: 카오스·soak에 "샤드 하나만 재시작·정지" 장애를 더한다. 그 샤드의 룸만 새 epoch·gap이 나고, 다른 샤드의 룸은 영향이 없어야 한다.
- **제어 Redis 용량을 먼저 잰다(구현 전).** 룸 트래픽을 빼도 join·leave는 제어 Redis에 presence와 세션을 쓴다. 다음을 잰다:
  - 접속 폭주(초당 접속·join 수)에서 제어 Redis 코어 사용률이 얼마인지.
  - 이것이 샤드로 늘린 발행 처리량보다 먼저 천장이 되는지.

  천장이 먼저 오면 이 ADR의 효과가 작다. 그러면 presence를 룸 샤드로 옮기는 안을 먼저 검토한다.

  **측정 결과(2026-10-22, BENCHMARKS 「0.2: 세션 churn과 제어 Redis 용량」):**
  - 세션 하나(join 1개)에 제어 Redis CPU 약 16 µs가 든다. join 5개면 약 40 µs다.
  - Redis 한 코어로 초당 약 6만 세션(join 5개면 2만 5천)이다. 노드 하나는 초당 약 3만 세션을 처리하므로, 노드 2개분의 폭주에서 제어 Redis가 천장이 된다.
  - 이 측정이 먼저 드러낸 것은 노드 쪽 결함(구독 직렬화, 노드당 초당 3,600 세션)이었다. 이것을 고쳐서 위 값이 나왔다.
  - 판단:
    - 발행 처리량을 위한 룸 샤딩은 여전히 유효하다. 이력 룸은 Redis 한 코어로 약 14만 메시지/s이고, 제어 쓰기와 독립이다.
    - 다만 "노드를 늘리면 접속도 는다"는 말은 제어 Redis 하나로 막힌다. 접속 폭주 용량이 요구되면, 세션 표·presence를 사용자·룸 키로 나누는 것이 다음 단계다.
    - 이 측정은 연결이 머물지 않는 최악의 경우다. 실제 운영의 접속 빈도로 환산한 용량은 배포마다 다르다.
- **이 기계의 측정으로 말할 수 있는 범위:**
  - 같은 장치의 샤드 2개는 "Redis CPU 부하가 샤드별로 나뉜다"는 것만 보여 준다.
  - 노드·부하 생성기·Redis가 같은 코어를 나눠 쓰므로, 처리량이 샤드 수에 선형으로 는다는 주장은 하지 않는다.
  - 선형 확장은 Redis마다 장치를 따로 둔 측정(클라우드 VM)으로만 주장한다. 그 측정은 로컬 원칙의 예외라 사용자 승인이 필요하다.

## 기각한 대안

1. **Redis Cluster를 그대로 지원.** 키는 이미 룸별 해시 태그라 룸 데이터는 맞는다. 하지만 막히는 곳이 있다.
   - `CLAIM`·`OF_USER`·`MEMBERS`가 인자로 받은 접두사로 다른 슬롯의 노드 슬롯 키를 읽는다. Redis Cluster는 스크립트의 교차 슬롯 접근을 막는다.
   - 펜싱도 이력 스크립트가 룸 키와 노드 슬롯 키를 함께 쓴다.
   - pub/sub는 샤드 pub/sub(`SPUBLISH`, Redis 7)로 바꿔야 한다.
   - 클러스터용 클라이언트와 슬롯 재배치 처리도 들어간다.
   - 결론: 스크립트 설계부터 바꿔야 해서 이번 범위를 넘는다. 이 ADR의 "제어 + 룸 샤드" 분리는 나중에 Redis Cluster로 갈 때도 룸 쪽을 그대로 옮길 수 있게 한다.
2. **테넌트별 Redis.** 간단하지만, 가장 큰 테넌트 하나가 여전히 한 코어에 묶인다.
3. **이력 저장 구조 변경(Streams 등, M5 시제품).** 코어당 약 1.3배라 배수 확장이 아니다. 샤딩 뒤에도 코어당 효율이 필요해지면 다시 본다.
4. **샤드 목록 온라인 변경(룸 이전).** 이전 중의 순서·중복 처리가 복잡하다. 재시작 + 새 epoch로 충분히 안전하고, 운영자는 미리 알 수 있다.
5. **이름 기준 rendezvous(HRW) 해시(개정 전의 결정).** 목록 순서와 무관하고, 샤드 추가 때 약 1/N만 옮긴다는 장점이 있었다. 기각한 이유:
   - 샤드 하나의 룸 일부만 옮기는 단위가 없다. 범위 표는 슬롯 범위를 옮기면 된다.
   - Redis Cluster의 슬롯과 대응하지 않아, 나중에 옮길 때 룸의 위치를 다시 계산해야 한다.
   - 운영자가 "이 룸은 어디에 있나"를 표 하나로 볼 수 없다.
6. **샤드 사본에 소유자 값만 복사(개정 전의 결정).** 네트워크가 늦게 전달한 옛 소유자의 쓰기가 새 소유자의 사본을 덮을 수 있다. 그러면 그 샤드에서 펜싱이 잠시 풀린다. 세대 번호를 붙여 단조 증가로 바꿨다.

## 위험과 미해결

- 샤드 하나가 내려가면 그 샤드의 룸만 멈춘다(지금은 전부가 멈춘다). 그 대신 장애 지점이 늘어난다.
- **제어 Redis는 단일 장애 지점이자 천장이다.** 샤드가 아무리 많아도, 제어 Redis가 내려가면 다음이 모두 멈춘다:
  - 새 접속(티켓·세션 등록).
  - presence.
  - 노드 슬롯 heartbeat. 이것이 멈추면 펜싱 사본도 갱신되지 않아 결국 모든 발행이 멈춘다.

  Sentinel로 가용성을 높일 수는 있다. 하지만 처리량 천장(세션·presence 쓰기)은 그대로다. 측정상 이 천장이 문제가 되면 사용자 키 기준으로 나눠야 한다. 아직 재지 않았다(위 측정 계획).
- 노드마다 샤드 수 × 연결이 늘어난다(샤드당 명령·발행·구독 4개 등).
- **Sentinel + TLS가 필요하다.** 샤드가 여러 개인 배포는 대개 관리형·원격 Redis다. 그런데 지금은 Sentinel과 TLS를 함께 쓸 수 없다(설정 검증이 거부한다). 샤딩을 실제 운영에 쓰려면 이것을 먼저 풀어야 한다.
- 이 기계에서는 Redis 두 개 + 노드 + 부하 생성기를 모두 같은 장치에 둬야 해서, 측정이 코어 수에 묶인다(샤드 2개가 한계).

## 검토 요청

1. "제어 Redis + 룸 샤드" 분리로 갈지, Redis Cluster 지원을 먼저 할지.
2. 샤드 표 변경 = 정비 시간(전체 drain·재시작) + 옮겨진 룸의 새 epoch 정책이 운영상 받아들여지는지.
3. 측정을 같은 장치의 샤드 2개로 할지(이 기계의 한계), 아니면 클라우드 VM 측정을 함께 할지(로컬 원칙과 부딪힘). 같은 장치로만 잰다면 선형 확장은 주장하지 않는다.
4. 구현 전에 제어 Redis 용량(접속·join 폭주)을 먼저 재는 순서에 동의하는지.
