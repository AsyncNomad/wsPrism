## 개정 2 (2026-10-19): 외부 검토 2차 반영 — R1 착수 조건

### B1. member id = 노드 슬롯 + 룸별 카운터 (개정 1 A1 대체)

A1(전역 카운터 구간 임대)은 계산은 적었지만 결론이 틀렸다. u32 전역 공간은 클러스터 전체 입장 속도에 따라 이렇게 소진된다.

| 클러스터 입장 속도 | 한 바퀴 |
|---|---|
| 초당 1,000 | 약 50일 |
| 초당 10,000 | 약 5일 |
| 초당 50,000 | 약 1일 |

24시간 열려 있는 로비·대시보드처럼 며칠씩 접속한 멤버가 있으면 실제로 충돌한다. 노드가 재시작하면 받아 둔 구간의 남은 id도 버려진다. 게다가 id를 다시 쓰면, presence 이벤트를 끈 테넌트에서는 수신자의 오래된 프레임 판정 기록 때문에 새 멤버의 프레임이 버려진다.

**결정:** `member_id(u32) = 노드 슬롯(상위 10비트) | 그 노드의 룸별 카운터(하위 22비트)`.
- **노드 슬롯:** 기동할 때 Broker에서 한 번 임대한다(Redis `SET NX` + heartbeat TTL). 죽은 노드의 슬롯은 그 노드 멤버의 presence 정리가 끝난 뒤에야 재사용한다(슬롯 TTL > presence TTL). 단일 노드·`MemoryBroker`는 슬롯 0이다. 최대 1,024 노드.
- **룸별 카운터:** 노드가 룸마다 갖고, 발급할 때 **그 룸의 살아 있는 로컬 멤버 id를 건너뛴다.** 노드는 자기 로컬 멤버를 전부 알기 때문에, 슬롯과 함께 **클러스터 전체에서 정확히 유일**하다(확률이 아니다).
- 한 바퀴는 "한 노드에서 한 룸에 약 419만 번 입장"해야 일어나므로 사실상 격리 시간이 된다. 그래도 남는 오래된 판정 기록 위험은, 같은 id 재사용이 아주 드문 대형 룸에 한정된다(문서화; presence 이벤트를 켜면 SDK가 퇴장 멤버의 기록을 지운다).
- **와이어(Hot v2 `sender` u32)는 그대로**이고, 입장은 동기이며 Redis 왕복이 없다.
- 기각: `sender`를 u64로 확장 — 배포 전이라 가능하지만, 프레임마다 4바이트가 늘고 슬롯 방식으로 정확성을 이미 얻는다.

### B2. R1 통과 기준 (개정 1 A12 강화)

| 지표 | 기준 | 측정 |
|---|---|---|
| **전달 1건당 명령어 수** (주 기준) | 시나리오마다 ±2% 이내 | `bench/run-icount.sh`: 소켓 없는 엔진 하네스(`crates/wsprism-engine/examples/icount.rs`)를 callgrind로 실행, 측정 구간 명령어 총합 ÷ 전달 수(입장·퇴장·종료는 ÷ 연산 수), 3회 중앙값. 시나리오: ext(chat.send), hot, hot_keyed, api(서버 발행), churn(presence 켠 입장+퇴장), disconnect(룸 4개 세션 종료). 측정 방법 변경 사유는 아래 기준선 참고 |
| **유휴 연결당 메모리** (사용자 분산) | +2% 이내 | `bench/run-mem-users.sh` 방식, 1만 연결 |
| 마이크로벤치 | 중앙값 ±5% | 같은 세션 교차 3회 |
| 종단 간 CPU·p99 | 보조 지표 | `run-ab-gateway.sh` |

R1 전에 같은 방법으로 기준선을 잰다.

**기준선 (2026-10-19, 커밋 `bc9bc5f`, `bench/results/mem-pre-r1.jsonl`):**

- 유휴 1만 연결, 연결당 RSS (3회): 사용자 분산 20.96 / 20.94 / 20.96 KB → **중앙값 20.96 KB**. 사용자 공유 20.65 / 20.61 / 20.54 KB → 중앙값 20.61 KB. 실행 간 흔들림은 0.6% 이하라 +2% 기준을 판정할 수 있다.
- 전달 1건당 명령어 수 (`bench/results/icount-pre-r1.jsonl`, 커밋 `56c78c9`):

  | 시나리오 | 명령어/단위 | 3회 차이 |
  |---|---|---|
  | ext (전달 1건) | 301.7 | 0.02% |
  | hot (전달 1건) | 188.2 | 0.00% |
  | hot_keyed (전달 1건) | 543.4 | 0.01% |
  | api (전달 1건) | 174.1 | 0.00% |
  | churn (입장+퇴장 1회, 100명 룸) | 384,064 | 0.68% |
  | disconnect (1회) | 73,600 | 0.33% |

  - **측정 방법을 바꾼 이유:** WSL2에는 CPU PMU가 없어 `perf stat -e instructions`가 `<not supported>`다(`/sys/bus/event_source/devices`에 `cpu` 없음). 그래서 처음 정한 "게이트웨이 종단 간 `perf stat`" 대신 callgrind를 쓴다. callgrind는 결정적이라 팬아웃 경로는 실행 간 차이가 0.02% 이하다. 입장·퇴장 경로는 해시 시드가 실행마다 달라 0.7%까지 흔들리므로 3회 중앙값을 쓴다.
  - **범위:** R1은 전송 계층(소켓·직렬화·쓰기 task)을 건드리지 않고 엔진 경로만 바꾸므로 엔진만 잰다. 전송 계층 비용은 종단 간 보조 지표로 본다.
  - 기각: 종단 간 CPU를 여러 번 재 신뢰구간으로 판정 — 실행 간 흔들림이 10%를 넘어 2% 회귀를 가려낼 수 없다.
  - 관찰(M5 후보): hot_keyed가 hot의 2.9배다. 키 있는 상태는 수신자마다 Hot 슬롯에 넣기 때문이다. R1 범위는 아니다.

### B3. 검증용 Broker 두 개를 R1 범위에 넣는다

- **기록 Broker (`RecordingBroker`, 테스트 전용):** 모든 발행을 기록한다. **룸으로 가는 모든 경로가 Broker를 거치는지** 테스트한다. 단일 노드에서는 Broker를 우회해도 기존 테스트가 다 통과하므로, 이것 없이는 R3에서 "다른 노드 멤버만 못 받음"으로만 드러난다.
  - 대상 경로: Ext 발행(서비스·RPC가 룸에 보내는 것 포함), 서버 API 발행(Ext·Hot), presence 이벤트 전 경로(입장, 퇴장, 연결 종료, 밀려남, 서버 API disconnect), Hot relay(로컬 우선이어도 Broker로 방송), 틱 송신, `sys.gap`.
  - 대상이 아닌 것: 자기 세션 응답(`reply`, `DeferredReply`), 사용자 대상 전송(`send_to_user`)은 R4의 사용자 제어 채널에서 따로 검증한다.
- **장애 주입 Broker (`FaultBroker`, 테스트 전용):** 지연·실패·큐 포화를 주입한다. 이것으로 R1에서 검증하는 것은 `UNAVAILABLE` 경로, 테넌트별 할당량(B4), 구독 참조 계수의 경쟁 조건(B5)이다.

### B4. 송신 큐와 테넌트 할당량은 엔진 공통부에

Broker 구현마다 백프레셔를 다시 만들지 않도록 엔진에 공통 `BrokerOutbox`를 둔다. 하는 일은 테넌트별 몫, 가득 찼을 때의 정책(Reliable은 `UNAVAILABLE`, Lossy는 버림), 묶어 보내기(A3)다. Broker는 `mode()`로 둘 중 하나를 밝힌다.
- **Inline:** `MemoryBroker`. 큐 없이 바로 호출하며 비용이 0이다.
- **Queued:** Redis 등. Outbox를 거친다.

### B5. 구독 참조 계수는 룸 생성·삭제와 같은 락 안에서, 명령은 순서대로

Broker 구독은 비동기라 shard 락 안에서 기다릴 수 없다. 그래서 룸이 생기고 비워지는 바로 그 shard 락 안에서 **순서 있는 `Subscribe`/`Unsubscribe` 명령을 큐에 기록만** 하고, Broker가 그 순서대로 적용한다. "마지막 멤버 퇴장(해제)"과 "새 멤버 입장(구독)"이 경쟁해도 명령 순서가 실제 순서와 같으므로, 끝 상태가 올바르다. `FaultBroker`(명령 적용 지연)로 검증한다.

### B6. 트레이트의 전체 형태를 지금 정하고, 공개는 R3 이후

엔진과 게이트웨이가 다른 크레이트라 트레이트는 `pub`이어야 한다. 그래서 (1) 알려진 연산의 동기/비동기 형태를 지금 모두 정하고, (2) `spi::broker`에 "실험적 — R3 전까지 외부 구현 금지, 변경 예정"을 명시한다. R1은 R1 연산만 구현하고, 나머지는 단계에서 채운다.

| 연산 | 형태 | 단계 |
|---|---|---|
| `mode() -> Inline \| Queued` | 동기 | R1 |
| `publish(frames)` — 룸 프레임 묶음(Outbox가 부름; Inline은 즉시 로컬 전달) | 동기(큐에 넣기) | R1 |
| `subscription(cmd)` — 순서 있는 구독·해제(B5) | 동기(큐에 넣기) | R1 |
| `incoming() -> BrokerRx` — 들어오는 프레임·제어·gap | 동기(수신기 반환) | R1(Memory는 빈 것) |
| `node_slot() -> u16` | 동기(기동 때 임대해 둔 값) | R1(Memory 0), 임대는 R3 |
| `history(room, since, limit)` | 비동기 | R2 |
| `kv()` — 티켓·presence 공유 저장소 | 비동기 | R3/R4 |
| `claim_session(...)` — 세션 소유권(A9) | 비동기 | R4 |
| `control(target, cmd)` | 동기(큐에 넣기) | R4 |

## 개정 1 (2026-10-19): 외부 검토 반영

본문과 충돌하면 이 절이 우선한다. 검토 의견 중 본문에 이미 있던 것(백프레셔 기본 정책 §1, 복구 대기열 상한 §3, Hot 이력 제외, 이력 없는 룸의 `sys.gap` §4, Redis 장애 동작 §9)은 유지하되, 아래에서 구체화한다.

| # | 바뀐 결정 | 내용 |
|---|---|---|
| A1 | **member id: 구간 임대, `join_room`은 동기 유지** (§5 대체) | 노드가 Redis 전역 카운터에서 id 구간(65,536개)을 받아 두고, 절반을 쓰면 백그라운드로 다음 구간을 미리 받는다. 입장 시 왕복도 취소 지점도 없고, 클러스터 전체에서 유일하다(u32는 클러스터 누적 약 43억 번 입장 후 한 바퀴 — 그때 같은 id의 옛 멤버가 같은 룸에 살아 있어야 충돌). `MemoryBroker`는 로컬 카운터. 구간을 못 받으면(Redis 다운) 입장을 `UNAVAILABLE`로 거절한다 |
| A2 | **이력 없는 룸은 Lua 없이 `PUBLISH`만** (§2 보완) | Lua(offset 발급·저장)는 이력 룸에만. 이력 없는 Reliable도 기본은 Broker 경유(클러스터 전체 같은 순서)이고, 룸 패턴별로 `delivery: local_first`(지연·Redis 부하를 줄이는 대신 노드 간 순서가 다를 수 있음)를 고를 수 있다 |
| A3 | **발행을 묶어 보내기** | 노드의 Broker 송신 task는 큐에 쌓인 발행을 Redis 파이프라인 한 번으로 보낸다(세션 쓰기 합치기와 같은 원리) |
| A4 | **Hot은 노드 단위로 모은 뒤 Redis로** (§2 보완) | 노드가 룸별 `(sender, svc, key)` 최신값 slot을 두고, 틱마다(테넌트 `hot_tick_hz`, 0이면 짧은 묶음 창 5 ms) 룸별로 한 번 보낸다. 송신자마다 30~60 Hz를 그대로 흘리지 않는다. 로컬 전달은 지금처럼 즉시 |
| A5 | **Redis 범위: 단일 Redis + Sentinel, 키는 지금부터 Cluster 대비** | 모든 키에 해시 태그 `{tenant:room}`을 써서, Lua가 다루는 키가 같은 슬롯에 놓이게 한다. 샤드 PubSub(`SPUBLISH`, Redis 7)과 Cluster 지원은 다음 단계에서 하되, 키 형식은 바꾸지 않아도 되게 지금 정한다 |
| A6 | **PubSub 연결 여러 개** | 구독을 룸 해시로 N개(기본 4) 연결에 나눈다. 한 연결의 느린 메시지가 다른 룸을 막지 않게 하고, 처리량 병목을 없앤다 |
| A7 | **테넌트별 할당량(noisy neighbor 방지)** (§1 보완) | Broker 송신 큐에 테넌트별 몫을 둔다. 한 테넌트가 몰아쳐 큐를 채워도 다른 테넌트의 발행은 막히지 않는다. 몫을 넘은 테넌트의 Reliable 발행은 `UNAVAILABLE`, Lossy는 버림 |
| A8 | **Redis AUTH·TLS·ACL** (§9 보완) | `rediss://` 지원, ACL 사용자와 최소 권한(필요한 명령·`wsp:` 키 접두사만) 문서화, 배포별 키 접두사(`gateway.broker.prefix`)로 여러 클러스터가 한 Redis를 나눠 쓸 수 있게 한다 |
| A9 | **세션 독점은 정확하게** (§6·§8 대체) | `sessions.mode: single`과 sid 교체는 Redis에서 Lua로 소유권을 원자적으로 차지한다(`SET` 소유자 = 노드·세션, 이전 소유자에게 `ReplaceSid`/`Kick` 제어). 노드가 동시에 받아도 정확히 하나만 남는다. rate limit·용량·`max_sessions_per_user`(multi)는 근사로 둔다 |
| A10 | **죽은 노드 정리를 멱등하게** (§6 보완) | 정리하는 노드가 `SET wsp:cleanup:{node} NX EX`로 정리권을 잡고, presence 항목 삭제(`HDEL`) 결과가 1일 때만 `member_left`를 낸다. 여러 스위퍼가 동시에 돌아도 이벤트는 한 번만 나간다 |
| A11 | **복구 대기열 상한을 숫자로** (§3 구체화) | 세션·룸당 1,000건 또는 1 MiB. 넘으면 `recovered: false`(클라이언트가 재동기화) |
| A12 | **R1 통과 기준을 숫자로** (§11 R1 구체화) | 마이크로벤치: 같은 세션에서 번갈아 3회 측정한 중앙값 변화가 ±5% 이내. 종단 간: CPU·p99가 같은 바이너리끼리의 실행 간 범위 안(같은 바이너리도 실행마다 CPU가 ±10% 흔들리므로 ±2%는 잡음보다 좁다) |
| A13 | **R5: 클라이언트 offset 검사기** | 카오스 중 모든 클라이언트가 받은 offset을 기록해, 중복·누락·순서 역전을 기계로 판정한다 |
| A14 | **M5 공개 벤치에 이력 켠 구성 포함** | 기능을 갖춘 상태의 메모리·CPU를 공개한다 |
| A15 | **Redis 처리량 측정** (R3 완료 기준 추가) | 216만 전달/s 시나리오(발행 약 24만/s)에서 Redis CPU·지연을 측정해 클러스터 천장을 숫자로 문서화한다. 클러스터 모드의 처리량 한계는 Redis이므로, 클러스터에서의 우위는 "노드당 효율(같은 부하를 더 적은 노드로)"로 주장한다 |

## 배경 (지금 구조에서 확인한 사실)

- **노드 하나에 갇혀 있다.** 세션 레지스트리·presence·룸 id·member id·1회용 티켓이 모두 프로세스 메모리에 있다. 노드를 늘려도 룸을 공유할 수 없어서 수평 확장이 안 되고, 노드가 죽으면 그 노드의 모든 상태가 사라진다(HA 없음).
- **끊기면 잃는다.** 끊긴 사이의 룸 메시지를 되찾을 방법이 없다. 그런데 느린 수신자는 일부러 끊는다(C1: "끊고 재동기화"). 그 재동기화 수단이 지금은 "클라이언트가 자기 백엔드에서 알아서"뿐이다. 모바일처럼 잠깐 끊기는 환경에서 채팅·이벤트가 사라진다.
- **경계는 좋다.** 발행은 거의 전부 엔진의 `RealtimeCore`(`publish_room*`, `send_to_user`, `DeferredReply`)를 거친다. 게이트웨이가 엔진 내부를 직접 만지는 곳은 몇 군데뿐이다: 서버 API(presence 조회·사용자 연결), admission(세션 수·sid 교체), `Gateway::session_count`. 그래서 Broker를 끼우는 위치가 분명하다.
- **노드마다 따로 매기는 id:** 룸 id(v2 `chan`)와 member id(v2 `sender`)가 노드별 카운터다. 클러스터에서는 같은 룸이 노드마다 다른 id를 갖고, 다른 노드의 member id와 충돌할 수 있다.
- Centrifugo(동급 경쟁 제품)는 Broker(Redis/NATS)·채널 이력(epoch+offset)·자동 복구를 모두 갖췄다. "대기업급"의 최소 조건이다.

## 목표와 비목표

**목표**
1. **수평 확장:** 노드 N개가 같은 룸을 공유한다. 어느 노드에 발행해도 모든 노드의 멤버에게 간다. 로드밸런서 고정 세션(sticky)이 필요 없다.
2. **복구:** 끊긴 클라이언트가 (다른 노드로) 다시 붙으면, 보존 기간 안의 놓친 룸 메시지를 순서대로 받는다. 못 받으면 "복구 실패"를 분명히 알린다.
3. **HA:** 노드 하나가 죽어도 클라이언트는 다른 노드로 붙어 복구한다. 죽은 노드의 멤버는 다른 멤버에게 퇴장으로 보인다.
4. **클러스터 제어:** 서버 API의 disconnect·presence, sid 교체, 1회용 티켓이 노드와 무관하게 동작한다.
5. **단일 노드는 그대로 빠르다.** 단일 노드 설정에서는 네트워크 홉도 추가 비용도 없어야 한다(인메모리 Broker).

**비목표 (이번에는 하지 않음):** Hot 레인 이력(상태는 최신값이라 클라이언트가 주기적으로 다시 보낸다), 정확한 클러스터 전역 상한(근사치로 둔다, §8), NATS·Kafka 구현(경계만 열어 둔다), 지역 간(multi-region) 복제.

## 결정

### 1. 엔진에 `Broker` 경계 (spi)

```rust
/// 노드 사이의 팬아웃·이력·제어. 엔진은 이것만 안다(Redis를 모른다).
#[async_trait]
pub trait Broker: Send + Sync + 'static {
    /// 룸 메시지를 클러스터에 발행. 이력이 켜진 룸이면 offset을 매겨 저장하고 돌려준다.
    fn publish(&self, room: &RoomKey, frame: BrokerFrame) -> Result<PublishTicket>;
    /// 이 노드가 룸을 구독/해제 (엔진이 로컬 멤버 수로 참조 계수).
    async fn subscribe(&self, room: &RoomKey) -> Result<()>;
    async fn unsubscribe(&self, room: &RoomKey) -> Result<()>;
    /// `since` 이후의 이력 (복구).
    async fn history(&self, room: &RoomKey, since: StreamPos, limit: usize) -> Result<History>;
    /// 사용자·노드 대상 제어 명령 (disconnect, sid 교체 …).
    fn control(&self, target: ControlTarget, cmd: ControlCmd) -> Result<()>;
    /// 들어오는 프레임·제어·"구독이 끊겼었음(gap)" 알림의 수신 스트림.
    fn incoming(&self) -> BrokerRx;
    /// 룸 안에서 유일한 member id 발급 (§5).
    async fn next_member_id(&self, room: &RoomKey) -> Result<u32>;
    /// 공유 키-값 (1회용 티켓, presence).
    fn kv(&self) -> &dyn SharedKv;
}
```

- **인메모리 Broker(`MemoryBroker`)가 기본값**이다. 지금 동작을 그대로 옮긴 것이라 단일 노드에서는 아무것도 바뀌지 않는다. 이력·복구(§3)도 메모리 링 버퍼로 동작하므로, **M3는 Redis 없이도 쓸 수 있다**(잠깐의 네트워크 끊김 복구).
- **Redis Broker**가 첫 외부 구현이다(§9). 설정 `gateway.broker: { kind: redis, url: ... }`.
- **`publish`는 동기 함수(대기 없음)다.** 서비스 코드(`ctx.publish_room_*`)가 지금처럼 동기로 남는다. Redis 구현은 노드별 송신 task의 유한 큐에 넣는다. 큐가 가득 차면 Reliable은 `UNAVAILABLE`, Lossy는 버린다.

### 2. 순서 규칙: 레인마다 다른 경로

| 메시지 | 경로 | 이유 |
|---|---|---|
| **Ext Reliable** (채팅, 서버 발행, 이벤트) | **Broker를 거쳐서**(발행 노드도 Broker에서 받아 전달) | 클러스터 전체가 같은 순서로 본다. 이력 offset이 그 순서다 |
| **Hot Lossy** (상태) | **로컬 먼저** 전달 + Broker로 다른 노드에 방송(원래 노드는 자기 것을 건너뜀) | 지연이 생명이다. 상태는 최신값이고, 순서는 `(sender, key)`별 `seq`로 이미 해결돼 있다 |

- 대가: Reliable은 Redis 왕복(같은 LAN에서 약 0.2~0.5 ms)만큼 늦어진다. 인메모리 Broker에서는 추가 지연이 없다.
- 기각: 모두 로컬 먼저 — 두 노드에서 동시에 발행하면 노드마다 순서가 달라지고, 이력 offset과 실제 전달 순서가 어긋난다.

### 3. 이력·복구 (M3)

- **룸 패턴별로 켠다(기본 꺼짐):** `tenants[].history: [{ rooms: "chat:*", size: 200, ttl_s: 600 }]`. 이력은 메모리(또는 Redis)를 쓰므로 필요한 룸만 켠다.
- **위치 = `epoch` + `offset`.** offset은 룸별 단조 증가 u64이고, epoch는 그 이력 저장소의 수명 식별자다. Redis 재시작이나 이력 유실이 나면 epoch가 바뀌므로, 클라이언트는 "이어 받기"가 불가능하다는 것을 알 수 있다.
- **v2에 추가(하위 호환, 필드 추가만):**
  - 이력 룸의 메시지에 `"offset": n`이 붙는다.
  - `room.join`에 `"data": {"recover": {"epoch": "e", "offset": n}}`를 실을 수 있다.
  - `sys.joined`에 `"epoch"`, `"offset"`(현재 위치)과 복구 결과 `"recovered": true|false`가 실린다. `false`면 클라이언트가 자기 백엔드에서 다시 동기화해야 한다.
- **복구 중 경쟁 처리:** 입장 즉시 라이브 메시지가 오기 시작하는데, 이력은 비동기로 읽는다. 그래서 그 세션의 그 룸을 "복구 중"으로 표시하고, 그동안 도착한 라이브 메시지를 세션 안에 잠시 모아 둔다. 이력을 다 보낸 뒤 **이미 보낸 offset 이하는 버리고** 모아 둔 것을 보낸다(중복·누락 없음). 모아 둘 수 있는 양에는 상한을 두고, 넘으면 `recovered: false`로 처리한다.
- **C1과의 정합:** 느린 수신자를 끊는 정책이 이제 "끊고 자동 복구"가 된다. SDK가 룸별 `{epoch, offset}`을 기억했다가 재접속하면서 자동으로 복구를 요청한다.
- **ACK(클라이언트 확인 응답)는 하지 않는다.** offset 기반 재요청으로 충분하고, ACK는 메시지마다 상향 트래픽을 만든다.

### 4. 노드 로컬 구독 색인

- presence(누가 이 노드의 어느 룸에 있나)는 계속 **노드 로컬**이다. 팬아웃은 지금처럼 로컬 멤버 핸들로 한다.
- 노드는 **로컬 멤버가 생긴 룸만** Broker 구독한다(첫 멤버 입장 시 구독, 마지막 멤버 퇴장 시 해제, 참조 계수). 그래서 노드 수가 늘어도 메시지가 필요 없는 노드에는 가지 않는다.
- **구독이 끊겼다 돌아오면(gap):** Redis 연결이 끊기거나 느려서 Redis가 구독자를 끊는 경우다. 노드는 모든 룸을 다시 구독하고, **이력 룸은 노드가 마지막으로 전달한 offset부터 스스로 이력을 읽어** 메운다. 클라이언트에게는 끊김이 보이지 않는다. 이력이 없는 룸은 메울 수 없으므로 멤버에게 `sys.gap {room}`을 보낸다.

### 5. id

- (개정 1 A1이 이 항목을 대체한다: 구간 임대, 입장은 동기.) **member id는 룸 안에서만 유일하면 된다.** 클라이언트가 `sender`로 구분하는 범위가 그 룸이기 때문이다. 그래서 Broker가 **룸별 카운터**로 발급한다(Redis `INCR`, 메모리는 로컬 카운터). 입장할 때 한 번 왕복이 생기지만, 입장은 드물다. 기각한 대안 두 가지는 아래와 같다.
  - u32 안에 노드 번호를 넣고 카운터는 22비트: 노드당 약 4백만 번 입장하면 값이 한 바퀴 돌아, 오래 남아 있는 멤버와 충돌할 수 있다.
  - v2 `sender`를 u64로 넓힘: 프레임마다 4바이트가 더 들고, 프로토콜도 바뀐다.
- **룸 id(`chan`)는 노드 로컬로 둔다.** `chan`은 세션이 자기 `sys.joined`에서 받는 값이라 노드마다 달라도 된다. 다른 노드에서 온 Hot 프레임은 받는 노드가 **자기 `chan`으로 헤더 4바이트만 바꿔서** 다시 인코딩한다(룸당 한 번, encode-once는 그대로 유지).

### 6. 클러스터 제어

- **사용자 제어 채널:** 노드는 로컬 세션이 있는 사용자의 채널 `user:{tenant}:{user}`를 구독한다(참조 계수). 이 채널로 오가는 명령은 다음과 같다.
  - `Disconnect{sid?, reason}`: 서버 API의 disconnect가 어느 노드에 들어와도 동작한다.
  - `ReplaceSid{sid, except_session}`: sid 교체(S4)가 노드를 넘어 동작한다.
  - `KickOldest`: `on_exceed: kick_oldest`가 노드를 넘어 동작한다(§8 근사).
- **presence 클러스터화:** 룸 멤버 목록을 공유 저장소에 둔다(Redis 해시 `presence:{tenant}:{room}`). 노드마다 살아 있음을 알리는 키에 TTL을 걸고, **죽은 노드의 멤버는 살아 있는 노드의 스위퍼가 정리하면서 `member_left`를 낸다**(ADR 0010을 클러스터로 확장). 서버 API의 presence 조회도 클러스터 전체를 본다. presence 이벤트는 룸 채널의 제어 프레임으로 방송한다.
- **1회용 티켓:** 공유 저장소에 둔다(Redis `SET NX EX` + `GETDEL`로 1회성을 원자적으로 보장). 티켓을 발급한 노드와 소비하는 노드가 달라도 된다.

### 7. 노드 사이 프레임 형식

- 버전 필드가 있는 이진 형식(내부용)이다: `[ver][kind][origin_node][room_key][qos][offset?][payload]`. Hot 프레임은 v1 페이로드와 헤더 필드(`svc, op, key, seq, sender`)를 보내고, 받는 노드가 자기 `chan`으로 v2를 만든다.
- **롤링 업데이트:** 노드는 자기가 아는 최고 `ver`까지만 보내고, 모르는 `ver`는 로그를 남기고 버린다. 형식을 바꿀 때는 "읽기를 먼저 배포하고, 쓰기는 나중에 바꾼다"는 규칙을 문서화한다.

### 8. 클러스터 전역 상한: 이번에는 근사치

| 상한 | 이번 결정 |
|---|---|
| `max_sessions_total`(테넌트), `max_rooms_total` | **노드별로 적용**한다(문서에 "노드당"이라고 명시). 전역 정확 계수는 매 접속마다 공유 저장소 왕복이 필요해서 보류 |
| `max_sessions_per_user` | 공유 카운터로 **근사**(경쟁 시 잠깐 초과 가능)하고, 초과분은 `KickOldest` 제어로 정리 |
| `max_users_per_room` | 클러스터 presence 수로 **근사** |
| handshake·메시지 rate limit | 노드별(로드밸런서 뒤에서 IP별 제한의 의미가 그대로 유지됨) |

### 9. 실패 시 동작

| 상황 | 동작 |
|---|---|
| Redis 다운 | Ext Reliable 발행 → `UNAVAILABLE`(조용히 잃지 않는다). Hot은 로컬 전달만 계속(다른 노드 멤버는 못 받음). 티켓 인증 → 503 + `Retry-After`(fail closed). 이미 연결된 세션은 유지 |
| Redis 재시작(이력 유실) | epoch가 바뀜 → 복구 요청은 `recovered: false` |
| 노드 강제 종료 | 클라이언트는 41xx/네트워크 오류로 다른 노드에 재접속하고 복구. 죽은 노드의 presence는 TTL 만료 후 정리되며 `member_left` 발생 |
| 노드의 구독 연결 지연·끊김 | §4의 gap 처리(이력 룸은 노드가 스스로 메움) |

### 10. 의존성 (승인 필요)

| 용도 | 후보 | 비고 |
|---|---|---|
| Redis 클라이언트 | `redis`(redis-rs, tokio, 연결 관리자) | 가장 널리 쓰임, BSD-3. 대안 `fred`는 기능이 많지만 의존성이 더 크다 |
| 테스트용 Redis 서버 | docker 이미지 `redis:7` (`--internal` 네트워크, 실험 로컬 원칙 준수) | 이미지 다운로드 필요 |

### 11. 단계 (단계마다 커밋, 테스트, 문서)

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| R1 | `Broker` 경계(B6의 R1 연산) + `MemoryBroker`로 지금 동작 이전, `BrokerOutbox`·테넌트 할당량(B4), 구독 명령(B5), member id = 슬롯 + 룸별 카운터(B1), `RecordingBroker`·`FaultBroker` 테스트(B3) | 기존 테스트 전부 + B2 기준 + B3 테스트 |
| R2 | 이력·offset·epoch, 복구 프로토콜(v2 추가), 복구 중 버퍼링, SDK 자동 복구 | **끊긴 사이 메시지 복구 테스트**(M3 완료 기준), slow consumer → 복구 |
| R3 | Redis Broker: 발행·구독(로컬 구독 색인), 이력(Lua로 offset 발급·저장·자르기를 원자적으로), member id, 공유 티켓, gap 처리 | 2노드 + Redis 통합 테스트 |
| R4 | 클러스터 제어·presence: disconnect·sid 교체·kick, presence 저장소와 노드 사망 정리, 서버 API 클러스터화 | 노드를 넘는 제어 테스트 |
| R5 | 카오스: 노드 `kill -9`, Redis 재시작, 구독 지연 시뮬레이션(netlab), 문서·운영 가이드 | **노드 강제 종료 카오스 테스트**(M4 완료 기준) |

## 기각한 대안

| 대안 | 이유 |
|---|---|
| 세션 고정(sticky)으로 노드마다 룸을 나눠 맡기 | 한 룸의 멤버가 여러 노드에 흩어지는 순간 깨진다. 노드 장애 시 룸 전체가 사라진다 |
| 노드끼리 직접 메시(gossip/mesh) | 소속 관리·분할·재연결을 직접 구현해야 한다. 검증된 Broker를 쓰는 편이 운영자가 이해하기도 쉽다 |
| Redis 대신 NATS 먼저 | NATS JetStream도 좋지만, 이력·카운터·키-값·presence를 한 저장소로 처리하기에는 Redis가 단순하고 운영 경험이 흔하다. 경계는 NATS를 막지 않는다 |
| 이력을 기본으로 켜기 | 룸마다 메모리를 쓰고, 상태성 룸(Hot)에는 의미가 없다 |
| 복구를 클라이언트 쪽 ACK로 | 메시지마다 상향 트래픽이 생긴다. offset 재요청이 더 싸고 단순하다 |
| Hot도 Broker를 거쳐 순서 보장 | 상태 동기화의 존재 이유인 지연을 희생한다. `seq`로 이미 충분하다 |

## 검토해 주셨으면 하는 결정

1. **레인별 경로(§2):** Ext Reliable은 Broker를 거쳐 클러스터 전체가 같은 순서로 보고, Hot은 로컬 먼저 전달합니다. 대가로 Reliable 지연이 Redis 왕복만큼 늘어납니다.
2. **이력은 룸 패턴별 옵트인(§3)**, 클라이언트 ACK는 하지 않음.
3. **member id를 룸별로 Broker가 발급(§5)**: 프로토콜은 그대로 두고, 입장 시 한 번 왕복이 생깁니다.
4. **전역 상한은 이번에 근사·노드별(§8).**
5. **Redis 먼저 + 다운로드 승인(§10):** `redis` 크레이트와 테스트용 `redis:7` docker 이미지.
6. **단계 R1~R5의 순서**: R2(단일 노드 복구)만 끝나도 "끊겨도 안 잃는다"가 됩니다. 멀티 노드는 R3부터입니다.
