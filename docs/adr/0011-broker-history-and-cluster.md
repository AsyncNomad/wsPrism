## R5-2 구현 (2026-10-20): 카오스 실험과 그것이 찾은 것

**도구:** `sdk/js/test/chaos.test.mjs`.
- 게이트웨이 노드 2개(실제 프로세스)와 Redis를 띄우고, JS SDK 클라이언트들(노드 목록 `url: [..]`, 재접속 시 다음 노드)이 이력 룸에 들어간다. 백엔드는 서버 API로 1, 2, 3, ... 을 발행한다.
- **offset 검사기:** 각 클라이언트가 받은 offset이 알림(`sys.gap`·`recovered:false`) 사이에서 하나씩만 오르는지 본다. 메시지 번호는 정확히 한 번씩 와야 하고, 발행자가 한 노드만 쓴 경우에는 순서도 맞아야 한다(개정 1 A13).
- `WSPRISM_TEST_REDIS`가 있으면 돈다. Redis 재시작·일시 정지는 docker 컨테이너가 있을 때만 돈다.

| 시나리오 | 결과 |
|---|---|
| 노드 `kill -9`(발행 중) | 그 노드의 클라이언트 5명이 다른 노드로 재접속해 이어 받음. 10명 모두 1~600을 빠짐없이 한 번씩 |
| Redis 재시작(데이터 없음) | 새 epoch 알림 뒤 재시작 후 100개가 모두 한 번씩, 끊긴 클라이언트 0 |
| Redis 일시 정지 2초(`CLIENT PAUSE ALL`) | 1~300 모두 한 번씩, offset 연속 |

**실험이 찾은 결함 네 가지 (모두 고침):**
1. **이력 epoch가 바뀌어도 연결된 클라이언트가 몰랐다.** Redis가 데이터를 잃으면 offset이 1부터 다시 시작한다. 그런데 SDK는 마지막 offset(예: 100)보다 작은 새 메시지를 이미 본 것으로 보고 조용히 버렸다(설계 중 발견).
   - 보관 프레임에 epoch를 싣는다(`<offset>:<epoch>`).
   - 노드가 epoch 변경을 보면 새 epoch를 담은 `sys.gap`을 먼저 보내고, SDK는 그 룸의 위치를 초기화한다.
2. **결과를 모르는 쓰기를 재시도해 중복이 생겼다.** redis-rs의 기본 응답 시간 초과는 500 ms다. 2초 정지 중 파이프라인이 시간 초과로 실패해 재시도됐는데, 정지가 풀리자 원래 요청도 실행됐다. 같은 메시지가 다른 offset으로 두 번 저장됐다.
   - 보관 프레임에 노드별 단조 번호(`BrokerFrame.seq`)를 붙이고, Lua가 룸별로 노드의 마지막 적용 번호를 기억해 이하를 건너뛴다(정확히 한 번). 같은 묶음을 두 번 보내는 Redis 크레이트 테스트가 있고, 검사를 빼는 변형에서 실패한다.
   - 발행 전용 연결은 응답 대기를 10초로 둔다. 그동안 새 발행은 송신 큐 대기 상한(1초)이 거절하므로 지연이 쌓이지 않는다. 이력 없는 룸의 중복 위험은 "연결이 끊겼는데 이미 실행된 경우"로 줄어든다(문서화).
3. **Redis가 재시작하면 스크립트가 사라진다(`NOSCRIPT`). 파이프라인 오류에서는 오류 코드로 이를 알아보지 못했다.** 그래서 스크립트를 다시 올리지 않고 같은 실패를 무한히 재시도했다. 이제 오류 문자열도 확인한다.
4. **§4의 "구독이 끊겼다 돌아오면 이력 룸은 노드가 스스로 메운다"가 구현되지 않았었다.** 재시작 직후 구독이 복구되기 전에 발행된 메시지는 노드에 오지 않았고, 클라이언트는 `gap`만 받았다.
   - 노드가 룸마다 마지막으로 전달한 (epoch, offset)을 기억한다. 구독이 돌아오면 그 뒤의 이력을 읽어 전달한다. epoch가 바뀌었으면 새 epoch 처음부터 전달한다.
   - 순서는 따로 장치가 필요 없었다. 그 룸의 수신 작업 task가 이력을 읽는 동안 새 프레임은 작업 큐에서 기다린다. 겹치는 부분은 노드 수준에서 offset으로 건너뛴다.
   - 메울 수 없을 때만 `sys.gap`을 보낸다.

**명시한 의미(CLUSTER.md):**
- 서버 API의 200은 "그 노드의 송신 큐에 들어갔다"는 뜻이다. 노드가 비우기 전에 죽으면 잃을 수 있다.
- 노드 사이의 발행 순서는 보장하지 않는다. 일시 정지 실험에서 발행자가 멈춘 노드를 건너뛰자 순서가 바뀐 것을 확인했고, 검사기는 이 경우 순서 대신 정확히 한 번만 본다.

**완료 기준:**
- M3: 끊긴 사이의 메시지 복구, 느린 수신자 복구.
- M4: 노드 강제 종료 카오스 테스트.
- 모두 충족했다. CI의 `cluster` job에 카오스 테스트(노드 kill)를 넣었다.

## R5-1 구현 (2026-10-20): 대조 작업과 슬롯 상실

R5는 둘로 나눈다. **R5-1** 대조 작업(R4에서 남긴 한계, 이 절), **R5-2** 카오스 실험(노드 강제 종료·Redis 재시작 중 offset 검사).

- **대조 작업(15초마다, 정리 task의 3번째 주기):** 노드가 자기 상태를 클러스터 표와 맞춘다(`RealtimeCore::reconcile`).
  - **클러스터가 이 노드를 모를 때**(노드 목록에 없음): Redis가 데이터 없이 재시작했거나, 노드가 `slot_ttl_s` 이상 끊겨 죽은 것으로 판정된 경우다. 노드를 다시 등록하고, 로컬 세션 전부를 세션 표에, 로컬 멤버십 전부를 멤버 표에 다시 넣는다. **아무도 끊지 않는다.**
    - 멤버십에는 원래 알림 여부가 필요하다. 그래서 `Member.notify`를 두었다(입장 때 테넌트 `presence_events`).
  - **알 때:** 로컬 세션 중 세션 표에 없는 것을 `replaced`로 닫는다. 다른 노드에서 교체·`kick_oldest`가 일어났는데 닫기 명령을 잃은 경우다.
  - 순서상의 경합: 방금 끝난 세션이 "없음"으로 잡혀도 닫기 요청은 아무 일도 하지 않는다(이미 레지스트리에 없음). 새 세션은 차지 후에 레지스트리에 들어가므로 "없음"으로 잡히지 않는다.
  - 알려진 경합: Redis 재시작 직후, 대조 전에 같은 sid로 다른 노드에 재접속하면, 대조가 옛 세션을 다시 넣어 같은 sid가 둘이 될 수 있다. 다음 재접속이나 수동 disconnect로 정리된다(문서화).
- **슬롯 상실:** 하트비트가 슬롯이 다른 노드 것임을 보면 Broker가 비정상(`healthy() = false`)이 된다. 그러면 게이트웨이 `/readyz`가 503이 되어 오케스트레이터가 트래픽을 빼고 재시작한다. member id가 겹칠 수 있는 상태로 계속 받지 않기 위해서다. 슬롯을 새로 받아 계속 도는 방식은 기존 member id와 섞여 기각했다.
- **테스트:**
  - 엔진: 모든 것을 잊은 Broker에 세션·멤버십이 복원되고 아무도 닫히지 않음. 표에서 빠진 세션만 닫힘.
  - 실제 Redis:
    - 접두사 키를 모두 지운 뒤 presence가 복원되고, single 사용자의 두 번째 세션이 다시 거절되며, 기존 연결은 그대로임
    - 세션 표 항목을 지우면 그 세션이 `replaced`로 닫힘
    - 슬롯 키를 남이 차지하면 `/readyz` 503

## R4-2 구현 (2026-10-20): 클러스터 presence

- **멤버 표:** `<prefix>:pr:{tenant::room}` 해시에 세션 키 → `노드 id|슬롯|사용자|member id|알림`을 둔다. 노드별 룸 색인(`<prefix>:nr:<노드 id>`, 룸 구독 해제 때 SREM)과 노드 목록(`<prefix>:nodes`)도 둔다.
- **기록 순서:** 입장·퇴장·세션 종료에서 `PresenceOp`를 송신 큐에 넣는다. 같은 노드의 `member_joined` 프레임보다 먼저 넣으므로 Redis에도 먼저 반영된다. 배출 루프는 연속된 멤버 변경을 한 번에 보낸다(입장이 몰려도 왕복 한 번). 프레임·구독 명령과 섞이면 경계에서 끊어 순서를 지킨다.
- **입장 스냅샷:** 클러스터에서는 모든 입장이 비동기 경로(`join_room_cluster`)를 탄다. 이 노드의 룸 구독이 적용된 뒤 표를 읽는다. 그러면 읽은 뒤 다른 노드에 들어온 사람은 이벤트로 받는다. 그 노드에서는 표 반영 → 이벤트 발행 순서이고, 우리 노드는 이미 구독 중이기 때문이다. `JoinOutcome.members`로 옮겨, 단일 노드는 지금처럼 로컬 스냅샷을 쓴다.
- **서버 API presence:** 표의 살아 있는 멤버(죽은 노드 항목 제외)를 사용자 단위로 묶는다.
- **죽은 노드 정리:** 각 노드가 5초마다 노드 목록을 보고, 슬롯 키가 그 노드의 것이 아니면 죽은 것으로 본다. `SET NX EX 60`으로 정리권을 잡은 노드가 색인의 룸마다 `REAP_ROOM` Lua로 그 노드 멤버를 지우고 반환한다. 엔진은 알림이 켜진 멤버에 대해 `member_left`를 발행한다.
  - **정확히 한 번의 근거는 Lua의 원자성이다.** 찾기와 지우기가 한 스크립트 안에서 일어난다. 정리권과 `HDEL == 1` 조건은 중복 작업을 줄이는 이중 장치다.
  - 테스트 때 확인했다. 둘을 모두 없애도 Broker 2개 × 16회 동시 정리에서 결과는 같았다(그래서 결과 테스트만으로는 두 장치를 검증하지 못한다. 기록해 둔다).
- **알려진 한계(R5에서 다룸):**
  - 살아 있는 노드라도 Redis와 `slot_ttl_s` 이상 끊기면 죽은 것으로 판정돼 멤버가 정리되고 `member_left`가 나간다. 연결이 돌아오면 하트비트가 슬롯을 되찾지만 표는 비어 있다. 자기 세션과 표를 대조하는 작업이 필요하다.
  - 정상 종료도 정리를 끝내지 못한 세션은 같은 경로(최대 `slot_ttl_s` + 5초 뒤)로 정리된다.
- **테스트:**
  - 엔진: 멤버 변경이 순서대로 Broker에 반영되는지, 죽은 노드 멤버의 `member_left`.
  - 게이트웨이 Queued 전체(서버 API presence 포함).
  - 실제 Redis 2노드: 다른 노드 멤버가 스냅샷에 있음, 서버 API가 두 노드 사용자를 모두 나열, 죽은 노드 멤버의 `member_left`를 두 노드의 각 멤버가 정확히 한 번 받음.
  - Redis 크레이트: 동시 정리 16회의 결과가 정확히 한 번.
  - ACL 최소 권한에 `SADD`·`SREM`·`SMEMBERS`를 더해 실측했다.
- **B2 (단일 노드, `icount-r4`):** 처음 측정에서 disconnect가 +2.0%였다. 원인은 멤버 변경을 기록할지 확인하기 전에 기록할 내용(`Arc` 할당)을 만든 것이었다. 확인을 먼저 하도록 고친 뒤 R1 전 기준선 대비 churn +0.02%, disconnect −0.5%, 나머지 ±0.4%다.

## R4-1 설계 (2026-10-20): 세션 소유권과 노드 간 제어

R4는 둘로 나눈다. **R4-1** 세션 소유권·노드 간 제어(이 절), **R4-2** 클러스터 presence 저장소·죽은 노드 정리.

**지금 클러스터에서 틀린 것 (코드 확인):**
1. 같은 sid 재접속(S4)이 다른 노드의 이전 연결을 교체하지 못한다. 같은 sid의 연결 둘이 남는다.
2. `max_sessions_per_user`와 `mode: single`을 노드마다 센다. 두 노드에 동시에 접속하면 넘는다.
3. 서버 API disconnect가 요청을 받은 노드의 세션만 끊는다.

**결정:**
- **사용자 세션 표를 Redis에 둔다**: `<prefix>:us:{tenant::user}` 해시. 필드는 세션 키(연결마다 유일), 값은 `노드 id|슬롯|sid|생성 ms`다.
- **입장 시 Lua 하나로 원자적으로 차지한다**(A9 "정확하게"). 스크립트는 다음을 한 번에 한다.
  - 죽은 노드의 항목 정리: 그 슬롯 키의 값이 항목의 노드 id와 다르면 버린다. 노드가 죽으면 그 세션은 자동으로 사라진다.
  - 같은 sid 교체
  - 상한 검사(`deny` / `kick_oldest`, 가장 오래된 항목)
  - 새 항목 등록
  - 결과로 내보낼 세션 목록(노드 슬롯·세션 키·이유)을 돌려준다.
  - 노드 여럿이 동시에 받아도 Redis가 직렬화하므로 정확히 하나만 남는다. 개정 1 A9는 `max_sessions_per_user`(multi)를 근사로 두었지만, 같은 스크립트로 정확하게 할 수 있어 근사로 두지 않는다. 테넌트 전체 세션 수(`max_sessions_total`)는 여전히 노드별이다(§8).
- **노드 간 제어 채널은 노드마다 하나**(`<prefix>:ctl:<슬롯>`, 시작할 때 구독)다.
  - §6의 "사용자별 채널(참조 계수)"은 기각했다. 접속·종료마다 구독·해제가 생기기 때문이다. 대신 내보낼 세션이 어느 노드에 있는지는 세션 표가 알려 주므로 그 노드에만 보낸다.
  - 메시지: `CloseSessions { keys, reason }`(노드 간 형식 kind 6, JSON). 받는 노드는 해당 세션에 닫기를 요청한다. 등록 해제·presence·메트릭은 세션 자신의 정리(RAII)가 한다.
  - 슬롯이 재사용돼 엉뚱한 노드가 받아도 그 세션 키가 없으니 아무 일도 없다.
- **종료 시 해제:** 세션 정리에서 `HDEL`을 비동기로(fire-and-forget) 한다. 필드가 연결마다 유일하므로 새 세션의 항목을 지울 일이 없다. 해제가 실패해도 다음 차지 때 죽은 노드 규칙이나 시간이 정리한다(살아 있는 노드의 유령 항목은 R5에서 대조 작업으로 다룬다).
- **서버 API disconnect:** 세션 표에서 그 사용자(와 sid)의 세션을 찾아 로컬은 바로 닫고, 다른 노드에는 제어 메시지를 보낸다. 응답의 `closed`는 대상 수다.
- **Redis 장애 시 새 접속은 1013(try again later)이다(실패 시 닫힘).** 세션 상한을 지킬 수 없기 때문이다. 이미 연결된 세션은 유지한다.
- **경계:** 엔진 `Broker::sessions() -> Option<&dyn SharedSessions>`(B6의 `claim_session`). Broker가 이것을 갖고 있으면 게이트웨이는 노드 로컬 검사 대신 이것을 쓴다. `TestBroker`도 메모리로 구현해서, 게이트웨이 테스트 전체(Queued)가 이 경로를 탄다.
- **남는 위험(R5):** 제어 메시지를 잃으면(노드 구독 연결이 끊긴 순간) 교체된 세션이 그 노드에 남는다. 세션 표는 이미 새 세션 것이므로, 노드가 주기적으로 자기 세션이 표에 있는지 대조해 정리하는 방식을 R5에서 넣는다.

## R3-3 구현 (2026-10-20): 공유 1회용 티켓

- **Broker의 공유 키-값(B6의 `kv`):** `SharedKv { put_once(key, value, ttl), take(key) }`, `Broker::kv() -> Option<&dyn SharedKv>`. Redis는 `<prefix>:kv:<key>`에 `SET NX PX`와 `GETDEL`(Redis 6.2+)을 쓴다. 원자적이라 여러 노드가 같은 티켓을 동시에 내밀어도 한 곳만 성공한다.
- **티켓 저장소:** Broker에 공유 키-값이 있으면 그것을, 없으면 지금처럼 프로세스 메모리를 쓴다(`TicketStore::for_broker`). 발급과 소비가 비동기가 됐다.
- **키는 티켓의 SHA-256**(`tk:<hex>`)이다. Redis를 읽을 수 있는 사람(운영자, 백업)이 키로 로그인할 수 없다. 값은 테넌트·사용자·권한 패턴의 JSON이다(`Permissions::to_lists`).
- **실패 시 닫힘(§9):** Redis에 닿지 않으면 티켓 로그인은 503 + `Retry-After`, 발급(서버 API)도 503 + `Retry-After`다.
- **상한:** 메모리 저장소의 `MAX_TICKETS`(100만)는 Redis에서는 적용하지 않는다. TTL(최대 300초)이 크기를 묶고, Redis 메모리는 운영자가 관리한다(문서화).
- **테스트:**
  - 티켓 테스트 묶음(단위 3, 통합 20)을 단일 노드와 Queued(TestBroker 공유 키-값) 양쪽에서 돌린다.
  - 실제 Redis 2노드: A 노드 발급 → B 노드에서 로그인(권한 유지) → A 노드에서 재사용하면 401, Redis 키에 티켓 원문 없음.
  - ACL 최소 권한에 `GETDEL`을 추가해 다시 실측했다.
- **B2:** 티켓은 메시지·입장 경로에 없으므로 명령어 수·메모리 측정 대상이 아니다(엔진 변경은 트레이트 기본 메서드와 권한 직렬화뿐).

## R3-2 구현 (2026-10-20): 클러스터 이력·복구

### 만든 것

| 항목 | 위치 | 내용 |
|---|---|---|
| 보관 프레임 | 엔진 `BrokerFrame.keep`·`offset`, 노드 간 형식 kind 4 | 이력 룸의 메시지는 `keep`(규칙의 한도)을 달고 송신 큐로 간다. 본문에는 `room`만 붙이고(`stamp(None)`), offset은 Broker가 정한다. kind 4는 offset을 본문 바로 앞에 `u8 길이 + 10진수`로 둔다. Lua가 헤더와 본문 사이에 끼워 넣을 수 있도록 하기 위해서다 |
| Redis 발행 | `PUBLISH_KEPT` Lua(`EVALSHA`, 파이프라인 안) | `INCR` offset → `ZADD`(점수 = offset, 멤버 = `<ms>:<프레임>`) → 개수·바이트·나이로 정리 → `PUBLISH`. 하나의 스크립트라 offset 순서 = 저장 순서 = 전달 순서다. 키는 룸 해시 태그 하나: `:seq`·`:epoch`·`:log`·`:bytes` |
| Redis 읽기 | `READ_KEPT` Lua | 위치(`epoch`, 꼭대기)와 재개 가능 여부(같은 epoch, 앞서지 않음, 틈 없음) 및 놓친 프레임 |
| 일부 유실 감지 | 두 스크립트 공통 | `:seq`나 `:epoch` 중 하나라도 없으면 새 epoch를 만들고 저장분을 지운다. 축출·재시작 뒤 "같은 epoch, 다른 의미의 offset"이 생기지 않는다 |
| 위치 수명 | `POSITION_TTL` 24시간 | 조용한 룸의 `:seq`·`:epoch`는 마지막 메시지·입장 뒤 24시간 유지. `:log`·`:bytes`는 `ttl_s` |
| 수신 노드 | `deliver_incoming` | offset을 본문 앞에 한 번 붙여 수신자들이 공유. 멤버의 `skip_upto` 이하는 건너뜀(아래 3) |
| 복구 입장 | `RealtimeCtx::join_room_recovering`(비동기), `RoomService` | 아래 「순서 보장」 |
| SDK | 변경 없음 | 같은 프로토콜(`offset`, `recover`, `recovered`) |

### 순서 보장 (클러스터에서는 이력 읽기가 비동기)

1. 멤버를 **보류 연결**로 추가한다. 이 연결은 1,000칸 채널과 자체 신호를 가진다. 그 순간부터 그 룸의 프레임은 보류 채널에 쌓인다.
2. **이 노드의 룸 구독이 실제로 적용될 때까지 기다린다**(룸마다 `watch`, 송신 큐가 Subscribe 적용 후 켬, 최대 5초). 구독 전에 이력을 읽으면 그 사이 발행분이 이력에도 라이브에도 없게 된다.
3. Redis에서 이력을 읽는다(`READ_KEPT`).
4. 응답과 재전송 묶음(`OutFrame::Batch`)을 진짜 큐에 넣는다.
5. **룸 쓰기 락 안에서** 멤버의 연결을 진짜 연결로 바꾸고, `skip_upto` = 읽은 위치로 둔다. 같은 락 안에서 보류분 중 위치 이후 것만 진짜 큐로 옮긴다. 락이 팬아웃을 막으므로 그 뒤 프레임은 옮긴 것보다 뒤에 온다.
6. 보류 채널이 넘쳤으면 `sys.gap`을 보낸다(A11 상한).

**`skip_upto`가 필요한 이유 (테스트가 찾은 결함):** Redis가 offset 244를 발행했지만 아직 이 노드의 수신 채널에 실려 오는 중이었다. 그 사이 이력 읽기가 "꼭대기 244"를 보고 연결을 바꾸면, 244가 진짜 연결로 한 번 더 도착했다. 동시 발행 경쟁 테스트의 첫 실행에서 재현됐다. 멤버별 `skip_upto`는 **클러스터 이력 프레임 경로에서만** 확인하므로 일반 팬아웃 비용은 그대로다. 대가로 멤버당 8바이트가 는다.

### 결정

- **Queued + 이력 = Broker가 보관한다.** R2의 "함께 설정하면 기동 실패"를 없앴다. 노드는 규칙(한도)만 안다.
- **발행이 실패해 재시도하면(`NOSCRIPT` 등) 메시지가 두 번 보관·전달될 수 있다.** 파이프라인의 앞선 명령은 이미 실행됐기 때문이다. Redis가 스크립트를 잊는 경우(재시작)에만 일어나고, 두 번째 사본은 새 offset을 받는다. 클라이언트에게는 같은 내용의 메시지 두 개로 보인다. 정확히 한 번 발행하려면 메시지 id 기반 중복 제거가 필요한데, 이는 R5 카오스 결과를 보고 결정한다.
- **Redis 메모리 정책:** 이력에는 `noeviction`(또는 `volatile-*`)을 권한다(CONFIG.md). 축출되더라도 새 epoch로 안전하게 무너진다.
- **클러스터에서는 세션 큐를 충분히 크게(기본 1024):** Redis에서 받은 프레임은 묶음(최대 256)으로 오기 때문에, 32칸 큐 테스트에서는 잘 읽는 클라이언트도 느린 수신자로 끊겼다. 작은 큐를 쓰는 테스트 하나(느린 수신자)는 Queued 모드에서 건너뛰고, 같은 성질(큐보다 큰 재전송)은 결정적 테스트가 두 모드 모두에서 검증한다.

### 테스트

- 엔진:
  - **클러스터 경로 동시 발행 경쟁:** 발행 스레드 2개 + 입장·퇴장·복구 재입장 반복. offset이 연속인지, gap이 없는지 본다(2,000개 이상, 20회 반복 통과).

  - 노드 간 형식 kind 4 왕복, `stamp(None)`·`prepend`·`offset_of`.

## R3-1 구현 (2026-10-20): Redis로 노드 간 룸 공유

R3는 크기 때문에 나눈다: **R3-1** 발행·구독·노드 슬롯·gap(이 절), **R3-2** 클러스터 이력(Redis offset·비동기 복구 버퍼링), **R3-3** 공유 1회용 티켓, 마지막으로 Redis 처리량 측정(A15). 사용자 승인(2026-10-20 "진행"): `redis` 크레이트 다운로드, 테스트용 `redis:7` 이미지(이미 로컬에 `redis:7.2`가 있어 받지 않음).

### 결정 (구현 중)

1. **`Broker::node_slot()`을 비동기 `start()`로 바꿨다.** 슬롯 임대는 네트워크가 필요한데 `GatewayBuilder::build()`는 동기 함수다. 그래서 `serve`가 연결을 받기 **전에**(서버 API 리스너보다도 먼저) `core.start().await`로 슬롯을 받는다. 노드 슬롯·presence의 슬롯 비트는 원자 변수다(입장마다 원자 읽기 1회, 명령어 수 변화는 측정 오차 수준).
2. **Redis에 연결할 수 없으면 기동하지 않는다.** 슬롯 없이 받은 입장은 member id가 겹칠 수 있다. 오케스트레이터가 재시작하는 편이 안전하다.
3. **구독 명령은 해당 구독 연결 task가 순서대로 적용하고, 끝나면 응답한다.** 연결이 끊긴 동안 명령은 `Unavailable`로 돌아가고 송신 큐가 재시도한다. 연결 task는 재연결 뒤 자기 룸 집합을 다시 구독한다.
4. **최소 권한 ACL을 실측으로 정했다.** 제한 사용자로 클러스터 테스트를 돌려 Redis ACL 로그로 확인했다(CONFIG.md). `SCRIPT LOAD`가 빠지면 라이브러리가 `EVAL`로 대신하므로 동작은 하지만, 넣는 편이 효율적이다.
5. **`xxhash-rust`(BSL-1.0)를 cargo-deny 허용 목록에 추가했다.** `redis`의 필수 의존성이다. OSI 승인이고, 바이너리 배포에는 고지 의무가 없다.

### 설계와 다르게 한 점 (구현 중 결정)

1. **경합 처리를 세션 버퍼링 대신 락으로 했다.** 단일 노드에서는 이력이 동기라서, 발행(offset·저장·팬아웃)과 복구 입장(멤버 추가·응답·재전송)을 같은 룸 이력 락 안에서 한다. 그러면 "복구 중 라이브 메시지 모아 두기"가 필요 없다(§3의 버퍼링, 개정 1 A11의 1,000건·1 MiB 상한은 비동기 이력인 R3에서 쓴다).
   - 락 순서: 이력 락 → presence shard 락. presence 락을 쥔 채 이력 락을 잡는 곳은 없다. 스위퍼는 이력 맵 shard → 링 락 → presence 읽기 순이다.
   - 대가: 이력 룸 하나의 발행은 직렬화된다. 룸 단위 순서를 보장하려면 어차피 필요하고, 이력이 없는 룸은 그대로다.
2. **재전송 크기를 세션 큐 여유분으로 제한하려다 버렸다.** 느린 수신자는 큐가 넘쳐서 끊기므로 놓친 양이 **정의상 큐보다 크다**. 큐 여유분으로 제한하면 C1 수신자는 영영 복구할 수 없다(경로 테스트를 쓰다가 발견). 그래서 재전송분을 `OutFrame::Batch` 하나로 넣는다. 크기는 이력의 `max_bytes`로 이미 묶여 있다.
3. **presence 이벤트는 이력에 넣지 않는다.** `sys.joined`의 스냅샷은 "지금"이다. 그 뒤에 더 오래된 입장·퇴장 이벤트를 다시 보내면 클라이언트의 멤버 목록이 틀어진다.
4. **`offset`·`room`은 `Map::insert` 대신 직렬화된 텍스트 앞에 붙인다.** 처음에는 Map에 넣었다. 그러자 엔진 크레이트에 `BTreeMap::insert` 호출 지점이 하나 늘었고, 컴파일러가 크레이트 전체에서 그 함수를 인라인하지 않게 됐다. 그 결과 이력을 켜지 않은 경로까지 느려졌다(churn +2.5%, ext 전달당 +1.7%; callgrind 함수별 비교로 확인). 텍스트 앞에 붙이면 같은 JSON이 나오고 기준선과 같은 비용으로 돌아온다(`stamp`, 단위 테스트 있음).
5. **메시지에 `room`이 없으면 넣는다.** 서비스가 `room` 없이 발행하면 클라이언트가 그 offset이 어느 룸 것인지 알 수 없기 때문이다. 메시지의 최상위 `offset`은 프로토콜 필드로 예약되어 덮어쓴다(PROTOCOL.md에 명시).
6. **Queued Broker와 이력을 함께 설정하면 기동이 실패한다.** 노드별 링은 클러스터에서 틀린 답(노드마다 다른 offset)을 내기 때문이다. 이력은 R3에서 Broker의 `history`로 옮긴다.

### 설계와 다르게 한 점 (구현 중 결정)

1. **`publish`·`subscription`은 비동기이고, 엔진의 task 하나만 부른다**(B6 표는 "동기, 큐에 넣기"). 큐는 이미 엔진(송신 큐)에 있으므로 Broker마다 큐를 또 두지 않는다. Redis 구현은 받은 묶음을 파이프라인 한 번으로 보내고 끝나면 반환하면 되고, 순서·재시도·할당량은 엔진이 한 곳에서 맡는다.
2. **Inline Broker는 아예 호출하지 않는다.** B4의 "Inline: 비용 0"을 문자 그대로 지키기 위해서다. `MemoryBroker::publish`를 빈 함수로 부르는 것조차 하지 않는다. 그래서 "모든 경로가 Broker를 거치는가"(B3)는 Queued 모드에서 검증한다. 분기점이 두 함수뿐이라 Inline과 Queued가 다른 경로를 탈 수 없다.
3. **검증용 Broker는 하나(`TestBroker`)로 두 역할을 한다.** 기록(발행 프레임·구독 명령)과 장애 주입(지연·`Unavailable`·`Rejected`·일시 정지)을 한 타입에 넣었다. 루프백은 **구독된 룸의 프레임만** 돌려준다. 그래서 구독 누락은 실제 Broker에서처럼 메시지 유실로 드러난다. 구독 명령이 상태와 맞지 않으면(이중 구독, 없는 구독 해제) `anomalies`로 센다.
4. **게이트웨이 테스트 전체를 Queued 모드로도 돌린다** (`WSPRISM_TEST_BROKER=queued`, CI 단계 추가). 경로 테스트만으로는 놓칠 수 있는 동작 차이(순서, 응답 시점)를 기존 테스트 전부로 확인한다.
5. **Queued 모드의 `publish_room` 반환값**(서버 API `recipients`)은 발행 시점의 로컬 멤버 수다. 클러스터 전체 수는 발행 시점에 알 수 없다. R3에서 의미를 다시 정한다.

### 확인된 동작 (문서화)

- **첫 입장자도 `member_joined`를 발행한다**(지금 받는 사람은 0명). 다른 노드의 멤버가 있을 수 있으므로 클러스터에서는 맞는 동작이다.
- **룸이 비워졌다가 다시 생기면 member id가 1부터 다시 시작한다.** 룸 id(`chan`)는 새로 발급되므로 멤버십은 `(chan, member_id)`로 구분되고, SDK의 오래된 프레임 기록도 이 쌍을 키로 쓴다(`forgetSender`). SDK 테스트 하나가 "재접속 후 member id가 달라야 한다"고 가정하고 있어서 쌍을 비교하도록 고쳤다.
- **틱 송신은 별도 룸 경로가 아니다.** 팬아웃 뒤 세션별 Hot 슬롯을 비우는 송신 측 동작이라, 들어온 프레임도 같은 로컬 팬아웃을 거쳐 슬롯에 들어간다. B3 목록의 "틱 송신"은 그래서 따로 시험하지 않는다.

## 개정 2 (2026-10-19): 외부 검토 2차 반영 — R1 착수 조건

### B1. member id = 노드 슬롯 + 룸별 카운터 (개정 1 A1 대체)

A1(전역 카운터 구간 임대)은 계산은 적었지만 결론이 틀렸다. u32 전역 공간은 클러스터 전체 입장 속도에 따라 이렇게 소진된다.

| 클러스터 입장 속도 | 한 바퀴 |
|---|---|
| 초당 1,000 | 약 50일 |
| 초당 10,000 | 약 5일 |
| 초당 50,000 | 약 1일 |

24시간 열려 있는 로비·대시보드처럼 며칠씩 접속한 멤버가 있으면 실제로 충돌한다. 노드가 재시작하면 받아 둔 구간의 남은 id도 버려진다. 게다가 id를 다시 쓰면, presence 이벤트를 끈 테넌트에서는 수신자의 오래된 프레임 판정 기록 때문에 새 멤버의 프레임이 버려진다.

**결정:** `member_id(u32) = 노드 슬롯(상위 10비트) | 그 노드의 룸별 카운터(하위 22비트)`.
- **노드 슬롯:** 기동할 때 Broker에서 한 번 임대한다(Redis `SET NX` + heartbeat TTL). 죽은 노드의 슬롯은 그 노드 멤버의 presence 정리가 끝난 뒤에야 재사용한다(슬롯 TTL > presence TTL). 단일 노드·`MemoryBroker`는 슬롯 0이다. 최대 1,024 노드.
- **룸별 카운터:** 노드가 룸마다 갖고, 발급할 때 **그 룸의 살아 있는 로컬 멤버 id를 건너뛴다.** 노드는 자기 로컬 멤버를 전부 알기 때문에, 슬롯과 함께 **클러스터 전체에서 정확히 유일**하다(확률이 아니다).
- 한 바퀴는 "한 노드에서 한 룸에 약 419만 번 입장"해야 일어나므로 사실상 격리 시간이 된다. 그래도 남는 오래된 판정 기록 위험은, 같은 id 재사용이 아주 드문 대형 룸에 한정된다(문서화; presence 이벤트를 켜면 SDK가 퇴장 멤버의 기록을 지운다).
- **와이어(Hot v2 `sender` u32)는 그대로**이고, 입장은 동기이며 Redis 왕복이 없다.
- 기각: `sender`를 u64로 확장 — 배포 전이라 가능하지만, 프레임마다 4바이트가 늘고 슬롯 방식으로 정확성을 이미 얻는다.

### B3. 검증용 Broker 두 개를 R1 범위에 넣는다

- **기록 Broker (`RecordingBroker`, 테스트 전용):** 모든 발행을 기록한다. **룸으로 가는 모든 경로가 Broker를 거치는지** 테스트한다. 단일 노드에서는 Broker를 우회해도 기존 테스트가 다 통과하므로, 이것 없이는 R3에서 "다른 노드 멤버만 못 받음"으로만 드러난다.
  - 대상 경로: Ext 발행(서비스·RPC가 룸에 보내는 것 포함), 서버 API 발행(Ext·Hot), presence 이벤트 전 경로(입장, 퇴장, 연결 종료, 밀려남, 서버 API disconnect), Hot relay(로컬 우선이어도 Broker로 방송), 틱 송신, `sys.gap`.
  - 대상이 아닌 것: 자기 세션 응답(`reply`, `DeferredReply`), 사용자 대상 전송(`send_to_user`)은 R4의 사용자 제어 채널에서 따로 검증한다.
- **장애 주입 Broker (`FaultBroker`, 테스트 전용):** 지연·실패·큐 포화를 주입한다. 이것으로 R1에서 검증하는 것은 `UNAVAILABLE` 경로, 테넌트별 할당량(B4), 구독 참조 계수의 경쟁 조건(B5)이다.

### B4. 송신 큐와 테넌트 할당량은 엔진 공통부에

Broker 구현마다 백프레셔를 다시 만들지 않도록 엔진에 공통 `BrokerOutbox`를 둔다. 하는 일은 테넌트별 몫, 가득 찼을 때의 정책(Reliable은 `UNAVAILABLE`, Lossy는 버림), 묶어 보내기(A3)다. Broker는 `mode()`로 둘 중 하나를 밝힌다.
- **Inline:** `MemoryBroker`. 큐 없이 바로 호출하며 비용이 0이다.
- **Queued:** Redis 등. Outbox를 거친다.

### B5. 구독 참조 계수는 룸 생성·삭제와 같은 락 안에서, 명령은 순서대로

Broker 구독은 비동기라 shard 락 안에서 기다릴 수 없다. 그래서 룸이 생기고 비워지는 바로 그 shard 락 안에서 **순서 있는 `Subscribe`/`Unsubscribe` 명령을 큐에 기록만** 하고, Broker가 그 순서대로 적용한다. "마지막 멤버 퇴장(해제)"과 "새 멤버 입장(구독)"이 경쟁해도 명령 순서가 실제 순서와 같으므로, 끝 상태가 올바르다. `FaultBroker`(명령 적용 지연)로 검증한다.

### B6. 트레이트의 전체 형태를 지금 정하고, 공개는 R3 이후

엔진과 게이트웨이가 다른 크레이트라 트레이트는 `pub`이어야 한다. 그래서 (1) 알려진 연산의 동기/비동기 형태를 지금 모두 정하고, (2) `spi::broker`에 "실험적 — R3 전까지 외부 구현 금지, 변경 예정"을 명시한다. R1은 R1 연산만 구현하고, 나머지는 단계에서 채운다.

| 연산 | 형태 | 단계 |
|---|---|---|
| `mode() -> Inline \| Queued` | 동기 | R1 |
| `publish(frames)` — 룸 프레임 묶음(Outbox가 부름; Inline은 즉시 로컬 전달) | 동기(큐에 넣기) | R1 |
| `subscription(cmd)` — 순서 있는 구독·해제(B5) | 동기(큐에 넣기) | R1 |
| `incoming() -> BrokerRx` — 들어오는 프레임·제어·gap | 동기(수신기 반환) | R1(Memory는 빈 것) |
| `node_slot() -> u16` | 동기(기동 때 임대해 둔 값) | R1(Memory 0), 임대는 R3 |
| `history(room, since, limit)` | 비동기 | R2 |
| `kv()` — 티켓·presence 공유 저장소 | 비동기 | R3/R4 |
| `claim_session(...)` — 세션 소유권(A9) | 비동기 | R4 |
| `control(target, cmd)` | 동기(큐에 넣기) | R4 |

## 배경 (지금 구조에서 확인한 사실)

- **노드 하나에 갇혀 있다.** 세션 레지스트리·presence·룸 id·member id·1회용 티켓이 모두 프로세스 메모리에 있다. 노드를 늘려도 룸을 공유할 수 없어서 수평 확장이 안 되고, 노드가 죽으면 그 노드의 모든 상태가 사라진다(HA 없음).
- **끊기면 잃는다.** 끊긴 사이의 룸 메시지를 되찾을 방법이 없다. 그런데 느린 수신자는 일부러 끊는다(C1: "끊고 재동기화"). 그 재동기화 수단이 지금은 "클라이언트가 자기 백엔드에서 알아서"뿐이다. 모바일처럼 잠깐 끊기는 환경에서 채팅·이벤트가 사라진다.
- **경계는 좋다.** 발행은 거의 전부 엔진의 `RealtimeCore`(`publish_room*`, `send_to_user`, `DeferredReply`)를 거친다. 게이트웨이가 엔진 내부를 직접 만지는 곳은 몇 군데뿐이다: 서버 API(presence 조회·사용자 연결), admission(세션 수·sid 교체), `Gateway::session_count`. 그래서 Broker를 끼우는 위치가 분명하다.
- **노드마다 따로 매기는 id:** 룸 id(v2 `chan`)와 member id(v2 `sender`)가 노드별 카운터다. 클러스터에서는 같은 룸이 노드마다 다른 id를 갖고, 다른 노드의 member id와 충돌할 수 있다.
- Centrifugo(동급 경쟁 제품)는 Broker(Redis/NATS)·채널 이력(epoch+offset)·자동 복구를 모두 갖췄다. "대기업급"의 최소 조건이다.

## 목표와 비목표

**목표**
1. **수평 확장:** 노드 N개가 같은 룸을 공유한다. 어느 노드에 발행해도 모든 노드의 멤버에게 간다. 로드밸런서 고정 세션(sticky)이 필요 없다.
2. **복구:** 끊긴 클라이언트가 (다른 노드로) 다시 붙으면, 보존 기간 안의 놓친 룸 메시지를 순서대로 받는다. 못 받으면 "복구 실패"를 분명히 알린다.
3. **HA:** 노드 하나가 죽어도 클라이언트는 다른 노드로 붙어 복구한다. 죽은 노드의 멤버는 다른 멤버에게 퇴장으로 보인다.
4. **클러스터 제어:** 서버 API의 disconnect·presence, sid 교체, 1회용 티켓이 노드와 무관하게 동작한다.
5. **단일 노드는 그대로 빠르다.** 단일 노드 설정에서는 네트워크 홉도 추가 비용도 없어야 한다(인메모리 Broker).

**비목표 (이번에는 하지 않음):** Hot 레인 이력(상태는 최신값이라 클라이언트가 주기적으로 다시 보낸다), 정확한 클러스터 전역 상한(근사치로 둔다, §8), NATS·Kafka 구현(경계만 열어 둔다), 지역 간(multi-region) 복제.

## 결정

### 1. 엔진에 `Broker` 경계 (spi)

```rust
/// 노드 사이의 팬아웃·이력·제어. 엔진은 이것만 안다(Redis를 모른다).
#[async_trait]
pub trait Broker: Send + Sync + 'static {
    /// 룸 메시지를 클러스터에 발행. 이력이 켜진 룸이면 offset을 매겨 저장하고 돌려준다.
    fn publish(&self, room: &RoomKey, frame: BrokerFrame) -> Result<PublishTicket>;
    /// 이 노드가 룸을 구독/해제 (엔진이 로컬 멤버 수로 참조 계수).
    async fn subscribe(&self, room: &RoomKey) -> Result<()>;
    async fn unsubscribe(&self, room: &RoomKey) -> Result<()>;
    /// `since` 이후의 이력 (복구).
    async fn history(&self, room: &RoomKey, since: StreamPos, limit: usize) -> Result<History>;
    /// 사용자·노드 대상 제어 명령 (disconnect, sid 교체 …).
    fn control(&self, target: ControlTarget, cmd: ControlCmd) -> Result<()>;
    /// 들어오는 프레임·제어·"구독이 끊겼었음(gap)" 알림의 수신 스트림.
    fn incoming(&self) -> BrokerRx;
    /// 룸 안에서 유일한 member id 발급 (§5).
    async fn next_member_id(&self, room: &RoomKey) -> Result<u32>;
    /// 공유 키-값 (1회용 티켓, presence).
    fn kv(&self) -> &dyn SharedKv;
}
```

- **인메모리 Broker(`MemoryBroker`)가 기본값**이다. 지금 동작을 그대로 옮긴 것이라 단일 노드에서는 아무것도 바뀌지 않는다. 이력·복구(§3)도 메모리 링 버퍼로 동작하므로, **M3는 Redis 없이도 쓸 수 있다**(잠깐의 네트워크 끊김 복구).
- **Redis Broker**가 첫 외부 구현이다(§9). 설정 `gateway.broker: { kind: redis, url: ... }`.
- **`publish`는 동기 함수(대기 없음)다.** 서비스 코드(`ctx.publish_room_*`)가 지금처럼 동기로 남는다. Redis 구현은 노드별 송신 task의 유한 큐에 넣는다. 큐가 가득 차면 Reliable은 `UNAVAILABLE`, Lossy는 버린다.

### 2. 순서 규칙: 레인마다 다른 경로

| 메시지 | 경로 | 이유 |
|---|---|---|
| **Ext Reliable** (채팅, 서버 발행, 이벤트) | **Broker를 거쳐서**(발행 노드도 Broker에서 받아 전달) | 클러스터 전체가 같은 순서로 본다. 이력 offset이 그 순서다 |
| **Hot Lossy** (상태) | **로컬 먼저** 전달 + Broker로 다른 노드에 방송(원래 노드는 자기 것을 건너뜀) | 지연이 생명이다. 상태는 최신값이고, 순서는 `(sender, key)`별 `seq`로 이미 해결돼 있다 |

- 대가: Reliable은 Redis 왕복(같은 LAN에서 약 0.2~0.5 ms)만큼 늦어진다. 인메모리 Broker에서는 추가 지연이 없다.
- 기각: 모두 로컬 먼저 — 두 노드에서 동시에 발행하면 노드마다 순서가 달라지고, 이력 offset과 실제 전달 순서가 어긋난다.

### 3. 이력·복구 (M3)

- **룸 패턴별로 켠다(기본 꺼짐):** `tenants[].history: [{ rooms: "chat:*", size: 200, ttl_s: 600 }]`. 이력은 메모리(또는 Redis)를 쓰므로 필요한 룸만 켠다.
- **위치 = `epoch` + `offset`.** offset은 룸별 단조 증가 u64이고, epoch는 그 이력 저장소의 수명 식별자다. Redis 재시작이나 이력 유실이 나면 epoch가 바뀌므로, 클라이언트는 "이어 받기"가 불가능하다는 것을 알 수 있다.
- **v2에 추가(하위 호환, 필드 추가만):**
  - 이력 룸의 메시지에 `"offset": n`이 붙는다.
  - `room.join`에 `"data": {"recover": {"epoch": "e", "offset": n}}`를 실을 수 있다.
  - `sys.joined`에 `"epoch"`, `"offset"`(현재 위치)과 복구 결과 `"recovered": true|false`가 실린다. `false`면 클라이언트가 자기 백엔드에서 다시 동기화해야 한다.
- **복구 중 경쟁 처리:** 입장 즉시 라이브 메시지가 오기 시작하는데, 이력은 비동기로 읽는다. 그래서 그 세션의 그 룸을 "복구 중"으로 표시하고, 그동안 도착한 라이브 메시지를 세션 안에 잠시 모아 둔다. 이력을 다 보낸 뒤 **이미 보낸 offset 이하는 버리고** 모아 둔 것을 보낸다(중복·누락 없음). 모아 둘 수 있는 양에는 상한을 두고, 넘으면 `recovered: false`로 처리한다.
- **C1과의 정합:** 느린 수신자를 끊는 정책이 이제 "끊고 자동 복구"가 된다. SDK가 룸별 `{epoch, offset}`을 기억했다가 재접속하면서 자동으로 복구를 요청한다.
- **ACK(클라이언트 확인 응답)는 하지 않는다.** offset 기반 재요청으로 충분하고, ACK는 메시지마다 상향 트래픽을 만든다.

### 4. 노드 로컬 구독 색인

- presence(누가 이 노드의 어느 룸에 있나)는 계속 **노드 로컬**이다. 팬아웃은 지금처럼 로컬 멤버 핸들로 한다.
- 노드는 **로컬 멤버가 생긴 룸만** Broker 구독한다(첫 멤버 입장 시 구독, 마지막 멤버 퇴장 시 해제, 참조 계수). 그래서 노드 수가 늘어도 메시지가 필요 없는 노드에는 가지 않는다.
- **구독이 끊겼다 돌아오면(gap):** Redis 연결이 끊기거나 느려서 Redis가 구독자를 끊는 경우다. 노드는 모든 룸을 다시 구독하고, **이력 룸은 노드가 마지막으로 전달한 offset부터 스스로 이력을 읽어** 메운다. 클라이언트에게는 끊김이 보이지 않는다. 이력이 없는 룸은 메울 수 없으므로 멤버에게 `sys.gap {room}`을 보낸다.

### 5. id

- (개정 1 A1이 이 항목을 대체한다: 구간 임대, 입장은 동기.) **member id는 룸 안에서만 유일하면 된다.** 클라이언트가 `sender`로 구분하는 범위가 그 룸이기 때문이다. 그래서 Broker가 **룸별 카운터**로 발급한다(Redis `INCR`, 메모리는 로컬 카운터). 입장할 때 한 번 왕복이 생기지만, 입장은 드물다. 기각한 대안 두 가지는 아래와 같다.
  - u32 안에 노드 번호를 넣고 카운터는 22비트: 노드당 약 4백만 번 입장하면 값이 한 바퀴 돌아, 오래 남아 있는 멤버와 충돌할 수 있다.
  - v2 `sender`를 u64로 넓힘: 프레임마다 4바이트가 더 들고, 프로토콜도 바뀐다.
- **룸 id(`chan`)는 노드 로컬로 둔다.** `chan`은 세션이 자기 `sys.joined`에서 받는 값이라 노드마다 달라도 된다. 다른 노드에서 온 Hot 프레임은 받는 노드가 **자기 `chan`으로 헤더 4바이트만 바꿔서** 다시 인코딩한다(룸당 한 번, encode-once는 그대로 유지).

### 6. 클러스터 제어

- **사용자 제어 채널:** 노드는 로컬 세션이 있는 사용자의 채널 `user:{tenant}:{user}`를 구독한다(참조 계수). 이 채널로 오가는 명령은 다음과 같다.
  - `Disconnect{sid?, reason}`: 서버 API의 disconnect가 어느 노드에 들어와도 동작한다.
  - `ReplaceSid{sid, except_session}`: sid 교체(S4)가 노드를 넘어 동작한다.
  - `KickOldest`: `on_exceed: kick_oldest`가 노드를 넘어 동작한다(§8 근사).
- **presence 클러스터화:** 룸 멤버 목록을 공유 저장소에 둔다(Redis 해시 `presence:{tenant}:{room}`). 노드마다 살아 있음을 알리는 키에 TTL을 걸고, **죽은 노드의 멤버는 살아 있는 노드의 스위퍼가 정리하면서 `member_left`를 낸다**(ADR 0010을 클러스터로 확장). 서버 API의 presence 조회도 클러스터 전체를 본다. presence 이벤트는 룸 채널의 제어 프레임으로 방송한다.
- **1회용 티켓:** 공유 저장소에 둔다(Redis `SET NX EX` + `GETDEL`로 1회성을 원자적으로 보장). 티켓을 발급한 노드와 소비하는 노드가 달라도 된다.

### 7. 노드 사이 프레임 형식

- 버전 필드가 있는 이진 형식(내부용)이다: `[ver][kind][origin_node][room_key][qos][offset?][payload]`. Hot 프레임은 v1 페이로드와 헤더 필드(`svc, op, key, seq, sender`)를 보내고, 받는 노드가 자기 `chan`으로 v2를 만든다.
- **롤링 업데이트:** 노드는 자기가 아는 최고 `ver`까지만 보내고, 모르는 `ver`는 로그를 남기고 버린다. 형식을 바꿀 때는 "읽기를 먼저 배포하고, 쓰기는 나중에 바꾼다"는 규칙을 문서화한다.

### 8. 클러스터 전역 상한: 이번에는 근사치

| 상한 | 이번 결정 |
|---|---|
| `max_sessions_total`(테넌트), `max_rooms_total` | **노드별로 적용**한다(문서에 "노드당"이라고 명시). 전역 정확 계수는 매 접속마다 공유 저장소 왕복이 필요해서 보류 |
| `max_sessions_per_user` | 공유 카운터로 **근사**(경쟁 시 잠깐 초과 가능)하고, 초과분은 `KickOldest` 제어로 정리 |
| `max_users_per_room` | 클러스터 presence 수로 **근사** |
| handshake·메시지 rate limit | 노드별(로드밸런서 뒤에서 IP별 제한의 의미가 그대로 유지됨) |

### 9. 실패 시 동작

| 상황 | 동작 |
|---|---|
| Redis 다운 | Ext Reliable 발행 → `UNAVAILABLE`(조용히 잃지 않는다). Hot은 로컬 전달만 계속(다른 노드 멤버는 못 받음). 티켓 인증 → 503 + `Retry-After`(fail closed). 이미 연결된 세션은 유지 |
| Redis 재시작(이력 유실) | epoch가 바뀜 → 복구 요청은 `recovered: false` |
| 노드 강제 종료 | 클라이언트는 41xx/네트워크 오류로 다른 노드에 재접속하고 복구. 죽은 노드의 presence는 TTL 만료 후 정리되며 `member_left` 발생 |
| 노드의 구독 연결 지연·끊김 | §4의 gap 처리(이력 룸은 노드가 스스로 메움) |

### 10. 의존성 (승인 필요)

| 용도 | 후보 | 비고 |
|---|---|---|
| Redis 클라이언트 | `redis`(redis-rs, tokio, 연결 관리자) | 가장 널리 쓰임, BSD-3. 대안 `fred`는 기능이 많지만 의존성이 더 크다 |
| 테스트용 Redis 서버 | docker 이미지 `redis:7` (`--internal` 네트워크, 실험 로컬 원칙 준수) | 이미지 다운로드 필요 |

### 11. 단계 (단계마다 커밋, 테스트, 문서)

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| R1 | `Broker` 경계(B6의 R1 연산) + `MemoryBroker`로 지금 동작 이전, `BrokerOutbox`·테넌트 할당량(B4), 구독 명령(B5), member id = 슬롯 + 룸별 카운터(B1), `RecordingBroker`·`FaultBroker` 테스트(B3) | 기존 테스트 전부 + B2 기준 + B3 테스트 |
| R2 | 이력·offset·epoch, 복구 프로토콜(v2 추가), 복구 중 버퍼링, SDK 자동 복구 | **끊긴 사이 메시지 복구 테스트**(M3 완료 기준), slow consumer → 복구 |
| R3 | Redis Broker: 발행·구독(로컬 구독 색인), 이력(Lua로 offset 발급·저장·자르기를 원자적으로), member id, 공유 티켓, gap 처리 | 2노드 + Redis 통합 테스트 |
| R4 | 클러스터 제어·presence: disconnect·sid 교체·kick, presence 저장소와 노드 사망 정리, 서버 API 클러스터화 | 노드를 넘는 제어 테스트 |
| R5 | 카오스: 노드 `kill -9`, Redis 재시작, 구독 지연 시뮬레이션(netlab), 문서·운영 가이드 | **노드 강제 종료 카오스 테스트**(M4 완료 기준) |

## 기각한 대안

| 대안 | 이유 |
|---|---|
| 세션 고정(sticky)으로 노드마다 룸을 나눠 맡기 | 한 룸의 멤버가 여러 노드에 흩어지는 순간 깨진다. 노드 장애 시 룸 전체가 사라진다 |
| 노드끼리 직접 메시(gossip/mesh) | 소속 관리·분할·재연결을 직접 구현해야 한다. 검증된 Broker를 쓰는 편이 운영자가 이해하기도 쉽다 |
| Redis 대신 NATS 먼저 | NATS JetStream도 좋지만, 이력·카운터·키-값·presence를 한 저장소로 처리하기에는 Redis가 단순하고 운영 경험이 흔하다. 경계는 NATS를 막지 않는다 |
| 이력을 기본으로 켜기 | 룸마다 메모리를 쓰고, 상태성 룸(Hot)에는 의미가 없다 |
| 복구를 클라이언트 쪽 ACK로 | 메시지마다 상향 트래픽이 생긴다. offset 재요청이 더 싸고 단순하다 |
| Hot도 Broker를 거쳐 순서 보장 | 상태 동기화의 존재 이유인 지연을 희생한다. `seq`로 이미 충분하다 |

## 검토해 주셨으면 하는 결정

1. **레인별 경로(§2):** Ext Reliable은 Broker를 거쳐 클러스터 전체가 같은 순서로 보고, Hot은 로컬 먼저 전달합니다. 대가로 Reliable 지연이 Redis 왕복만큼 늘어납니다.
2. **이력은 룸 패턴별 옵트인(§3)**, 클라이언트 ACK는 하지 않음.
3. **member id를 룸별로 Broker가 발급(§5)**: 프로토콜은 그대로 두고, 입장 시 한 번 왕복이 생깁니다.
4. **전역 상한은 이번에 근사·노드별(§8).**
5. **Redis 먼저 + 다운로드 승인(§10):** `redis` 크레이트와 테스트용 `redis:7` docker 이미지.
6. **단계 R1~R5의 순서**: R2(단일 노드 복구)만 끝나도 "끊겨도 안 잃는다"가 됩니다. 멀티 노드는 R3부터입니다.
