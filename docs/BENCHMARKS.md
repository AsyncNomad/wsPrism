# Benchmarks

wsPrism의 성능 수치와 측정 방법이다. 원칙: **수치 없이 성능을 주장하지 않는다** ([ROADMAP](ROADMAP.md)).
모든 성능 관련 변경은 이 문서의 시나리오로 전후를 측정하고 결과를 여기에 추가한다.

## 측정 도구

| 도구 | 위치 | 무엇을 재나 |
|---|---|---|
| 마이크로 벤치마크 (criterion) | `crates/wsprism-protocol/benches/protocol.rs`, `crates/wsprism-gateway/benches/hotpath.rs` | 메시지당 핫패스 비용: 디코드, 정책, 메트릭, 룸 팬아웃 |
| 부하 생성기 | `crates/wsprism-loadgen` | 실제 WebSocket 연결로 종단 간 지연(p50~p99.9), 전달 처리량, 전달률 |
| 시나리오 스크립트 | `bench/run-baseline.sh`, `bench/gateway.yaml` | 표준 시나리오 실행 + 게이트웨이 RSS 측정 → `bench/results/<label>.jsonl` |

```bash
# 마이크로 벤치마크
cargo bench -p wsprism-protocol --bench protocol
cargo bench -p wsprism-gateway --bench hotpath

# 종단 간 시나리오 (release 빌드, 로컬 게이트웨이 자동 기동)
bench/run-baseline.sh <label>
```

### 부하 생성기 방법론

- 모든 연결이 룸에 들어가 수신한다. 앞쪽 `--publishers`개 연결이 송신 시각(프로세스 공통 기준 시각 기준 ns)을 담은 프로브를 `--rate`/s로 보낸다.
  - Hot: `[v][svc=1][op][flags][ts u64][padding]` → svc 1(룸 릴레이 `HotRelayService`, 초기 측정 때는 echo 서비스)이 룸에 Lossy 팬아웃.
  - Ext: `chat:send` JSON, `data.msg` 앞 20자리가 ts → Reliable 팬아웃.
- 수신 시 `지금 - ts`를 HdrHistogram(µs, 유효숫자 3)에 기록. 송신·수신이 같은 프로세스라 시계 동기화가 필요 없다.
- 전달률 = 받은 프로브 수 / (보낸 프로브 수 × 룸 인원). Lossy 레인의 드롭이 여기에 드러난다.
- 클라이언트는 브라우저처럼 TCP_NODELAY를 쓴다.
- Ext 지연에는 **클라이언트의 JSON 파싱 비용**이 포함된다.

### 표준 시나리오

| 이름 | 연결 | 룸 (인원) | 발행자 × 속도 | 레인 | 목적 |
|---|---|---|---|---|---|
| `idle_10k` | 10,000 | 100 (100) | 0 | — | 연결당 메모리 |
| `hot_100x10` / `ext_100x10` | 1,000 | 10 (100) | 10 × 100/s | Hot / Ext | 일반 부하 지연 |
| `hot_room1000` / `ext_room1000` | 1,000 | 1 (1,000) | 1 × 50/s | Hot / Ext | 큰 방 팬아웃 |
| `hot_heavy` | 5,000 | 50 (100) | 50 × 200/s | Hot | 고부하 처리량 |

## 측정 환경과 한계

- Intel i7-13700K (24 스레드), 16 GB, **WSL2** (Linux 6.18, Windows 호스트). Rust 1.99, release 빌드.
- **게이트웨이와 부하 생성기가 같은 머신에서 CPU를 나눠 쓴다.** 절대값은 전용 서버보다 나쁘게 나오고, 고부하에서는 부하 생성기가 먼저 포화될 수 있다(`hot_heavy`가 목표 10,000 msg/s 대신 8.5~9k msg/s만 보냄 — 어느 쪽이 병목인지는 아직 분리하지 않음).
- 각 시나리오 1회 실행. 같은 설정 2회 실행 간 차이는 p99 기준 약 15% 이내, p99.9는 더 크게 흔들린다(예: 4.1 vs 6.6 ms).
- RSS는 프로세스 전체이며 할당자가 반납하지 않은 메모리를 포함한다(시나리오 간 감소하지 않음).
- (기준선 측정 당시) 경쟁 제품 비교는 없었다. 이후 비교는 아래 「경쟁 게이트웨이와의 WebSocket 비교」(compete-v1), 「경쟁 비교 재측정」(compete-v2), 「이력을 켠 경쟁 비교」(A14). 전용 호스트 2대(서버/클라이언트 분리) 측정은 아직 없다.

## 해석과 다음 목표

1. **TCP_NODELAY가 꼬리 지연을 지배했다.** axum은 기본값으로 Nagle을 끄지 않는다. Nagle + 지연 ACK 때문에 저부하에서도 p99.9가 23~27 ms에 고정됐다. `gateway.socket.tcp_nodelay`(기본 true)로 3.6~9 ms가 됐다.
2. **메시지당 비용에서 가장 큰 항목은 메트릭(275 ns)과 팬아웃(수신자당 약 200 ns)이다.** 프로토콜 디코드(21~254 ns)나 정책(5~18 ns)보다 크다. M5의 우선 대상:
   - 메트릭: 세션·테넌트별로 미리 만든 카운터 핸들 + 원자 연산(라벨 할당 제거). 목표 < 10 ns.
   - 팬아웃: Presence가 세션 키 대신 연결 핸들을 직접 보유(레지스트리 조회·문자열 복제·`Sender` 복제 제거). 목표 수신자당 < 50 ns.
3. **큰 방에서 p99가 먼저 늘어난다** (1,000명 방 p99 약 6 ms vs 100명 방 약 2 ms). 팬아웃이 발행자 task 안에서 순차로 수행되기 때문으로 추정한다. 팬아웃 비용을 줄인 뒤 다시 측정한다.
4. **연결당 약 27.6 KB**의 구성(소켓 버퍼, tungstenite 버퍼, 송신 큐, task)은 아직 분해하지 않았다. 내역을 측정한 뒤 목표를 정한다.
5. **아직 모르는 것**: 고부하에서 병목이 게이트웨이인지 부하 생성기인지, 전용 호스트에서의 절대값, 경쟁 제품 대비 위치.

## 검증 V: 상태 동기화 — WebTransport datagram vs WebSocket

[ADR 0004](adr/0004-product-direction.md) 관문 G1(체감 성능)·G5(비용)의 판정 칸 측정. 설계: [§7](design/hot-lane-over-webtransport.md#7-검증-단계-v-약-3주).

- **도구**: `bench/netlab.sh`(비특권 netns + veth, 방향별 netem, offload 끔), 버리는 스파이크 릴레이 `spikes/wt-hotlane`(WS·WSS·WT가 같은 릴레이 로직), `wsprism-loadgen statesync`(60 Hz AoI·끊김 비율·서버 CPU/RSS). 실행: `bench/run-v.sh v-judgment 3`, 판정: `bench/analyze-v.py bench/results/v-judgment.jsonl`.
- **판정 칸**: 단방향 20 ms(RTT 40 ms), 60 Hz 송신, 10명 룸 × 10개 전원 발행, 손실 {없음, 균등 1%, 버스트 평균 1%·길이 4}, 틱 {즉시, 60 Hz, 30 Hz}, 각 3회(중앙값). 같은 실행에서 AoI와 비용을 함께 측정.
- **비교 규칙**: WT의 틱 T는 **같은 틱 T의 WSS**와 비교한다(실재하는 설정끼리). 초과 AoI = 같은 전송·틱·지연의 손실 0% 대비 AoI p99 증가분.

### 해석

1. **끊김 제거가 가장 뚜렷한 이득이다.** WSS는 1% 손실에서 렌더 틱의 2.3~3.8%가 100 ms 넘게 오래된 상태를 보여 준다(60 Hz에서 초당 1~2회 끊김). WT는 0~0.6%.
2. **초과 AoI의 배수는 "TCP 복구 시간 ÷ 송신 주기"로 제한된다.** datagram 하나를 잃으면 다음 업데이트(60 Hz면 16.7 ms 뒤)가 대신하므로 WT의 초과분은 약 한 주기, TCP는 재전송 복구 시간(여기서 약 50 ms)이다. 그래서 60 Hz에서 3배를 겨우 넘고, **20 Hz에서는 배수가 크게 줄 수 있다**(미측정 — 다음 측정 대상). 반대로 RTT가 크거나 송신이 빠를수록 이득이 커진다.
3. **비용은 약 2~2.5배로 G5(2배)를 넘는다.** 메모리가 모든 설정에서 2.2배 이상으로 일관되게 실패하고, CPU는 즉시 전송에서 2배 경계. **quinn/wtransport 기본 설정 그대로**의 값이다(전송 창·datagram 버퍼 등 미조정). 틱 묶음은 모든 전송의 CPU를 낮추지만 격차를 줄이지는 않는다.
4. **틱 30 Hz**는 60 Hz 송신을 절반으로 솎아(전달률 0.5) AoI 바닥값을 올린다. 초과 AoI가 거의 0인 것은 손실된 업데이트가 어차피 덮일 것이었기 때문이다.

|---|---|---|---|---|---|---|---|
| 균등 1% | 65.8 | 31.0 | **2.1×** | 7.12% | 1.65% | 1.72× | 2.26× |

예측대로 초과 AoI 배수가 줄었다(60 Hz 3.1× → 20 Hz 2.1×): WT의 초과분은 약 한 송신 주기(50 ms)로 늘고, TCP의 복구 시간은 그대로다. **끊김 비율은 20 Hz에서도 4배 이상 개선**되고, WSS는 1% 손실만으로 렌더 틱의 7%가 100 ms 넘게 오래된 상태를 보인다.

### 추가 측정 2: 메모리 — 조정 프로필과 측정 방법 정정

- **QUIC 조정 프로필**(`--quic-lean`): datagram 버퍼 1 MB/1.25 MB → 64 KB, 스트림 창 1.25 MB → 64 KB, 송신 창 → 256 KB, 동시 스트림 100+100 → 4+8, MTU 탐색 끔. 판정 칸 재측정(`v-lean.jsonl`): G1 그대로 통과, 연결당 메모리는 약 6%만 감소(127 → 120 KB).
- **측정 방법 정정**: 지금까지의 "연결당 메모리"는 (RSS 증가 ÷ 연결 수)여서 연결 수와 무관한 고정 비용(엔드포인트 버퍼, 런타임 초기화)까지 나눠 담았다. **한계 비용**(연결 100 → 300개의 기울기)으로 다시 측정했다(`v-mem-*.jsonl`, 손실 없음, 60 Hz, 각 3회).

| 설정 | WSS KB/conn (한계) | WT KB/conn (한계) | WT÷WSS | 참고: 100개 단순 평균 WSS / WT |
|---|---|---|---|---|
| 기본값 | 29.6 | 85.6 | **2.89×** | 55.3 / 128.1 |
| `--quic-lean` | 29.0 | 76.4 | **2.64×** | 56.8 / 117.1 |

고정 비용이 WT를 부풀렸을 것이라는 가설은 **틀렸다** — 오히려 WSS 쪽이 고정 비용 비중이 커서, 한계 비용으로 보면 격차가 더 크다.

**CPU의 연결 수 의존성**: 같은 측정에서 메시지당 CPU가 연결 100 → 300개일 때 WSS 4.3 → 5.1 µs, **WT 6.2 → 11.9 µs**. WT는 연결이 늘수록 메시지당 비용이 커진다(가설: 수신자마다 QUIC 패킷을 따로 암호화하고 시스템 콜을 쓰는 비용, 엔드포인트 단일 처리 경로 — 미검증). 세션 간 CPU 측정 잡음은 약 20%라 CPU는 같은 실행 안의 비교만 신뢰한다.

| 즉시 | 5.09 (0.82) | 11.62 (1.88) | 2.28× | 51.9 / 51.7 |
| **60 Hz** | 1.74 (0.28) | **3.06** (0.48) | **1.76×** | 68.4 / 68.1 |

틱 묶음으로 패킷 수를 줄이면 WT의 메시지당 CPU가 약 1/4이 된다 — 연결 수에 따른 증가는 **수신자별 패킷(암호화 + 시스템 콜) 비용**이었다. 60 Hz 틱은 판정 칸에서 G1도 통과한 설정이므로, **CPU는 틱 묶음 전송으로 G5 안에 들어온다.** 대가는 두 전송 모두 AoI 약 +16 ms(최대 한 틱).

### G4 폴백 (`v-fallback.jsonl`)

`--transport auto`(WT를 1.5초 시도 → 실패 시 WSS), 단방향 20 ms, 100 클라이언트, 각 3회. 차단은 클라이언트 netns의 `iptables -A OUTPUT -p udp -j DROP`.

| 조건 | 연결된 전송 | 연결 시간 p50 / p99 / 최대 (ms) |
|---|---|---|
| UDP 열림 | WT 100 / 100 (3회 모두) | 169~181 / 1,126~1,133 / 1,134 |
| UDP 차단 | WSS 100 / 100 (3회 모두) | 1,674~1,690 / 1,676~1,691 / **1,691** |

**G4 통과**: 전원이 2초 안에 WSS로 전환, 전환 후 AoI 정상. **새 위험**: UDP가 열려 있어도 100명 동시 접속 시 WT 연결 p99가 약 1.13초 — 손실 없이도 첫 핸드셰이크 패킷 일부가 버려지고 약 1초 후(QUIC 초기 PTO) 재전송되는 것으로 보인다(가설: 서버 UDP 수신 버퍼 부족). 폴백 예산(1.5초)에 가까워, 접속 폭주 시 WT 가능 클라이언트가 불필요하게 WSS로 넘어갈 수 있다 → T 과제(수신 버퍼 크기, 병렬 시도 방식 검토).

### G3 소크 (`v-soak*.{jsonl,log}`)

WT 세션 1,000개(100 룸 × 10), 20 Hz, 틱 60 Hz 묶음, 단방향 20 ms + 균등 1% 손실(손실 처리 경로 포함), 워밍업 5분 + 측정 55분.

| 항목 | 결과 |
|---|---|
| 패닉 | **0** |
| 끊긴 연결 | **0** (1,000/1,000 WT) |
| 처리량 | 수신 프레임 약 7,000만, 전달 약 17.4만/s, 송신 드롭 0 |
| RSS (워밍업 후) | 92.2 → 93.6 MiB, **+1.5%** — 10분 92.7, 20분 93.1, 30분 93.4, 40분 93.5, 50·56분 93.6 MiB로 수렴 |
| 서버 CPU | 4.9 µs/msg |

**G3 통과.** 미해결: 소크의 끊김 비율 6.5%·AoI p99 140 ms는 20 Hz 소규모 측정(WT 1.65%)보다 크다. 유력한 원인은 부하 생성기 포화(클라이언트 1,000개 × 초당 54만 AoI 표본)이며, 소크 조건은 판정 칸과 달라 판정에 쓰지 않는다.

### V6 MoQ 평가 (완료)

대상: Cloudflare 유지보수 IETF 계열(`moq-transport` 0.16, `moq-relay-ietf` 0.7.29, `moq-native-ietf` 0.10). 원 저자 계열(`moq-lite`→`moq-net`, `moq-native`→`moq-tokio`)은 최근 이름이 바뀌었다.

**방법**: 버리는 프로브 `spikes/moq-probe`(부하 생성기의 AoI·프레임·비용 코드를 `#[path]`로 그대로 사용 → 지표 동일). 참가자마다 네임스페이스 `r<room>/p<id>`의 `state` 트랙을 발행하고, 업데이트마다 datagram 객체 1개를 보낸다. 같은 룸의 다른 N−1명의 트랙을 각각 구독한다. 릴레이는 netlab 안에서 실행마다 자가 서명 인증서로 기동한다(`bench/run-moq.sh`). 판정 칸과 같은 조건(20 ms, 60 Hz, 10×10)이고, **같은 세션에서 WSS·WT(틱 0)도 함께 재서** 같은 파일에 넣었다(`moq-judgment.jsonl`, 각 3회).

| 손실 | 초과 AoI WSS / WT / MoQ (ms) | 끊김 WSS / WT / MoQ | CPU µs/msg WSS / WT / MoQ | RSS 평균 KB/conn WSS / WT / MoQ |
|---|---|---|---|---|
| 없음 | — | 0 / 0 / 0 | 4.28 / 6.46 / 11.54 | 57.8 / 130.0 / 527.8 |
| 균등 1% | 49.6 / 15.7 / 15.7 | 2.42% / 0.001% / 0 | 3.57 / 6.67 / 11.68 | 55.0 / 130.0 / 525.1 |
| 버스트 1% | 49.4 / 15.7 / 15.6 | 2.31% / 0 / 0 | 3.77 / 6.50 / 11.36 | 55.1 / 128.8 / 521.5 |

- **이득은 WT와 같다**(datagram이라는 같은 물리). 지연 p99는 WT보다 약 3 ms 짧고(46 vs 49 ms), 손실 0%에서는 WSS보다 약 3 ms 길다(릴레이 경유 비용).
- **비용은 훨씬 크다**: 같은 세션 기준 CPU **2.7~3.3×** WSS(WT 1.5~1.9×), 메모리 평균 9.1~9.6×. **한계 메모리**(연결 100 → 300, `moq-mem-30.jsonl`)는 **약 477 KB/conn** — WSS 29.6, WT 85.6의 각각 16배, 5.6배. 릴레이의 트랙 캐시(`--cache-idle-timeout` 기본 30초)가 포함된 값이다.
- 연결 300개에서는 손실이 없는데도 전달률 0.86~0.88, AoI p99 84 ms로 떨어졌다. 릴레이 포화인지 프로브(클라이언트 300개 각자의 QUIC 엔드포인트) 포화인지는 **분리하지 않았다**.
- **의미론**: datagram 트랙 리더는 "최신값" 의미다(`read()`가 가장 최근 객체만 돌려주고, 늦은 리더는 중간 값을 건너뛴다). 상태 동기화의 conflation과 맞는다. 룸 구독은 참가자별 트랙 N−1개가 필요하다(이름 공간 단위 구독 없음).

**발행자 재접속(M-5, `bench/run-moq-reconnect.sh`, `moq-reconnect-*.log`)**: 구독자 1명, 발행자가 3초 후 떠났다가 0.5초 뒤 같은 네임스페이스로 다시 발행.

| 떠나는 방식 | 구독자가 본 것 |
|---|---|
| 정상 종료(세션 닫기) | 41 ms 안에 구독 종료 알림 → **재구독 필요**. 재구독 후 데이터 재개, 공백 약 1.07초(간격 0.5초 + 접속 + 재구독 폴링 포함) |
| 비정상 종료(`kill -9`, 모바일 망 전환과 같은 상황) | 새 발행자의 네임스페이스 등록이 **즉시 거절**(REQUEST_ERROR 0x20). 구독은 끊김 알림 없이 열린 채 **13초 넘게 새 데이터 0**. 추정 원인: 죽은 세션이 QUIC 유휴 타임아웃(10초)까지 네임스페이스를 쥐고 있음 |

대표 시나리오(모바일·Wi-Fi)에서는 망 전환이 곧 비정상 종료다. 그래서 이 동작은 "참가자 재접속마다 10초 이상 정지"를 뜻한다. 우회하려면 세션마다 네임스페이스를 바꾸고 구독자가 이를 발견해야 하는데, 이름 공간 단위 구독이 없어 상위 시그널링이 필요하다.

| 항목 | 확인 결과 |
|---|---|
| 한 세션으로 발행·구독 | 가능 (`Session::connect`가 `(Session, Publisher, Subscriber)` 반환. 릴레이 README의 역할 설명은 낡음) |
| datagram 중계 | 가능 (실측 전달률 0.98 @1%) |
| 정책 지점 | 스코프별 토큰 인가(CAT, 기능 플래그 기본 꺼짐) |
| 생태계 | 두 계열 분기, 크레이트 개명·deprecate, 문서-코드 불일치 |

**판단(M-6)**: ADR 0004 개정 3에 기록. 요약하면 **MoQ 위에 구축 — 기각**(비용 3×·16×, 비정상 종료 시 10초 넘는 정지, 생태계 변동), **MoQ 릴레이와 정면 경쟁 — 기각**(이득이 같은 물리라 차별점이 아님), **MoQ 호환(와이어 수준) — T 이후 재검토**(초안 안정화 대기, `SessionIo` 경계가 이를 막지 않게). 한계: 릴레이 한 버전만, 기본 설정만 측정. 조정 가능한 설정(캐시 시간 등)은 시험하지 않았다.

### 측정 결함 (4차 리뷰, 2026-10-14) — G1 판정 보류

리뷰가 지적했고 코드로 확인했다:

1. **위상 고정**: 모든 클라이언트가 같은 시각 `t0`에 송신을 시작하고 렌더는 `t0 + 정수 초`에 시작한다([mod.rs](../crates/wsprism-loadgen/src/statesync/mod.rs)). 송신과 렌더가 둘 다 60 Hz라 렌더 틱이 송신 틱과 정확히 겹친다. 그래서 AoI가 연속 분포가 아니라 계단값(50 / 66.7 / 83.3 / 100 ms)이 된다. 0% AoI p50 50.0, p99 51.1 ms가 그 증거다. WT 초과분 15.8 ms는 정확히 한 프레임이다. 같은 설정인데 WT 틱 60의 p99가 실행마다 68.0~82.5 ms로 갈리는 것도 위상 민감성의 증거다.
2. **끊김 기준이 계단 위에 있음**(리뷰가 놓친 점): 100 ms 기준이 계단값 100 ms에 정확히 걸친다. WSS의 끊김 2.3%도 계단 경계 근처 표본의 영향을 받았을 수 있다.
3. **버스트가 연결 단위가 아님**: veth 하나를 100개 연결이 공유해 패킷 단위 Gilbert-Elliott 버스트가 연결마다 흩어진다. 실측도 균등과 버스트가 같다(WSS p99 100.7 vs 100.8). Wi-Fi형 "일정 시간 통째로 끊김"은 검증되지 않았다.
4. **오프로드를 끄고 비용 측정**: [netlab.sh](../bench/netlab.sh)가 TSO/GSO/GRO를 끈다(netem이 GSO 묶음 단위로 버리지 않게 하려고). 다만 64 B·60 Hz·수신자별 송신이라 TSO 이득은 작을 것으로 보고, 방향과 크기는 재서 정한다.

편향의 방향은 정해지지 않았다. 위상을 무작위로 하면 WT의 바닥값 p99도 함께 오른다. 그래서 **현재 G1 숫자는 통과도 실패도 아닌 "보류"**로 둔다. 재측정 계획은 [validation-v-status.md](design/validation-v-status.md) 「측정 수정」.

### G1 재측정 (v2, 측정 수정 후)

`v2-judgment.jsonl`: 위상 무작위(`--phase random --seed <run>`), 손실 {없음, 균등 1%, 단절 평균 1초마다 50 ms, 단절 평균 5초마다 250 ms}(단절은 양방향 동시, 같은 run 번호면 전송 간 일정 동일), 틱 {즉시, 60 Hz, 30 Hz}, {ws, wss, wt}, 각 3회, 측정 20초, 판정 칸(20 ms, 60 Hz, 10×10).

**위상 고정 해소 확인**: 손실 0% AoI가 p50 49.2 / p99 57.8 ms로 연속 분포가 됐다(이전 50.0 / 51.1의 계단 → 한 송신 주기 폭의 톱니). 같은 설정의 실행 간 p99 범위도 0.1~0.3 ms로 좁아졌다(이전 WT 틱 60은 14 ms).

| 손실 | 틱 | 초과 AoI p99 WSS / WT (ms) | 배수 | 끊김(>100 ms) WSS / WT | 판정(사전 등록 기준) |
|---|---|---|---|---|---|
| 균등 1% | 즉시 | 54.3 / 9.1 | **6.0×** | 3.25% / 0.00% | 통과 |
| 균등 1% | 60 Hz | 45.0 / 2.9 | **15.6×** | 2.91% / 0.01% | 통과 |
| 균등 1% | 30 Hz | 46.1 / 4.3 | 10.7× | 3.79% / 0.54% | 통과 |
| 단절 50 ms/1초 | 즉시 | 159.1 / 66.0 | 2.4× | 13.6% / 3.1% (4.3×) | **실패**(초과 AoI) |
| 단절 50 ms/1초 | 60 Hz | 174.6 / 70.9 | 2.5× | 16.3% / 5.0% (3.3×) | **실패**(초과 AoI) |
| 단절 250 ms/5초 | 즉시 | 407.1 / 245.1 | 1.7× | 8.8% / 5.1% (1.7×) | **실패** |
| 단절 250 ms/5초 | 60 Hz | 414.7 / 243.2 | 1.7× | 9.2% / 5.3% (1.7×) | **실패** |

**사전 등록 기준으로는 G1 실패**다(단절 조건). 균등 손실에서는 수정 전 측정(3.1~3.2×)보다 오히려 크게 통과한다 — 위상 고정은 WT에 **불리하게** 작용했다.

**해석 (사후 분석, 판정 기준 아님)**: 단절 조건에서 WT의 초과 AoI는 **단절 길이 자체**와 거의 같다(50 ms 단절 → 66~71 ms ≈ 50 + 한 주기, 250 ms 단절 → 243~245 ms). 즉 WT는 어떤 전송도 넘을 수 없는 물리적 바닥에 있다. "WSS의 1/3 이하"라는 기준은 단절이 길수록 **어떤 전송도 만족할 수 없다**(바닥값 L에 대해 WSS 초과분이 3L 이상이어야 함). 단절 길이를 뺀 "복구 지연"으로 보면:

| 단절 | 틱 | 단절 후 추가 지연 WSS / WT (ms) |
|---|---|---|
| 50 ms | 즉시 / 60 Hz | 109 / 16, 125 / 21 (6~7×) |
| 250 ms | 즉시 / 60 Hz | 157 / ≈0, 165 / ≈0 |

TCP는 링크가 돌아온 뒤에도 재전송 타이머(백오프 포함)를 기다려 100~165 ms를 더 잃고, WT는 다음 datagram으로 즉시 회복한다. 이 지표는 결과를 본 뒤 정의한 것이므로 판정에 쓰려면 **사용자 결정**이 필요하다(아래 「현재 판정」).

- **끊김 기준 민감도**: 균등 1%에서 WSS의 끊김은 대부분 100~150 ms 구간이다(150 ms 초과는 0.1%). 단절에서는 WSS가 200 ms 초과 2.6~7.5%, WT 0~3.3%. 100 ms 기준이 결론을 뒤집지는 않지만, 균등 손실의 "끊김 제거"는 **100~150 ms 지연을 없앤 것**이라고 표현하는 것이 정확하다.
- **긴 단절의 WT 끊김 5.1%**는 단순 바닥값 추정(약 3.8%: 단절 중 AoI가 100 ms를 넘는 구간 ÷ 평균 주기)보다 약 1.3%p 높다. 가설: 손실 감지 후 QUIC 혼잡 제어가 창을 줄여 단절 직후 datagram 송신이 잠깐 막힘 — **미검증**.
- 비용(오프로드 끔, 같은 실행): CPU 1.6~2.3×, 메모리 2.0~2.5× — 이전과 같은 결론(G5 메모리 실패).
- **비용, 오프로드 켬**(`v2-cost-{10,30}.jsonl`, 손실 없음, 연결 100 → 300, 각 3회): 한계 메모리 WSS 30.7 / WT 85.5~90.1 KB/conn(**2.8~2.9×**). CPU WT÷WSS는 즉시 1.65×(100)·1.88×(300), 60 Hz 틱 1.89×·1.88×. 오프로드를 켜면 격차가 커질 것이라는 리뷰 예측은 방향은 맞지만 크기는 작다(60 Hz·300 연결 1.76× → 1.88×). **G5: CPU는 기준 안, 메모리 실패.**

### 경쟁 게이트웨이와의 WebSocket 비교 (`compete-v1.jsonl`)

> **대체됨 (2026-10-19):** 아래 수치는 wsPrism이 크게 바뀌기 전의 측정이다. 현재 코드의 비교는 「경쟁 비교 재측정 (`compete-v2.jsonl`)」 절을 본다.

**목적**: 목표("기존 게이트웨이보다 훨씬 좋은 성능")를 직접 잰다. 4차 리뷰가 놓친 공백이었다.

**방법** (`bench/run-compete.sh`, `bench/analyze-compete.py`):
- 대상: wsPrism(현재 `main`의 게이트웨이, Ext = JSON `chat:send`, Hot = 바이너리 echo), **Centrifugo 6.9.7**(JSON 프로토콜, 메모리 엔진), **Sockudo 5.1.0**(Pusher 프로토콜 7, private 채널 + client 이벤트, 로컬 어댑터). 바이너리는 공식 릴리스를 체크섬 검증해 사용(`bench/competitors/fetch.sh`).
- 같은 netlab(지연·손실 없음, 평문 ws), **서버는 코어 0~7(8코어)**, 부하 생성기는 코어 8~23에 고정. 로그 수준은 모두 warn/error.

- **8코어 기준 포화점은 Centrifugo가 더 높다.** 앞의 "wsPrism의 여유가 가장 크다"는 rooms:120까지만 맞다. rooms:160에서 이미 p99가 실행마다 크게 흔들리고(16~317 ms), rooms:240에서 wsPrism은 전달을 놓친다.
- **원인 (산술은 확인, 메커니즘은 가설)**: wsPrism의 전달당 CPU는 부하와 무관하게 약 4.8 µs로 거의 일정하다. 216만/s × 4.74 µs ≈ 10.2코어 > 8코어. Centrifugo는 부하가 오를수록 전달당 CPU가 5.8 → 3.3 µs로 내려간다(216만/s × 3.3 µs ≈ 7.1코어). 가설: Centrifugo는 고부하에서 연결별로 여러 메시지를 모아 한 번에 쓰고, wsPrism은 프레임마다 WebSocket 메시지 하나를 보내고 flush한다(`transport/session` 쓰기 경로) — **미검증**.
- **함의**: 저·중부하의 CPU 우위(1.07~1.25×)와 메모리 우위는 유지되지만, "고부하에서 더 많이 처리한다"고 말할 수 없다. 쓰기 묶음(T0의 틱 묶음 전송·쓰기 합치기)이 이 격차를 줄이는지 T0에서 같은 시나리오로 다시 잰다.

**읽기**:
- **메모리**: 가장 큰 차이. Centrifugo 대비 1.4~3.6×, Sockudo 대비 9~14× 적다. 연결이 많은 서비스에서 서버 대수에 직접 영향을 준다.
- **CPU**: 앞서지만 **차이는 작다** — Centrifugo 대비 1.07~1.25×. "훨씬 빠르다"고 말할 근거는 아니다. 방송형(룸 1,000명)에서는 거의 같다(1.07×).
- **고부하 꼬리 지연**: 108만 전달/s에서 Centrifugo p99가 2.4배 높고 Sockudo는 포화. 단 **포화점 자체는 Centrifugo가 더 높다**(위 「포화점 추가 측정」: 216만/s에서 wsPrism 전달률 0.65~0.86, Centrifugo 1.0).
- **Hot 레인**: 스모크(n=1)에서 본 "Hot p99가 Ext보다 나쁨"은 재현되지 않았다(3회 중앙값에서 같거나 더 좋음, rooms:60은 1.53 vs 3.61 ms).

**공정성 한계** (결론을 약하게 하는 방향 포함):
- **기능 차이**: Centrifugo·Sockudo는 이력·복구·presence·멀티 노드 등 wsPrism에 없는 기능을 갖고 있고, 연결당 메모리의 일부는 그 대가일 수 있다. 같은 기능을 갖춘 뒤에도 차이가 유지되는지는 M3/M4 이후 다시 재야 한다.
- **인증 경로**: Centrifugo는 익명 접속, Sockudo는 부하 생성기가 서명한 private 채널, wsPrism은 개발용 티켓. 연결당 1회 비용이라 전달당 CPU에는 영향이 작다.
- **Sockudo의 코어 인식**: 로그상 `cpu_cores=24`로 버퍼·작업자 수를 정한다(코어 고정 8개를 모름). 8코어 고정에서 불리했을 가능성이 있다.
- 단일 노드, 평문 ws(TLS 없음), 64 B JSON. 프로토콜마다 메시지 크기가 조금 다르다(봉투 형식).
- 같은 장치에서 부하 생성기와 서버가 돈다(코어는 분리).

### G1 확인 측정 (개정 4, 사전 등록 기준, `v2-confirm.jsonl`)

ADR 0004 개정 4에서 단절 칸 기준("복구 지연" = `max(0, 초과 AoI p99 − 단절 길이)`, WT ≤ WSS/3이고 차이 ≥ 16.7 ms, 끊김은 L < 100 ms 칸만)과 판정 코드 `bench/analyze-g1-confirm.py`를 **측정 전에 커밋**(`d95bc56`)한 뒤, 탐색에 쓰지 않은 **시드 4~6**으로 36회 측정했다. 조건은 판정 칸(20 ms, 60 Hz, 10×10, 측정 20초, 위상 무작위).

| 단절 | 틱 | 복구 지연 WSS / WT (ms) | 차이 | 끊김(>100 ms) WSS / WT | 판정 |
|---|---|---|---|---|---|
| 50 ms / 평균 1초 | 즉시 | 107.3 / 15.2 | 92.2 | 13.47% / 3.05% | 통과 |
| 50 ms / 평균 1초 | 60 Hz | 122.2 / 19.4 | 102.8 | 16.03% / 4.71% (기준 5.34%) | 통과 |
| 250 ms / 평균 5초 | 즉시 | 139.0 / 0.0 | 139.0 | 8.50% / 5.07% (공개만) | 통과 |

- **G1(개정 4): 통과** — 즉시·60 Hz 두 틱 모두. 탐색 데이터(시드 1~3)와 수치가 거의 같다(예: 50 ms 단절 즉시, 복구 지연 109.1/16.0 → 107.3/15.2 ms).
- 사전에 밝혀 둔 가장 얇은 여유(60 Hz·50 ms 단절의 끊김 비율)는 4.71%로 기준 5.34% 안이었다.
- **개정 3 기준으로는 여전히 실패**한다(단절 칸 초과 AoI 배수 1.6~2.5×). 이 기준은 단절 길이를 바닥값으로 포함해 어떤 전송도 만족할 수 없다는 이유로 개정 4에서 바꿨고, 두 결과를 모두 공개한다.
- 끊김 기준 민감도: 50 ms 단절에서 WSS는 150 ms 초과도 7.9~11.0%, WT는 0.05~0.45%. 250 ms 단절에서는 300 ms 초과가 WSS 4.3~4.9% / WT 1.1~1.3%.
- 비용(오프로드 끔, 같은 실행): CPU 1.8~1.9×, 메모리 2.1~2.4× — G5 결론과 같다.

### T0: 쓰기 합치기 (같은 세션 교차 A/B, `ab-coalesce.jsonl`, `ab-feed.jsonl`)

세션 루프가 프레임마다 WebSocket 메시지 하나를 보내고 flush하던 것을, 큐에 이미 쌓인 프레임을 최대 64개까지 이어서 쓰고(`feed`) **flush를 한 번만** 하도록 바꿨다. 프로토콜 변화 없음. 판정은 변경 전 바이너리(worktree 빌드)와 같은 세션에서 번갈아 실행한 결과로 한다(`bench/run-ab-gateway.sh`) — CPU는 같은 바이너리끼리도 실행마다 6.2~8.0 µs로 흔들려 세션이 다르면 비교할 수 없다.

1차 구현(`recv_many`로 연결별 `Vec`에 모아 쓰기)은 CPU 이득은 같았지만 **연결당 메모리가 2.8~6.2 KB 늘었다**(버퍼가 부하 시 커진 채 남음). 버퍼 없이 큐에서 바로 `feed`하는 방식으로 바꿔 다시 쟀다:

| 시나리오 | 전달률 이전 → 이후 | CPU µs/전달 (중앙값) | p99 ms (3회) | KB/연결 |
|---|---|---|---|---|
| rooms:20 (18만/s) | 1.0 → 1.0 | 8.22 → 8.30 (잡음 범위) | 1.0~1.2 → 0.8~1.5 | 22.9 → 23.3 |
| rooms:120 (108만/s) | 1.0 → 1.0 | 5.72 → **5.51** | 4.0~45.7 → **4.3~7.1** | 25.6 → 26.0 |
| rooms:240 (216만/s) | **0.70~0.79 → 1.0** | 6.07 → **3.77** | 418~500 → **22~23** | 80 → 42 (이전은 포화로 큐 적체) |

- **216만 전달/s 포화가 사라졌다.** 같은 조건에서 Centrifugo는 p99 56~148 ms, CPU 3.30 µs(`compete-v1`, 다른 세션이라 참고값) — 꼬리 지연은 wsPrism이 낮고 CPU는 비슷한 수준이 됐다.
- 저부하 CPU·메모리 회귀 없음.
- 해석: 고부하에서 전달당 비용을 지배한 것은 **flush(시스템 콜) 횟수**였다는 가설과 맞는다. 프로파일로 확인 예정([성능 아키텍처 설계](design/performance-architecture.md) §10).

### 성능 P0-b·P0-c: 사용자 분리 측정과 중첩 `DashSet` 제거 (`mem-users`, `mem-p0c`, `ab-p0c`)

**사용자 분리 측정**: 지금까지 모든 벤치마크 연결은 같은 사용자(`ticket=dev` → `user:dev`)였다. 개발용 티켓 `dev:<id>`와 부하 생성기 `--distinct-users`로 연결마다 다른 사용자를 쓰게 했다(`bench/run-mem-users.sh`, 유휴 1만 연결, 3회).

| 빌드 | 사용자 1명 | 연결마다 다른 사용자 |
|---|---|---|
| 변경 전 (`ec00984`) | 20.5~20.7 KB/연결 | **24.2 KB/연결** (+3.5) |
| 중첩 `DashSet` 제거 후 | 18.5~18.8 | **18.9** |

- 연결마다 사용자가 다르면 변경 전에는 연결당 3.5 KB가 더 들었다(사용자별 `DashSet` 2개). 제거 후에는 사용자 수와 무관하다. **실제 조건(연결마다 다른 사용자) 기준 24.2 → 18.9 KB, −22%.**
- **설계 추정 정정**: `DashSet` 하나를 약 7 KB로 추정했지만, dashmap의 샤드 수는 **프로세스가 쓸 수 있는 CPU 수(CPU 고정 반영)** × 4로 정해진다. 벤치마크 서버는 8코어 고정이라 샤드 32개(약 1.8 KB)였다. 고정 없이 24스레드면 128개(약 7 KB), 64코어면 256개(약 14 KB) — **중첩 `DashSet`의 비용은 서버 코어 수에 비례해 커졌을 것이다.**

**CPU·지연** (같은 세션 교차 A/B, 3회 중앙값):

| 시나리오 | CPU µs/전달 이전 → 이후 | p99 ms (3회) | KB/연결 (부하 중) |
|---|---|---|---|
| rooms:120 | 5.37 → 5.57 (잡음 범위) | 3.2~4.9 → 2.8~8.7 | 25.6 → 23.2 |
| rooms:240 | 3.33 → 3.41 (잡음 범위) | 16.0~29.5 → **11.1~12.0** | 41 → 31 |

- 전달당 CPU는 변하지 않았다. 프로파일의 "레지스트리·Presence 12.3%"는 대부분 **세션 레지스트리 조회**(문자열 해시, `Connection` 복제)였고, 안쪽 집합 자체는 아니었다 → P1(핸들·스냅샷)의 몫.
- 216만/s의 꼬리 지연과 부하 중 메모리는 줄었다.

### 성능 P0-g: 쓰기 타임아웃을 막힐 때만 (`ab-p0g`, 프로파일 `rooms120-p0g`)

쓰기 묶음마다 `timeout()`으로 타이머를 등록하던 것을, 먼저 타이머 없이 한 번 폴링하고 `Pending`일 때만 마감을 걸도록 바꿨다. 느린 소비자 보호가 그대로인지 확인하는 통합 테스트(`tests/writer_timeout.rs`: 읽지 않는 클라이언트가 쓰기 타임아웃으로 끊기는지)를 추가했고, 마감을 걸지 않게 일부러 망가뜨리면 이 테스트가 실패함을 확인했다.

- 같은 세션 A/B(3회 중앙값): CPU µs/전달 rooms:20 6.74 → 6.36, rooms:120 5.14 → 5.27, rooms:240 3.67 → 3.61 — **모두 잡음 범위**. 종단 간 CPU로는 5% 크기의 효과를 가를 수 없다.
- **프로파일로 확인**(rooms:120): 타이머 범주 4.7% → 2.9%, 레지스트리·Presence 10.2% → 7.0%(P0-c 효과). 남은 2.9%는 세션 루프 `select!`가 매 반복 폴링하는 **세션별 ping·idle 타이머**의 `Sleep::poll` — P0-d(스위퍼)의 대상이다.

### 성능 P0-d: 종료 신호 경량화와 스위퍼 (`mem-p0d`, `ab-p0d`, 프로파일 `rooms120-p0d`)

세션마다 있던 종료 요청 채널(`mpsc`, 용량 1이어도 32슬롯 블록을 미리 할당)과 타이머 2개(ping 20초, idle 검사 1초)를 없앴다. 다른 task의 종료 요청은 세션별 `SessionSignals`(`Mutex<Option>` + `Notify`)로, keep-alive와 idle 판정은 서버 전체에서 **스위퍼 task 하나**가 1초마다 모든 세션을 훑어 처리한다. 동작을 지키는 통합 테스트(`tests/keepalive_idle.rs`: 응답하지 않는 클라이언트에게 약 5초에 Ping, 10초에 `sys.error TIMEOUT` + close 1000 `idle_timeout`)를 **변경 전에** 추가해 통과를 확인한 뒤 바꿨다.

| CPU µs/전달 rooms:240 | 3.41 | 3.41 |

### 성능 P0-f: 전역 할당자 mimalloc (`mem-alloc`, `ab-alloc`) — 채택하지 않음

같은 코드(`e0ebf3d`)를 시스템 할당자(glibc)와 `--features mimalloc`으로 빌드해 같은 세션에서 비교했다.

|---|---|---|
| 유휴 1만 연결 KB/연결 (다른 사용자 / 1명) | **16.2 / 16.0** | 18.7 / 19.0~19.9 |

- 결정: **기본값은 glibc 유지.** feature는 다른 환경에서 다시 재 볼 수 있게 남긴다.

### 성능 P1-a: 룸 멤버가 전달 핸들을 직접 보유 (마이크로 벤치, `ab-p1a`, 프로파일 `rooms120-p1a`)

Presence의 룸 멤버 목록이 세션 키 문자열 대신 **전달 핸들(`Member { key, conn }`)** 을 갖는다. 발행은 룸의 샤드 읽기 락 한 번 안에서 멤버를 순회하며 `try_send` — 수신자마다 하던 키 문자열 복제, 레지스트리 해시 조회, `Connection` 복제가 사라졌다. 같은 세션이 같은 룸에 두 번 join하면 사용자↔룸 참조가 두 번 세어지던 버그도 고쳤다(join을 멱등으로, 테스트 추가).

**마이크로 벤치 `publish_room`(발행 1회, criterion 중앙값)**:

| 룸 인원 | 이전 (기준선 `4b73999`) | 이후 | 수신자당 |
|---|---|---|---|
| 10 | 4.5 µs | **0.37 µs** | 약 37 ns |
| 100 | 18.4 µs | **3.28 µs** | 약 33 ns |
| 1,000 | 201 µs | **35.0 µs** | **약 35 ns** (설계 목표 ≤ 50 ns) |

**종단 간 같은 세션 A/B** (3회 중앙값, CPU µs/전달): rooms:120 4.49 → 4.39, rooms:240 3.40 → 3.43, broadcast:10(1,000명 룸) 8.99 → 9.55, broadcast:50 7.49 → 7.39 — **모두 잡음 범위**. 1,000명 룸의 p50·p99도 차이 없음.

**프로파일**(rooms:120): 레지스트리·Presence 6.6% → **2.2%**, publish_room·deliver 7.6% → **6.2%**. 약 6%p 줄었지만 종단 간 CPU의 실행 간 흔들림(±10%)에 묻힌다.

**해석**: 발행자 쪽 팬아웃은 이제 수신자당 약 35 ns로, 전달 1건 전체 비용(3.4~9 µs)의 1% 수준이다. 남은 비용은 수신자 쪽 — 커널 송신(46%, netlab에서는 상대 수신 포함), tokio 런타임(15%), WebSocket 프레이밍(14%)이다. **다음 레버는 P2(전송 재작성)와 P3(코어 간 깨움)** 이고, P1의 나머지(ID 인터닝)는 남은 레지스트리 2.2%가 대상이라 효과가 작다.

### v2-4: Hot 슬롯 틱 송신 (`tick-0v30.jsonl`, `tick-0v60.jsonl`)

같은 바이너리(`28f3a62`)를 `policy.hot_tick_hz` 0(즉시)과 30·60으로 같은 세션에서 교차 측정했다. 부하 생성기 `--lane hot2`: v2 키 있는 Hot 프레임(발행자마다 키 하나), 10명 룸 100개 전원 발행. 키별 최신값 슬롯이 적용되므로 전달 수가 줄 수 있어 **CPU는 전달당이 아니라 서버 전체 사용 코어**로 비교한다.

| 송신 / 틱 | 서버 CPU (코어, 3회 중앙값) | 전달률 | 지연 p50 / p99 (ms) |
|---|---|---|---|
| 60 Hz / 즉시 | 2.07 | 1.00 | 0.53 / 1.3 |
| 60 Hz / **60 Hz** | **0.88 (−57%)** | 0.99 | 8.4 / 16.6 |
| 60 Hz / 30 Hz | 0.66 (−68%) | 0.50 | 9.1 / 17.5 |
| 120 Hz / 즉시 | 4.85 | 1.00 | 0.8 / 2.7 |
| 120 Hz / **60 Hz** | **1.26 (−74%)** | 0.52 | 4.7 / 9.4 |
| 120 Hz / 30 Hz | 1.01 (−79%) | 0.25 | 4.5 / 9.6 |

- 송신률과 틱이 같아도(60/60) CPU가 절반 이하로 준다: 수신자마다 룸 멤버 9명의 업데이트를 틱당 flush 한 번에 보낸다.
- 대가는 최대 한 틱의 추가 지연(60 Hz에서 p99 약 +15 ms). 송신률이 틱보다 높으면 키별 최신값만 남는다(전달률 0.25~0.52는 설계된 동작).
- **한계**: 지연은 전달된 프레임만 잰 값이다. 상태 동기화의 판정 지표인 신선도(AoI)는 이 부하 생성기 모드에 아직 없다 — 틱의 신선도 비용은 평균 반 틱으로 예상되지만 미측정.
- 판단: 틱은 기본 꺼짐(0)을 유지하고, CPU가 병목인 대규모 상태 동기화 테넌트가 고르는 옵션으로 둔다.

### ADR 0007 단계 1: 자체 송신 경로 프로토타입 (`raw-ext`, `raw-hot`, 프로파일 `rooms120-{tg,raw}`) — 기준 미달

- **Redis 자체는 이력이 없으면 싸다.** 발행 1건에 1.2~3.7 µs(부하가 높을수록 파이프라인 효과로 싸짐). rooms:240에서도 Redis는 코어의 약 15%만 썼다.
- **rooms:240에서 Redis Ext가 무너진 원인은 게이트웨이 안의 직렬화다(추정).** Redis에서 돌아온 모든 프레임의 팬아웃(초당 216만 전달)이 수신 task 하나에서 일어난다. 단일 노드에서는 같은 팬아웃이 발행한 세션 task들에서 병렬로 일어난다. 같은 부하에서 Hot(로컬 먼저 전달, 수신 프레임은 버림)은 단일 노드와 같은 결과였다는 점이 이를 뒷받침한다. → **수신 팬아웃 병렬화**가 필요하다.
- **이력 Lua는 발행 1건에 14~18 µs로, Redis 한 코어의 천장이 약 6~7만 발행/s다.** rooms:120(발행 12만/s)부터 포화된다. 포화 시 송신 큐(최대 65,536)에 쌓이면서 지연이 수백 ms로 늘고, 큐가 차면 거절한다(설계대로 무한 대기는 없음). → **묶음 단위 Lua 처리**와 **송신 큐 대기 시간 상한**이 필요하다.
- **낮은 부하에서는 게이트웨이 CPU가 늘어난다**(rooms:20에서 +32%): 노드 간 인코딩·디코딩·복사와 수신 task 비용이다. 높은 부하에서는 묶음 효과로 +4~22%다.
- broadcast(발행 적음·팬아웃 큼)는 모든 대상이 같다. 노드 간 비용이 발행 수에 비례하기 때문이다.
- 한계: 노드 1개 + 같은 기계의 Redis(왕복 지연 거의 0)다. 실제 네트워크 너머의 Redis면 지연이 왕복만큼 더 붙는다.

#### M5: Hot 슬롯 해시 (`icount-m5.jsonl`, 2026-10-20)

키 있는 Hot 상태는 전달 1건에 명령어 543개로, 키 없는 Hot(189)의 2.9배였다. callgrind로 보면 비용의 약 절반이 수신자 슬롯의 `HashMap` 키를 SipHash로 해싱하는 데 들었다.
- 프로세스마다 무작위 시드를 쓰는 곱셈 접기 해시(foldhash와 같은 방식)로 바꿨다. 키 일부(`svc`, `key`)를 클라이언트가 고르므로, 충돌을 미리 계산할 수 없게 시드를 무작위로 둔다. 슬롯은 세션당 키 1,024개로 묶여 있다.
- 결과: **543 → 259 명령어/전달(−52%)**. 나머지 시나리오는 변화 없음.

#### M5: 낮은 부하의 클러스터 CPU 증가 분석 (프로파일 `{mem,redis}-rooms20`, `ab-m5-refresh.jsonl`, 2026-10-20) — 원인 미확정

rooms:20에서 Redis Ext는 게이트웨이 CPU를 단일 노드보다 24~32% 더 쓴다. `bench/profile-gateway.sh`(`cpu-clock:u`)로 두 구성을 비교했다.
- 범주별 비중은 거의 같다(tokio 런타임 47.6% → 51.3%, 송신 큐 9.0% → 10.2%). 할당자만 2.9% → 7.0%로 눈에 띄게 늘었다(노드 간 프레임 디코딩·복사).
- 특정 함수 하나가 늘어난 것이 아니라 세션 루프 전체가 더 자주 깨어난다. Redis에서 돌아온 프레임이 묶음으로 오면서 세션마다 깨어나는 횟수와 작업자 간 깨우기가 늘어난 것으로 보인다(가설, PMU가 없는 WSL2라 깨우기 수를 직접 세지 못했다).
- 상위 항목에 갱신 채널 `pop`(4.3~4.5%)이 있어, 갱신이 기다리는 중일 때만 그 채널을 폴링하도록 바꿨다. 같은 세션 교차 A/B 결과 차이는 잡음 범위다(rooms:20 이전 5.02 / 이후 4.89, rooms:120 4.41 / 4.75 µs/전달). 해롭지 않은 단순화라 유지한다.
- **결론:** 원인은 노드 간 디코딩·할당과 깨우기 증가로 추정하지만 확정하지 못했다. 높은 부하에서는 묶음 효과로 차이가 줄거나 역전된다(rooms:240에서 클러스터가 더 적게 씀). 낮은 부하의 절대 CPU는 작으므로 우선순위를 낮춘다. PMU가 있는 기계에서 다시 볼 항목으로 남긴다.

**참고 (churn 비용):** 입장·퇴장 반복(icount `churn`)의 비용은 대부분 `serde_json::Value` 기반 멤버 스냅샷의 할당이다. 스냅샷을 직접 직렬화하면 줄일 수 있다(M5 선택 과제).

  - 낮은 부하에서 크다: rooms:20에서 단일 노드 대비 +65%, 단일 노드 Redis 대비 +28%.
  - 부하가 높을수록 줄어든다: rooms:120에서 +24%·+10%.
  - 방송형은 오히려 적다(−10%). 노드마다 수신자 절반만 맡기 때문이다.
  - 비용의 원인: 모든 노드가 모든 발행을 Redis에서 받아 디코딩한다(룸에 그 노드의 멤버가 있으면).
- **Redis CPU는 구독 노드 수에 비례한다.** 발행 하나를 노드마다 한 번씩 보내기 때문이다(rooms:120에서 3.9 → 6.5 s). 이력 Lua 비용은 노드 수와 무관하다.
- **rooms:240을 4+4코어로 나누면 용량을 넘는다.** 단일 노드도 이 부하에서 8코어의 약 89%를 쓰는데, 노드 간 디코딩이 더해지기 때문이다. 메시지는 대부분 도착하지만 큐가 쌓여 p99가 수 초다(RSS가 연결당 700 KB 안팎).
- **단일 노드 Redis Ext의 rooms:240(24만 발행/s)은 한계선이다.** 오늘 6회 중 3회 1.000, 나머지 0.88~0.94다(`cluster-m5-batch4k`는 3회 모두 1.000, p99 최대 74 ms). 노드 하나의 송신 큐가 한 번에 파이프라인 하나만 보내는 것이 상한이다. 노드당 발행 약 20만/s를 운영 상한으로 본다.
- 이력은 노드 수와 무관하게 Redis 한 코어가 천장이다(rooms:240에서 Redis가 89% 사용).

### 0.1.x: 테넌트 공정성 (`fairness-v1.jsonl`, `bench/run-fairness.sh`, 2026-10-21)

한 테넌트(A)가 몰아칠 때 다른 테넌트(B)가 얼마나 느려지는지 쟀다.
- B: 연결 200개, 룸 20개, 연결당 초당 10개 발행(약 2만 전달/s). 혼자일 때와 A가 몰아치는 동안을 비교했다.
- A: 연결 1,000개, 룸 100개. 연결당 초당 100개(90만 전달/s) 또는 200개(180만 전달/s, 노드 하나의 Redis 송신 한계 근처) 발행. A의 rate limit은 일부러 풀었다.
- 코어 배치: 게이트웨이 0~7, A의 부하 생성기 8~17, B의 부하 생성기 18~22, Redis 23. 각 3회.

| 구성 | A | B 전달률 | B p50 (ms) | B p99 (ms) | B p99.9 (ms) |
|---|---|---|---|---|---|
| 노드 1개 (memory) | 없음 | 1.000 | 0.18 | 0.5 | 0.8~1.0 |
| | 90만 전달/s | 1.000 | 0.21~0.25 | 1.1~1.4 | 1.7~2.8 |
| | 180만 전달/s | 1.000 | 0.54~0.57 | 2.5~3.1 | 3.5~5.6 |
| Redis 클러스터 노드 | 없음 | 1.000 | 0.26~0.28 | 0.6 | 1.3~1.6 |
| | 90만 전달/s | 1.000 | 0.70~0.76 | 1.8~2.2 | 3.6~4.4 |
| | 180만 전달/s | 1.000 | 1.9~2.9 | 6.7~16.0 | 12.9~29.2 |

**읽기:**
- **기아는 없다.** B는 모든 경우 메시지를 모두 받았고, 송신 큐가 B를 거절한 적도 없다.
- **격리도 없다.** B의 지연은 A가 만든 전체 부하의 지연을 따라간다.
  - 노드 1개: CPU를 나눠 쓴다.
  - Redis 노드: 송신 큐가 테넌트 구분 없는 FIFO라 B의 프레임이 A의 묶음 뒤에서 기다린다. 한계 근처에서 B의 p99는 혼자일 때의 11~27배다.
- **지금의 대책:** 테넌트별 rate limit(`policy.rate_limit_*`)으로 한 테넌트의 몫을 제한한다.
- **구조적 개선 (0.2 과제):** 송신 큐를 테넌트별로 나눠 차례로 비운다. 같은 룸의 구독·presence 명령과의 순서를 지키는 설계가 필요하다. 노드 1개의 CPU 경합은 이것으로 해결되지 않는다.
