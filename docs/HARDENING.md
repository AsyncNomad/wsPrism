# Hardening Log

wsPrism을 "엔터프라이즈급에 가깝게" 끌어올리기 위한 작업 기록이다.
결함 목록, 우선순위, 내린 결정과 기각한 대안, 아직 못 본 사각지대를 남긴다.
작업 브랜치: `hardening` (main 기준).

## 작업 원칙

- 수정 하나 = 커밋 하나 (conventional prefix). 포맷/리팩터와 동작 변경은 커밋을 섞지 않는다.
- 결함 수정은 **재현 테스트 먼저** 작성 → 실패 확인 → 수정 → 통과.
- 게이트: `cargo fmt --all --check` / `cargo clippy --workspace --all-targets --locked -- -D warnings` / `cargo test --workspace --locked` (CI: `.github/workflows/ci.yml`).

### 결정

- **`Cargo.lock` 커밋**: 이 워크스페이스는 바이너리(게이트웨이)를 배포한다. 재현 가능한 빌드와 CI `--locked`를 위해 lock을 고정한다.
- **gateway lib의 panic 금지**: 문서상 "panic-free"를 표방하므로 lint로 강제한다. `main.rs`(bin 타깃)는 기동 실패 시 즉시 종료가 맞으므로 예외로 둔다.
- **MSRV 미선언** (당시): clippy 제안으로 `u32::is_multiple_of`(Rust 1.87+)를 쓰게 됐다. → 이후 MSRV 1.95를 선언하고 CI에서 검사한다(ADR 0009 §5-4).

#### S3 결정 기록

- **수정**: `chat.send`는 발신 *세션*이 해당 룸에 join한 경우에만 발행하고, 아니면 `NOT_ALLOWED`. `Presence::is_member` / `RealtimeCtx::is_in_room` 추가.
- **세션 단위 vs 유저 단위**: 세션 단위로 판정한다. 라우팅(Presence)이 세션 단위이고, 같은 유저의 다른 탭이 join했다고 이 탭이 그 룸에 말할 수 있게 하면 "받지 못하는 룸에 쓰기"가 가능해진다.
- Hot Lane(echo)은 join 성공 시에만 설정되는 `active_room`으로만 발행하므로 별도 검사 불필요. 단, 강제 종료(kick)된 세션이 루프를 계속 도는 동안 로컬 `active_room`으로 발행할 수 있는 문제는 C8로 별도 추적.

#### S4 결정 기록

- **원인 확인**: 수정 전 동작을 임시 테스트로 관찰했다. 같은 `sid` 재접속 후 예전 연결이 끊기면 그 정리 코드가 **살아 있는 새 연결의 레지스트리 항목을 삭제**했다(연결은 붙어 있는데 서버는 모르는 고아 상태). 테넌트 카운터도 +1 누수.
- **근본 수정 — 내부 키 분리**: 레지스트리/Presence 키를 `tenant::user::sid#<conn_id>`로 바꿔 연결마다 유일하게 만든다. 클라이언트가 고르는 `sid`는 표시용 식별자로만 남는다(`RealtimeCtx::session_id()`). 키 공유 자체가 불가능해지므로 정리 순서·타이밍과 무관하게 안전하다.
  - 기각: *세대 번호로 정리 조건부 실행* — 레지스트리는 막을 수 있지만, kick된 예전 루프가 같은 키로 다시 join하면 Presence에서 새 연결의 키로 섞여 들어간다(C8과 결합). 키를 분리하는 쪽이 문제를 원천 제거.
- **정책 — 같은 sid는 교체(takeover)**: 같은 user가 사용 중인 `sid`로 접속하면 예전 연결을 `sys.kicked{reason:"replaced"}` + close 1008로 내보내고 새 연결을 받는다. 세션 한도 평가 *전에* 교체하므로 교체가 한도를 소모하지 않는다.
  - 기각: *거부* — 네트워크 단절 후 재접속하는 탭이 흔한 정상 사례인데, 예전 연결이 idle 타임아웃(기본 60s)으로 정리될 때까지 재접속이 막힌다.
  - 전제: 현재 인증 스텁에선 모든 클라이언트가 `user:dev`라 서로의 sid를 교체할 수 있다. 실제 인증(Phase 4) 후엔 *같은 유저*만 교체 가능.
- **강제 종료 경로 통합**: kick_oldest와 replace가 `evict_session` 하나를 공유한다(레지스트리 제거 → Presence 정리 → 게이지 감소(C2 원칙) → 통지·close).
- **프로토콜 변화**: 강제 종료 close 프레임의 reason이 고정 `"kicked"`에서 사유 문자열(`max_sessions_exceeded` / `replaced`)로 바뀌었다. `sys.kicked.data.reason`은 기존과 동일 형식.

#### S5 결정 기록

- **수정**: `ws_upgrade`에서 테넌트를 먼저 조회하고, 메트릭 라벨은 *설정에 있는 id* 또는 고정값 `_unknown`만 쓴다. 레이트리밋은 여전히 테넌트 검증보다 먼저 적용된다(조회는 읽기 전용이라 순서를 바꿔도 비용 차이 없음).
- **신규 계측**: 미등록 테넌트로 인한 400도 `handshake_rejections{reason="unknown_tenant",tenant="_unknown"}`로 센다(이전엔 미계측).
- **예약어**: `_unknown`과 실제 테넌트가 겹치지 않도록 `_`로 시작하는 테넌트 id를 설정 검증에서 거부한다.
- **감사**: 모든 메트릭 라벨 값을 점검. `tenant` 외에는 전부 정적 문자열 또는 `ClientCode::as_str()`(고정 집합)이다.

#### S6 결정 기록 (S5 재현 테스트 작성 중 발견)

- **원인**: `entry(ip).or_insert_with(..)`가 돌려준 `RefMut`(샤드 쓰기 락)이 `self.per_ip.len()`(전 샤드 읽기 락) 호출 시점까지 살아 있었다. 같은 스레드의 자기 교착이며, async가 아닌 블로킹 락이라 tokio 워커 스레드 자체가 멈춘다. `tokio::Mutex`를 샤드 락 안에서 `.await`하는 것도 같은 위험이 있었다.
- **수정**:
  - `check()`를 동기 함수로 바꾸고 DashMap guard는 **한 표현식 안에서만** 쓴다. `if let` 조건식에 guard를 두지 않는다(edition 2021에서는 else 블록까지 살아 있음).
  - 짧은 임계 구역이라 `tokio::Mutex` → `std::Mutex`. poison은 버킷이 단순 데이터이므로 `into_inner()`로 복구.
  - 검사 순서 **IP → 전역**: 한 IP의 폭주가 자기 버킷에서 막혀 전역 예산을 소모하지 못한다(이전엔 IP 거절 전에 전역 토큰을 먼저 소비).
  - 메모리 상한: `max_ip_entries` 하드캡. 캡에서 새 IP가 오면 (최대 초당 1회) *버킷이 가득 찬* 엔트리만 축출(새 엔트리와 구별 불가 → 무손실). 그래도 자리가 없으면 그 IP는 추적하지 않고 전역 버킷만 적용.
  - 기각: 기존 무작위 10% 축출 — 공격자 엔트리가 지워지면 burst가 리셋되어 우회 가능.
- **테스트 장치 변경**: 서버를 별도 OS 스레드·런타임에서 띄우고 핸드셰이크에 타임아웃을 건다. 서버가 멈추면 테스트가 *걸리는* 대신 *실패*한다.
- **동일 패턴 감사**: `SessionRegistry`, `Presence`, `obs::metrics`의 DashMap 사용을 점검. guard는 문장 단위로 해제되거나 명시적 `drop` 후 재접근하며, 맵 간 락 순서 역전 경로도 없음.

#### S1 결정 기록

- **수정**: Hot 분기에도 연결 단위 토큰버킷 검사 추가. 초과 시 조용히 drop하고 `policy_decisions{lane="hot",reason="conn_rate_limit"}` 증가(Ext와 동일한 처리).
- **버킷 공유**: Ext와 Hot이 연결당 **하나의** 버킷을 공유한다. 설정에 `rate_limit_rps`가 하나뿐이고, 테넌트 스코프 리미터도 이미 두 레인이 공유하기 때문이다. 레인별 예산이 필요해지면 `hot_rate_limit_rps` 같은 별도 설정으로 확장한다. 공유 동작은 `hot_and_ext_share_one_connection_budget` 테스트가 고정한다.
- 참고: `select!` 매크로 내부는 rustfmt가 포맷하지 않아 들여쓰기가 고르지 않다. `run_session` 분해(Phase 3) 때 해소한다.

#### S2 결정 기록

- **수정**: 업그레이드 시 `max_message_size`/`max_frame_size`를 테넌트 `max_frame_bytes`로 설정. 초과 시 tungstenite가 *헤더만 보고* 거절하므로 본문 버퍼링·JSON 파싱이 일어나지 않는다. 기존 `check_len`은 2차 방어로 유지.
- **클라이언트 통지**: 초과 시 RFC 6455 close **1009**(Message Too Big)를 보내고 `policy_decisions{lane="transport",reason="frame_too_large"}`를 증가.
- **에러 판별**: `axum::Error` → `tungstenite::Error::Capacity(MessageTooLong)` downcast. 이를 위해 gateway가 `tungstenite = "0.24"`를 직접 의존한다. **axum이 쓰는 버전과 반드시 같아야 한다** — 다르면 downcast가 조용히 실패하고 1009 대신 그냥 끊긴다. `tests/s2_message_size.rs`가 이를 잡는다(`Cargo.lock`에 tungstenite가 1개 버전만 있어야 함).
- **Lingering close (500ms)**: 처음 구현에선 테스트가 약 1/6 확률로 실패했다(close 프레임 대신 연결 리셋). 원인: tungstenite는 초과 프레임의 헤더만 소비하고 본문을 건너뛰지 못해 이후 읽기도 같은 에러만 반복한다. 미수신 데이터가 남은 소켓을 닫으면 커널이 FIN 대신 RST를 보내 피어가 close 프레임을 버릴 수 있다. close 전송 후 500ms 대기로 해결(60/60 통과).
  - 기각: *본문 드레인* — axum이 raw 소켓을 노출하지 않고 tungstenite가 본문 skip을 지원하지 않음.
  - 기각: *정상 close 핸드셰이크 대기* — 위와 같은 이유로 피어의 close 응답을 읽을 수 없음.
  - 비용: 초과 전송 연결마다 task가 500ms 더 산다. 읽지 않으므로 메모리는 TCP 흐름제어로 묶이고, 연결 수는 핸드셰이크 리미터가 묶는다.
- **테스트 장치**: `tests/common/mod.rs` — 실제 게이트웨이를 임시 포트에 띄우고 `tokio-tungstenite` 클라이언트로 붙는다. 이후 결함 재현 테스트도 이 장치를 쓴다.

#### C6 결정 기록

- **Ext 버전**: 검증을 core로 올렸다(`protocol::text::decode_envelope`, `EXT_PROTOCOL_VERSION`). Hot Lane과 같은 계층에서 프로토콜 계약을 강제하고, gateway codec은 이를 호출만 한다. v≠1 → `UNSUPPORTED_VERSION` + 1002.
- **토큰버킷**: 토큰으로 바뀐 시간만 소비하고 나머지는 이월. 가득 찬 버킷은 추가 시간을 적립하지 않는다(표준 토큰버킷). 테스트 작성 중 "burst=1이면 10s에 95개"를 버그로 오인했으나, 상한에 닿아 있는 동안 적립하지 않는 것이 정의상 맞다 — 지속율 테스트는 burst=2로 상한 영향을 배제. 구 로직으로 돌려 2개 테스트가 실패함을 확인.
- **Span**: `run_session` 안에서 `span.enter()` guard를 await 너머로 쥐던 것을, 업그레이드 클로저에서 span을 만들고 세션 future 전체를 `.instrument(span)`으로 감싸도록 변경. 재발 방지로 `clippy.toml`의 `await-holding-invalid-types`에 `tracing::span::Entered`/`EnteredSpan` 등록 → CI clippy가 차단(도입 시 기존 위반을 정확히 잡는 것 확인). 실제 바이너리 로그에 `ws{trace_id=.. t=.. u=.. s=..}` 필드가 붙음을 확인.

#### C1 결정 기록

- **재현 조건이 중요했다**: 읽기를 *완전히 멈춘* 수신자로는 재현되지 않는다(서버 writer 타임아웃 1.5s가 그 수신자를 끊어 금방 풀림). 문제는 **느리지만 꾸준히 읽는** 수신자(모바일 등): writer가 조금씩 진행해 타임아웃이 안 걸리는 동안 큐가 계속 차 있어, 발신자(및 룸 전체)가 가장 느린 멤버의 속도로 끌려간다. 50ms마다 1개씩 읽는 수신자로 3/3 재현(메시지 198개째에서 8s 초과).
- **기존 "Reliable"의 실제 의미**: 수신자 큐를 최대 1.5s 기다린 뒤 **조용히 버림**. 발신자를 막으면서도 신뢰성은 보장하지 못했다.
- **새 의미**: `QoS::Reliable` = *순서대로 빠짐없이 전달하거나, 불가능하면 수신자를 `slow_consumer`(1008)로 끊는다*. 발신자는 절대 기다리지 않는다. `QoS::Lossy`는 큐가 차면 그 수신자에게만 버린다. 끊긴 수신자는 재접속으로 상태를 다시 맞춘다.
  - 기각: *팬아웃을 별도 task로 spawn* — 발신자는 안 막히지만 같은 발신자의 연속 메시지 순서가 수신자별로 뒤섞일 수 있고, 느린 수신자 문제(무한 대기 task 누적)는 그대로.
  - 기각: *발신자별 순차 팬아웃 워커* — 순서는 지키지만 구조가 크고, 결국 느린 수신자에 대해 같은 선택(버림/끊음/대기)을 해야 한다.
- **통합**: 모든 송신 경로(`send_to_user`, `send_to_session`, `publish_room*`)가 `deliver` 하나를 거치며 `out.qos`를 따른다. (이전엔 `send_to_user`/`send_to_session`이 QoS를 무시하고 항상 lossy.) `publish_room_lossy`/`_reliable`은 QoS를 강제하는 래퍼로 유지.
- **API 변화**: `QoS::Reliable { timeout_ms }` → `QoS::Reliable`(단위 variant), `publish_room_reliable`은 더 이상 `async`가 아니다.
- **메트릭 변화**: `wsprism_egress_send_fail_total` 제거 → `wsprism_egress_slow_consumer_closes_total`(reliable 메시지 때문에 끊은 수신자 수). 대시보드가 있다면 갱신 필요.
- **복구와의 정합 (2026-10-20, ADR 0011 R2)**: 이력 룸(`tenants[].history`)에서는 끊긴 수신자가 재접속하면서 마지막 offset부터 이어 받는다("끊고 재동기화" → "끊고 자동 복구"). 다시 보내는 메시지는 큐 한 칸(`OutFrame::Batch`)으로 들어가므로, 큐보다 많이 놓쳤어도 복구할 수 있다. 이력이 없는 룸은 여전히 클라이언트가 자기 백엔드에서 다시 맞춘다.

#### C4 결정 기록

- **수정**: `room:leave`는 `room`이 있으면 그 룸을, 없으면 active room을 떠난다(기존 클라이언트 호환). 떠난 룸이 active room이면 active room을 비운다(다른 룸으로 자동 전환하지 않음 — Hot Lane 대상이 암묵적으로 바뀌는 것을 피하려고).
- **응답**: `sys.left`에 `room` 필드 추가.
- **동작 변화**: 가입하지 않은 룸(또는 active room이 없는데 `room` 생략)을 떠나려 하면 `sys.error BAD_REQUEST`. 이전엔 무조건 `sys.left`를 돌려줘 클라이언트 버그를 가렸다.
- 테스트 주의: "한도 슬롯이 풀린다"만 보면 수정 전에도 통과한다(엉뚱한 active room이 빠져도 슬롯은 생김). 그래서 r2 멤버십이 유지되는지까지 확인한다.

#### C5 결정 기록

- **재현**: 단위 스트레스 테스트(스레드 2~4개가 같은 룸/유저에서 join·leave 4만 회 반복)로 5/5 재현.
  - leave가 순간적으로 빈 룸 집합을 지우면서 동시 join의 멤버십이 소실.
  - `user_index`에서 같은 유저의 동시 삽입 세션이 소실.
  - **테넌트 룸 카운터가 음수로 드리프트**(u64 wrap → 약 1.8e19). `max_rooms_total`을 쓰는 테넌트는 이후 **새 룸을 영구히 만들 수 없게 된다**.
- **수정**:
  - "비었으면 제거"를 `remove_if`로 원자화(`remove_from_set` 헬퍼). 삽입은 모두 `entry`(같은 샤드 쓰기 락)를 거치므로 두 연산이 직렬화된다.
  - 룸 집합 *생성*(`Entry::Vacant`)과 *제거*(`remove_if` 성공) 시점에만 테넌트 룸 카운터를 증감. 기존 `contains_key` 선판단 제거.
  - `max_rooms_total`은 CAS로 검사+증가를 한 번에 하여 **정확한 상한**이 됐다. (`tenant_room_cap_is_never_exceeded`는 수정 전에도 통과했으므로 과거 초과의 증거가 아니라 회귀 방지용.)
  - 유저↔룸 색인은 해당 user+room 참조 카운트 엔트리를 잡은 채로 갱신(join·leave 모두). 마지막 세션이 나갈 때의 색인 제거와 새 join이 섞이지 않는다.
  - 감소는 `checked_sub`로 0 아래로 내려가지 않게 한다.
- **락 순서**: `user_room_refs` → (`room_to_users`, `user_to_rooms`), `room_to_sessions` → `tenant_room_counts`. 역순으로 잡는 경로 없음.
- **여전히 best-effort**: `max_users_per_room`, `max_rooms_per_user` 검사는 색인을 잠그지 않고 읽는다. 정확하게 하려면 거버넌스 갱신을 라우팅보다 먼저 하고 실패 시 롤백해야 해서 보류.
- **CAS 헬퍼**: `AtomicU64::fetch_update`는 Rust 1.99에서 deprecated(`try_update`로 개명). MSRV를 더 올리지 않으려고 `compare_exchange_weak` 루프(`cas_update`)를 직접 쓴다.

#### C9 결정 기록

- **재현**: `session_queue_capacity: 1`로 요청 50개를 파이프라이닝하면 6/6회 응답 1~14개 후 세션이 영구 정지. 느린 클라이언트가 아니어도, 브로드캐스트로 큐가 *순간적으로* 찬 시점에 요청이 오면 같은 일이 생긴다. writer 타임아웃은 쓰기 arm에서만 동작해 이를 못 잡는다.
- **수정**: 루프 내 응답은 `reply!` 매크로(`queue_reply`, `try_send`)로만 넣는다. 큐가 차 있으면 `SLOW_CONSUMER` 통지 + 1008 `slow_consumer`로 종료하고 `policy_decisions{lane="transport",reason="slow_consumer"}` 증가. keep-alive ping은 큐가 차 있으면 이번 회차만 건너뛴다.
  - 기각: *응답을 버리기* — `sys.joined` 같은 응답을 조용히 잃으면 클라이언트 상태가 서버와 어긋난다.
  - 기각: *응답 전용 무제한 큐* — 메모리 상한이 사라지고 메시지 순서가 섞인다.
- **오탐 여유**: 기본 용량 1024에 연결당 레이트리밋(기본 burst 400)이 있어, 정상 클라이언트가 자기 응답만으로 큐를 채우기는 어렵다.
- **설정 추가**: `gateway.session_queue_capacity`(기본 1024, 1..=1048576). 테스트에서 결정적 재현을 위해 필요했고 운영에서도 조정할 만한 값이라 노출.
- **부수 정리(C6 일부)**: 클라이언트 Ping에 대한 수동 Pong 제거. tungstenite 0.24가 이미 자동 응답함을 소스로 확인(`protocol/mod.rs`의 `OpCtl::Ping` 처리).

#### C3 · C8 결정 기록

- **구조**: 세션 루프가 `break` 대신 종료 사유 `Exit`(`Peer` / `Abort` / `Close(CloseSpec)` / `TooBig`)를 반환하고, 종료 처리는 루프 밖 한 곳에서 한다.
- **정중한 종료 `close_session`**: ① 송신 큐를 닫고 이미 쌓인 메시지를 순서대로 전송 → ② 사유 통지(`sys.error`/`sys.kicked`) → ③ close 프레임 → ④ 피어의 close를 최대 1s 대기(깨끗한 TCP 종료). 쓰기는 `writer_send_timeout_ms` 하나의 예산을 공유하며, 막힌 피어는 포기한다.
  - 큐 플러시를 먼저 하는 이유: 통지가 그보다 먼저 큐에 들어간 메시지를 앞지르지 않게(순서 보장).
- **C8 — 제어 채널**: `Connection`에 `ctl: mpsc::Sender<CloseSpec>`(용량 1)을 추가. kick/replace/drain은 메시지 큐에 Close를 넣는 대신 `ctl`로 종료를 요청하고, 루프는 즉시 빠져나와 `close_session`을 실행한다. 피어가 close에 응답하지 않아도 최대 ~(writer timeout + 1s) 안에 끝난다(이전: idle 타임아웃까지 루프가 계속 돌며 메시지 처리 가능).
- **등록 해제 시점**: 종료가 끝날 때까지 세션은 레지스트리에 남는다. `main`의 drain 대기가 레지스트리를 보고 있어서, 먼저 해제하면 종료 핸드셰이크가 끝나기 전에 프로세스가 내려간다. 그 사이 라우팅된 메시지는 닫힌 큐가 거절한다(egress drop 카운트에 잡힘).
- **인증은 업그레이드 전**: 티켓 검증 실패 → HTTP **401** + `handshake_rejections{reason="auth_failed"}`. 인증 안 된 클라이언트에게 소켓 task를 할당하지 않는다.
  - 트레이드오프: 브라우저 `WebSocket` API는 실패한 핸드셰이크의 HTTP 상태를 읽을 수 없다(1006만 보임). 티켓은 보통 REST로 미리 발급받으므로 오류 처리는 그 단계에서 하는 게 일반적이라 판단.
  - 반면 **세션 한도 초과(deny)는 업그레이드 후 in-band**(`sys.error TOO_MANY_SESSIONS` + 1008): 이미 인증된 사용자에게 "다른 곳에서 접속 중" 같은 이유를 보여줄 수 있어야 하므로.
- **종료 코드**: 정상/idle 1000, drain 1001, 디코드 오류 1002, 정책·kick·replace·세션 한도 1008, 크기 초과 1009, 테넌트 용량 경합 1013. `docs/PROTOCOL.md`에 표로 정리.
- **C9는 별도**: 루프 내 응답이 여전히 `out_tx.send().await`를 쓴다. 다음 커밋에서 처리.

#### C2 결정 기록

- **원칙**: 레지스트리에서 세션 항목을 *실제로 제거한 쪽*이 게이지를 1 감소시킨다. kick 경로가 이미 제거·감소했으면 피해 세션의 RAII 정리(`SessionCleanup::drop`)는 `remove_session`이 `None`을 돌려주므로 감소하지 않는다.
- Presence 정리는 계속 무조건 수행한다. kick된 세션이 루프 종료 전에 다시 join했을 수 있기 때문(C8).
- 테스트 주의: 버그가 있어도 kick 직후엔 게이지가 1로 보인다. 이중 감소는 피해 세션의 정리가 돈 *뒤에* 일어나므로 테스트는 정리 시간을 기다린 후 판정한다.

### 0.2: soak 확장·장애 조치 일관성 (2026-10-22, 외부 검토 #2)

| # | 결함 | 수정 |
|---|---|---|
| S2 | 복제가 뒤처진 상태의 Sentinel 장애 조치에서 **1회용 티켓이 두 번 수락됨**: 주 노드에서 `GETDEL`로 소비했는데, 그 삭제를 받지 못한 복제본이 승격되면 티켓이 되살아났다. 세션 표·멤버십·노드 슬롯·이력은 새 `run_id`로 다시 등록·복원되지만, 티켓 소비만은 아무것도 되돌려 놓지 않는다 | 티켓 소비 뒤 전용 연결에서 `WAIT`(`gateway.broker.replica_ack`, Sentinel이면 기본 복제본 1개·500 ms). 확인이 모자라면 그 로그인은 503(닫힌 실패). 회귀 테스트 `cluster_sentinel_ticket.rs`: `replicas: 0`이면 두 번 수락으로 실패, 기본값이면 통과(각 2회 확인) |
| S3 | 펜싱된 노드가 펜싱을 안 뒤 서버가 멈출 때까지(최대 250 ms 감시 주기) 발행을 계속 큐에 받아 200을 답했다. Redis가 모두 거부하므로 그대로 사라졌다 | 모든 룸 발행이 지나는 `route_queued`에서 `healthy()`가 거짓이면 즉시 `UNAVAILABLE`(서버 API 503). 테스트 `a_fenced_node_refuses_publishes` |

- **문서화한 한계:** 노드가 `slot_ttl_s`보다 오래 Redis와 끊긴 사이 슬롯을 빼앗기면, 끊긴 동안 큐에 받은 발행(최대 `outbox_max_wait_ms` 분량)은 사라진다. 펜싱된 노드의 쓰기는 Redis가 모두 거부해야 하므로 의도된 동작이다. kill -9와 같은 종류의 손실이다(CLUSTER.md 「서버 API의 200」).
  - soak가 이것을 "알림 없는 유실" 위반으로 처음 잡았고, 판정기는 이 구간을 면제한다.
  - 면제한 개수는 요약의 `lost_with_a_queue`에 보인다.
- **기각한 대안:** 펜싱된 노드도 큐의 Text 프레임은 발행하게 하는 것. 늦게(수 초 뒤) 도착한 발행이 새 소유자의 같은 슬롯 번호(`origin`)로 해석되어 `except`·로컬 판정이 틀어진다. 또 "슬롯을 잃은 노드는 아무것도 쓰지 않는다"는 불변식이 깨진다.
- **soak 확장:** 노드마다 Redis 앞에 결함 프록시를 둔다(`startProxy`).
  - 넣는 장애: 지연(20~800 ms), blackhole(0.3~2초 또는 4~7초), 연결 리셋.
  - 슬롯을 실제로 빼앗는 시나리오(`takeover`): 노드를 멈추고, TTL이 지난 뒤 새 노드가 그 슬롯을 얻게 한다. 깨어난 노드가 스스로 멈춰야 한다.
- **하네스 결함 세 가지(제품 결함 아님):**
  1. 지연 프록시가 지연이 줄어드는 순간 **TCP 바이트 순서를 뒤바꿨다.** 새 청크는 즉시 보내고 옛 청크는 아직 타이머에 걸려 있었다. 실제 TCP에서는 일어날 수 없는 일이다. 증상은 어느 노드도 전달하지 않은 오프셋 구간이었다(시드 11, 33개). 방향별 FIFO로 고쳤다.
  2. `takeover`가 "멈춘 노드의 슬롯"을 빼앗는다고 가정했다. 하지만 새 노드는 비어 있는 슬롯 중 번호가 가장 낮은 것을 가져간다(`lease`). 앞선 재시작 때문에 더 낮은 빈 슬롯이 있으면 다른 슬롯을 가져갔다. 그러면 멈춘 노드가 계속 도는 것이 정상인데, 위반으로 보고됐다. 지금은 Redis에서 사라진 슬롯을 찾아 더 낮은 빈 슬롯을 임시 값으로 채우고, 판정은 슬롯 키의 값으로 한다.
  3. `docker pause`로는 복제 지연을 만들 수 없다. 멈춘 동안에도 커널이 복제 스트림을 소켓 버퍼에 받아 두고, 재개하면 반영한다. 그래서 S2 테스트가 처음에는 수정 없이도 통과했다. 지금은 복제본을 네트워크에서 분리(`docker network disconnect`)한다.
- **결과(수정 후):** 시드 11·7·3·21, 각 3분. 장애 37~46회, 메시지 약 2만 1천, 펜싱 1~5회. 위반은 모두 0건이고 `lost_with_a_queue`도 0이다(S3 수정 뒤에는 면제 구간이 쓰이지 않았다).
- **15분 soak(시드 8) 첫 실행이 감시 장치에 걸렸다. 하네스 결함이고 유실은 없었다.**
  - 그 시점까지 메시지 11만 2천 개가 모든 클라이언트에 도착했다.
  - 원인: node 0이 스스로 멈춘 뒤(exit 1, 펜싱) `stopNode`가 다시 오지 않을 `exit` 이벤트를 기다렸다. 이미 끝난 프로세스를 처리하도록 고쳤고, soak 타임라인에 "스스로 종료"를 남기게 했다.
  - 수정 후 재실행(시드 8, 15분): 장애 177회, 메시지 8만 9,616개, 재접속 63회, gap 알림 333회, 펜싱 21회. 위반 0건, `lost_with_a_queue` 0.

  - 그러면 원래 노드는 펜싱되어 멈추고 재시작된다. 안전하지만 불필요한 재시작이다.
  - **수정(2026-10-23):** 노드가 Redis에 다시 닿으면(구독 재연결, 제어 채널 재연결, 프로브 회복) heartbeat를 즉시 한 번 돌린다. 슬롯을 되찾는 데 최대 10초 걸리던 것이 54 ms가 됐다(`cluster_slot_refresh.rs`, 수정 전 실패). 같은 김에 제어 채널의 구독 실패 재시도에 지수 백오프를 넣었다.

  - 원인: 송신 큐가 구독 명령마다 앞의 발행·presence를 모두 내보내고 `SUBSCRIBE` 하나의 확인을 기다렸다. 노드 전체가 구독을 한 번에 하나씩 처리했다.
  - 수정: 구독을 모아서 보낸다. 순서는 "같은 룸의 뒤 프레임보다 먼저"만 지킨다. 이 노드의 Ext 프레임은 구독을 거쳐 로컬 멤버에게 오기 때문이다. 구독 연결별로 동시에 보내고 연결 안에서는 파이프라인으로 보낸다. 결과: 8~10배, join p50 28 → 1 ms.
  - **함정 하나를 피했다:** 여러 채널을 한 번에 `SUBSCRIBE`하면 채널마다 확인 응답이 따로 온다. redis-rs는 응답 하나로 요청 하나를 끝내므로, 남은 응답이 다음 요청을 실행 전에 끝난 것으로 처리할 수 있다. 그래서 채널 하나짜리 명령을 파이프라인으로 보낸다.
  - **순서 변경의 근거:**
    - 같은 룸의 presence 변경이 그 룸의 구독보다 먼저 반영될 수 있다. 다른 노드에서는 join과 구독 사이의 순간과 같다. join 응답은 구독 뒤에 나간다.
    - 노드–룸 색인 `SREM`은 묶음 안에서 마지막 명령이 해제인 룸만 한다. "해제 → 재가입"이 한 묶음에 오면, 재가입 presence가 넣은 색인을 지우지 않아야 하기 때문이다.
  - 검증:
    - 워크스페이스 전체 테스트(Redis 포함), JS 카오스 7개, soak 3분(위반 0).
    - 같은 세션 A/B로 발행 처리량 무변화를 확인했다(6개 시나리오 × 3회).
- **외부 검토 #3 뒤 (구독 묶음의 경쟁 조건):**
  - **P2 (결함, 수정):** 구독 확인 대기에 5초 제한이 있었다. 넘으면 구독 전인데도 `sys.joined`를 보냈다. Redis가 멈춘 동안 들어온 멤버는 그 사이 다른 노드의 메시지(이력 없는 룸)를 gap 알림 없이 놓칠 수 있었다. 수정 전부터 있던 결함이다. 이제 join이 `UNAVAILABLE`로 실패하고 멤버에서 빠진다. 테스트는 `an_unconfirmed_subscription_fails_the_join`(멈춘 시계)이다.
  - **P3 (성능 결함, 수정):** presence 이벤트를 켠 테넌트에서는 구독 묶음의 효과가 없었다. 원인은 두 가지다.
    - `member_joined` 프레임이 같은 룸의 구독을 앞당겨 비웠다.
    - 프레임과 presence가 바뀔 때마다 송신 큐가 비워졌다.

    룸 단위 순서만 지키게 바꿨다(BENCHMARKS 「세션 churn」, 9배). 테스트는 `membership_changes_and_frames_keep_order_per_room_only`다. 대가로 한 노드에서도 룸 사이의 발행 순서는 보장하지 않는다(CLUSTER.md).
  - **경쟁 조건 두 가지는 실제 Redis 테스트로 고정했다**(`cluster.rs`). 처음 쓴 두 테스트는 결함을 일부러 넣어도 통과했다(변이 시험). 루프백에서는 구독이 발행보다 항상 먼저 끝나고 묶음이 작기 때문이다. 노드 A 앞에 순서를 지키는 지연 프록시를 두는 방식으로 고쳤다.
    - `a_message_right_after_joined_arrives_from_another_node`: 지연 100 ms. 구독 대기를 건너뛰는 변이를 잡는다.
    - `rooms_joined_and_left_in_a_hurry_stay_subscribed_while_occupied`: 지연 10 ms, 세션 12개 × 룸 24개. join마다 다른 노드가 발행한 값을 받아야 한다. 묶음의 구독을 해제보다 먼저 보내는 변이를 잡는다.
  - **soak 프로브:** 노드마다 하나씩, 공유 룸 3개를 계속 들락날락하는 클라이언트를 넣었다. join 직후 다른 노드가 발행한 값이 와야 한다. 면제는 재접속·gap·큐 손실뿐이다. Redis 정지·재시작·연결 끊김과 동시에 돈다.
- **20분 soak(시드 51) 첫 실행: 위반 34건, 모두 판정기의 틈이었다.** 프로브 8만 4,754회는 위반이 없었다.
  - **이 WSL의 벽시계는 30초마다 약 2.3초씩 뒤로 간다**(20분에 34번). 판정기가 `Date.now()`로 시간 창을 비교했으므로 그 근처에서 판정이 틀어졌다. 이제 단조 시계(`performance.now()`)를 쓴다. 아래 Sentinel TILT도 같은 원인으로 보인다.
  - 손실 63건: node 2의 Redis 링크에 지연 +375 ms가 걸린 채 `kill -9`됐다. 큐에 받아 둔 메시지가 1초보다 오래 머물 수 있었다(대기 한계 1초 + 링크 왕복). kill 면제 창을 "1.5초 + 링크 지연 × 2"로 넓혔다.
  - 손실 9건: Redis가 빈 상태로 재시작되는 순간 다른 노드가 재시작되며 node 2의 슬롯을 가져갔다(위 「관찰」). node 2는 펜싱되어 큐를 잃었다. 판정기는 `takeover`·`freeze`·`partition` 장애로 생긴 펜싱만 면제했다. 이제 노드가 스스로 종료(펜싱)하면 원인과 관계없이 큐 손실로 면제한다.
  - 판정기를 넓힌 범위는 문서에 적힌 손실 종류(kill -9, 펜싱 때의 큐 손실)뿐이다.
  - 고친 판정기로 같은 시드를 다시 돌렸다(20분). 장애 248회, 메시지 12만 5,340개, 재접속 234회, gap 알림 423회, 펜싱 18회였다. 프로브는 정상 7만 4,776회, 늦음 10회, 면제 39회였다. **위반 0건.**
- **과부하 보호 (외부 검토 #3):**
  - 우려된 연쇄는 이렇다. 재접속 폭주가 제어 Redis를 포화시키면 → slot heartbeat가 늦어지고 → 슬롯이 만료되고 → 그 슬롯을 다른 노드가 가져가면 펜싱이 일어나 → 세션이 대량으로 닫히고 → 더 큰 폭주가 된다.
  - 코드로 확인하니 만료만으로는 펜싱되지 않는다. 그 사이 다른 노드가 슬롯을 가져가야 한다. 기본 TTL 30초에서 heartbeat는 10초마다라, 이 연쇄가 일어날 가능성은 낮다. 그래도 두 장치를 넣었다.
  - **접속 허용:** `PING` 지연(전용 연결, 250 ms마다)이나 대기 중인 세션 등록 수가 기준을 넘으면 핸드셰이크에서 503 `cluster_busy`를 준다. `Retry-After`는 1~5초로 흩뜨리고, 인증 전에 거절하므로 티켓을 소모하지 않는다.
    - 테스트: `cluster_admission.rs`. Redis를 3초 멈추면 새 접속은 즉시 503을 받고, 기존 세션은 유지되고, 끝나면 다시 받는다. 기능을 끄면 실패하는 것을 확인했다(변이 시험).
  - **heartbeat 전용 연결:** 일반 명령의 줄 뒤에 서지 않게 했다. 다만 Redis 자체가 포화되면 효과가 제한적이다(Redis는 단일 스레드).
  - "재접속 폭주로 제어 Redis 포화" 카오스는 이 기계로 재현할 수 없다. 노드 하나가 초당 약 4만 세션에서 먼저 막히고, Redis 한계는 약 9만 5천이다. 대신 soak의 Redis 정지 장애가 이 거절 경로를 거친다(5분, 위반 0).
- **CI 카오스 실패 (2026-10-23, push 뒤):** `a node stopped while Redis is slow`가 CI(2 vCPU)에서 실패했다. 노드 0의 클라이언트가 30초 동안 `connecting`에 머물렀다.
  - 로컬에서는 재현되지 않았다. 카오스 파일 전체를 2코어로 묶어(`taskset -c 0,1`) 돌리자 **다른 두 테스트(Redis 재시작 계열)가 매번** 실패했다.
  - 이분 탐색으로 `f593bef`(heartbeat 전용 연결)를 찾았다. heartbeat만 일반 명령 연결로 되돌린 빌드는 통과했고, 프로브만 끈 빌드는 실패했다.
  - **P4 (결함, 수정): 오래된 잠복 결함이었다.** Redis 재시작 뒤 구독이 다시 붙으면 노드는 그 사이의 메시지를 이력에서 채운다. 그런데 그 이력 읽기가 재시작 뒤 일반 명령 연결의 첫 사용이라, 죽은 옛 소켓에서 `broken pipe`로 실패했다. 재시도가 없어서 클라이언트는 gap 알림만 받고, 그 사이 메시지(이력에는 있음)를 받지 못했다.
    - 전에는 heartbeat가 1초마다 같은 연결을 써서 죽은 소켓을 먼저 만났기 때문에 드러나지 않았다.
    - 수정: 반복해도 안전한 읽기(이력 읽기, join의 멤버 목록)는 연결 수준 오류에서 한 번 더 시도한다(`read_again`). 그 사이 연결 관리자가 다시 연결한다.
    - 확인: 카오스 파일 전체를 2코어로 release 3회, debug 4회 돌려 모두 통과했다. CI에서 실패한 테스트만 2코어로 15회 돌려 실패 0이었다.
  - **안전장치 추가:** redis-rs의 연결 관리자는 응답 시간 초과 뒤에는 다시 연결하지 않는다. 그래서 프로브의 전용 연결이 시간 초과만 내는 상태에 빠지면, 노드가 새 세션을 영원히 거절하게 된다. 이제 프로브가 4번 연속(1초) 실패하면 전용 연결을 새로 만든다. CI의 정확한 증상(클라이언트가 `connecting`에 머묾)은 로컬에서 재현하지 못했다. 이 경로가 그 증상과 맞는 유일한 후보라 막아 두었다.
  - **진단 보강:** 카오스 시간 초과 보고에 클라이언트별 재접속 시도 수, 최근 종료 코드, 오류를 넣었다. 다음 CI 실패 때 원인이 바로 보인다.
  - **soak 판정기 결함 두 가지(제품 결함 아님):**
    - 같은 노드에 `kill -9`와 `takeover`가 동시에 걸리면, 판정기가 멈춘 옛 프로세스가 아니라 재시작된 새 프로세스(다른 슬롯)를 판정했다. 이제 멈춘 프로세스를 기억하고, 바뀌었으면 판정하지 않는다.
    - 같은 노드에 프로세스 장애 두 개가 겹치는 경우가 더 있었다(`freeze + takeover`: 짧은 정지가 먼저 풀려, takeover가 다른 빈 슬롯을 "빼앗은 것"으로 봄). 그래서 프로세스 장애(`kill -9`·SIGTERM·정지·takeover)는 노드당 하나씩만 걸리게 했다(`exclusive`). 링크·Redis 장애는 여전히 겹칠 수 있다.
    - `kill -9` 면제 창의 끝을 kill 시각으로 잡았더니, 이미 오고 있던 200이 몇 ms 늦게 기록되어 창 밖으로 나갔다(손실 1건). 창 끝에 250 ms 여유를 두었다.
    - 발행 API 호출이 시간 초과되면 발행자는 같은 번호를 다른 노드로 다시 보낸다. 멈춰 있던 노드도 그 요청을 받아 두었다면 같은 메시지가 두 번 갈 수 있다. 백엔드가 재시도할 때의 문서화된 동작이다. 판정기는 시간 초과 뒤 다시 보낸 번호의 중복만 허용한다.
  - 수정 뒤: 5분 soak 7회(시드 71~76, 75 재실행) 위반 0. 15분 soak(시드 81)은 장애 193회, 메시지 9만 5천, 프로브 6만 805회에서 위반 0. 카오스 파일 전체 2코어 2회 통과.
- **CI 카오스 재실패 (2026-10-23, 두 번째 push 뒤):** 같은 테스트가 다시 실패했다. 이번에는 보강한 진단 덕분에 원인이 보였다.
  - 노드 0이 멈출 때 클라이언트 세 개가 4103(드레인)으로 닫혔다. 그 뒤 **재접속을 단 한 번 시도했는데, 그 시도가 끝나지 않았고 오류도 없었다**(`attempts=1, errors=[]`).
  - **SDK 결함 (수정):** 접속 시도에 시간 제한이 없었다. 서버나 프록시가 핸드셰이크에 답하지 않거나, 거절된 핸드셰이크 뒤 `close` 이벤트가 오지 않으면 `connecting`에 영원히 머물렀다.
  - CI는 Node 22, 로컬은 Node 24다. Node 24는 503 핸드셰이크 뒤 `error`와 `close`를 모두 낸다(확인). Node 22에서 `close`가 빠지는지는 내려받지 않아 확인하지 못했다. 그 사이 노드 1은 Redis 쓰기 정지 중이라 503(`cluster_busy`)을 줬을 수 있다.
  - 수정: `connectTimeoutMs`(기본 10초) 안에 `sys.authed`가 오지 않으면 소켓을 닫고 실패한 시도로 처리한다. `error` 뒤 1초 안에 `close`가 오지 않아도 같다. 두 경우 모두 `error` 이벤트(`CONNECT_TIMEOUT`, `CONNECT_ERROR`)를 낸다.
  - 테스트: TCP만 받고 아무 말도 하지 않는 서버. 수정 전에는 영원히 멈췄고, 수정 뒤에는 시간 제한 후 재시도한다.
  - 같은 push에서 `history.rs::a_returning_client_gets_what_it_missed_in_order`도 한 번 실패했다("expected publish, got Timeout"). 로컬에서는 두 브로커 모드와 1코어로 각 30회씩 돌려도 재현되지 않았다. 이 테스트는 `msg`를 기다리는 동안 `publish`를 건너뛰므로, 순서가 바뀌어도 "시간 초과"로만 보였다. 이제 두 종류를 도착 순서대로 모아 정확한 순서와 비교한다. 엄격함은 같고, 다시 실패하면 실제 순서가 보인다. **원인 미확정.**
- **환경 주의:** 이 WSL에서 Sentinel이 시계 역행으로 TILT 모드(30초)에 자주 들어간다. 그 사이 복제본의 데이터 나이가 Sentinel 허용치(`down-after` × 10)를 넘으면 장애 조치가 "쓸 만한 복제본 없음"으로 중단된다. S2 테스트는 `WSPRISM_SENTINEL_DOWN_AFTER_MS=5000`으로 돌린다.

| F4 | **아주 먼 `exp`를 가진 토큰이 핸드셰이크를 패닉시킴.** `UNIX_EPOCH + exp`가 `SystemTime` 범위를 넘으면 덧셈이 패닉했다(발급자 서명이 필요해서 위험은 낮다). 연결 프록시가 돌려주는 `expires_at`도 같았다. | 범위를 확인하는 덧셈으로 바꿨다. 넘으면 만료 없음으로 처리한다. 테스트 `a_far_future_expiry_is_admitted_without_overflow`(수정 전 패닉). |
| F5 | **SDK가 재연결 뒤 rejoin에 실패한 룸을 영원히 버림.** 오류 종류와 관계없이 버렸다. 그래서 rejoin 중 연결이 또 끊기면(`DISCONNECTED`) 그 룸은 다음 재접속에서도 다시 들어가지 않아, 클라이언트가 조용히 메시지를 받지 못했다. P2 수정(구독이 확인되지 않으면 join 실패)과 겹치면 Redis 정지 중의 재접속이 룸을 잃게 됐을 것이다. | 일시적 오류(`UNAVAILABLE`·`RATE_LIMITED`·`TIMEOUT`·`INTERNAL`)는 같은 연결에서 백오프로 재시도하고, 연결이 끊긴 경우는 룸을 남겨 다음 연결이 다시 들어간다. 거절(예: `NOT_ALLOWED`)만 버린다. 가짜 WebSocket으로 순서를 정확히 재현한 테스트 `rejoin.test.mjs`(수정 전 2개 실패). |

검증: 고친 뒤 전체 테스트(Redis 포함·queued 모드), SDK 17개, 2코어 카오스 2회, 10분 soak(시드 91: 장애 128회, 메시지 6만 4천, 프로브 3만 4천) 모두 위반 0.

**살펴봤고 결함을 찾지 못한 곳(근거):**
- **인증:**
  - JWT: 알고리즘 고정, 설정한 `iss`·`aud`는 필수, `kid`로 연결 고리를 고른다.
  - JWKS: 모르는 `kid`의 재조회는 속도 제한, 대칭 키 제외, 오래된 키는 거절.
  - 1회용 티켓: 한 번만 쓰이고, 테넌트에 묶이고, 만료되고, 개수 상한이 있다.
  - 대역 내 갱신: 속도 제한, 다른 사용자로 바꾸기 금지, 좁아진 권한을 즉시 적용.
- **권한:** join(구독)·발행(발행 권한)·chat·Hot relay(룸 멤버 여부)의 모든 경로가 검사한다.
- **입력:**
  - 프레임 크기 제한은 WebSocket 계층에서 테넌트별로 건다.
  - 디코딩에 패닉 경로가 없다(퍼징).
  - 비테스트 코드에 `unwrap`·`expect`·`panic`이 없고(린트), 패닉할 슬라이스 인덱싱도 없다.
- **룸 이름과 Redis 키:** 룸 이름에는 출력 가능한 문자가 모두 오지만, 키·채널·참조 키 모두 앞부분이 안전한 문자의 테넌트·사용자 ID이고 접미사가 서로 달라 충돌하지 않는다. 키 패턴(`KEYS`·`SCAN`)에는 룸 이름을 쓰지 않는다.
- **클라이언트 IP:** 신뢰 프록시 뒤에서 "오른쪽부터 첫 신뢰 불가 주소" 규칙을 쓴다. 핸드셰이크 제한기의 IP 표는 상한이 있다.
- **백엔드 호출:** 리다이렉트를 따라가지 않고, 환경의 프록시 설정을 무시하고, 응답 크기 상한·시간 제한이 있고, 로그에서 자격 증명을 가린다. RPC는 세션별·전체 동시 실행 상한이 있다.
- **시간:**
  - 유휴·핑·인증 만료는 단조 시계로 잰다(벽시계 역행에 안전).
  - 설정 검증이 유휴 > 핑 같은 관계까지 강제한다.
- **동시성:**
  - presence의 생성·삭제는 샤드 잠금 하나 아래에서 일어난다(C5).
  - 축출과 join이 겹쳐도 세션 종료 때 정리가 한 번 더 돈다.
  - Hot slot의 깨움과 비움 순서는 깨움을 잃지 않는다.
  - 레지스트리 잠금 순서는 "사용자 색인 → 세션"으로 일관된다.
- **이력:** 단일 노드 링과 Redis 읽기 스크립트 모두 정확히 복구할 수 없으면 `recovered: false`를 준다. 한가한 링은 정리된다.
- **설정 치환:** 파싱 뒤의 값만 바꾸므로 구조를 바꿀 수 없다.

**관찰(수정하지 않음):**
- **클러스터 join이 기다리는 동안 그 세션의 송신 큐가 비워지지 않는다.** 구독 확인은 최대 5초, 이력 읽기는 최대 2초를 기다리고, 그동안 이벤트 루프가 멈춰 있다. 실제로 이 대기가 길어지는 건 Redis가 멈췄을 때뿐이고, 그때는 Redis를 거치는 룸 트래픽도 함께 멈춘다. 큐가 차서 신뢰 전달 세션이 "느린 소비자"로 닫힐 위험은 낮다고 판단했다. join을 이벤트 루프 밖으로 빼는 것은 큰 구조 변경이다.
- **Redis 이력 상태 해시에 노드 프로세스마다 중복 제거 필드(`n:<node id>`)가 하나씩 쌓인다.** 읽기는 특정 필드만 하므로 성능에는 영향이 없다. 에폭이 바뀌면 지워진다. 오래 사는 룸에서 배포가 잦으면 재시작 한 번에 약 40바이트씩 는다.
- **JWKS 첫 조회가 끝나기 전에 동시에 들어온 다른 접속은 503을 받는다**(재시도로 해결). 노드 시작 직후 잠깐만 생긴다.
- **클러스터에서 사용자별 한도로 가장 오래된 세션을 축출하는 경쟁의 거절 사유:** 축출 대상이 아직 등록 전이면(F2의 doomed) 그 등록은 "replaced"로 거절된다. 원래 사유인 `max_sessions_exceeded`가 아니다. 드물고, 클라이언트 동작(1008)은 같다.

## 사각지대 (아직 검증하지 않은 것)

- (해소) 부하 테스트는 BENCHMARKS, 멀티 노드는 ADR 0011과 카오스 테스트, mdBook 잔여물은 문서 정리로 없어졌다.
- 남은 사각지대 (2026-10-21):
  - 클러스터 펜싱은 룸 발행만 덮는다(0.2): 슬롯 없는 노드의 발행은 Redis가 거부한다. 세션 표·멤버십 쓰기는 막지 않고, 노드가 멈춘 뒤 정리된다(ADR 0011 「출시 전 검토」 수정 3).
  - 무작위 장애 soak의 네트워크 장애는 노드–Redis 구간의 TCP 프록시 수준이다(지연·blackhole·리셋, 0.2). 패킷 손실·재정렬·비대칭 분할(tc/netem)과 노드–클라이언트 구간은 아직 넣지 않았다.
  - Sentinel 장애 조치는 soak에 섞지 않았다. 따로 두 테스트(`cluster_sentinel.rs`, `cluster_sentinel_ticket.rs`)로만 확인한다.
  - 테넌트 간 공정성: 측정했다(BENCHMARKS 「테넌트 공정성」). 기아는 없지만 격리도 없다. 한계 근처에서 다른 테넌트의 p99가 11~27배로 는다. 테넌트별 송신 큐는 0.2 과제다.
- **간헐 실패 (2026-10-19) — 원인 확정·수정:** `tests/jwt.rs::invalid_tokens_are_rejected`의 "bad signature" 토큰이 가끔 **통과**했다(두 번째 발생 때 메시지 보존). 제품 결함이 아니라 테스트 결함: 서명의 마지막 글자를 `'A'`로 바꿔 위조했는데, 이미 `'A'`였거나 마지막 글자의 하위 비트(base64url 패딩 비트, HS256 서명 43자의 마지막 2비트)만 달라 같은 서명으로 디코딩되는 경우가 있었다. 서명 가운데 글자를 확실히 다른 값으로 바꾸도록 수정. 첫 발생 때의 "메모리 압박 타임아웃" 가설은 틀렸다.
